# 知夏的方块日记：圆形人物、横向人物窗与 B 站留言姬

日期：2026-10-29；分支：mc；版本：1.0.0；修订：04；状态：设计已定稿。以[定稿说明](定稿说明.md)和[权威布局配置](../../../configs/layouts/mc-landscape-v1.json)为后续实施基准，纳入后台左右切换要求，替代修订03的位置固定方案。

**定稿方案：1920×1080全屏游戏＋默认右侧、后台可切到左侧的连续上滚留言＋右下264像素圆形人物。另保留320×180横向人物窗，以及可替换留言栏的横向飘屏。**

“直播姬”在本次需求中指 Bilibili 留言姬／弹幕姬。本轮重构的是观众留言展示和人物构图。推流客户端沿用现有项目方案，其选择不决定留言层的视觉结构。

已完成可操作的样稿、原创样式、权威布局、开源检索、素材规范，以及后台左右位置配置、持久化和实时投影。当前人物是原图裁切演示，未生成新横屏人物视频；留言是本地示例，游戏是原创占位插图。后台联动使用隔离的本机测试服务，没有接通 B 站、启动游戏或推流。

## 1. 人物方案可行性与取舍

| 方案 | 1080P显示尺寸 | 主体媒体几何面积占比 | 相比修订02的4%主体面积 | 实际适用性 |
|---|---:|---:|---:|---|
| 圆形遮罩，默认 | 直径264 | 约2.64% | 减少约34% | 面部辨识度好，适合边玩边聊；边缘会裁掉肩膀和大幅手势 |
| 横向小窗，备选 | 320×180 | 约2.78% | 减少约31% | 低高度、取景可设计，适合头肩和小幅动作；同尺寸中脸部与手势需要取舍 |
| 旧竖窗，历史方案 | 216×384 | 4% | 基准 | 保留原竖屏素材全貌，但占据更高的游戏区域 |

圆形外接正方形面积为3.36%，圆外四角透明；2.64%按圆形本身计算。横窗比例为16:9。以上未累计姓名条、边线和阴影，不能视作节目全体叠层的遮挡率。两版人物的主体下边都在996像素，保留相同落点感。

圆形只需对人物媒体容器使用50%圆角并裁切溢出，不需要把整幅游戏变成圆形，也不要求人物先抠成透明背景。当前宿舍背景可以保留在圆内。若改为纯人物透明剪影，是另一项需要抠像、边缘和编解码验收的工作，本方案并不依赖它。

横向构图可通过真正重做16:9头肩／上半身素材实现；不能把720×1280竖图横向拉宽，也不能把原图裁切描述成新拍摄出的宽背景。当前样稿为了可比较，只演示以下原图取景：

| 模式 | 原图坐标中的取景框 | 真实性边界 |
|---|---|---|
| 圆形 | X80、Y215、560×560，再套圆形遮罩 | 原图的脸和上肩；没有新增动作 |
| 横向 | X0、Y230、720×405 | 近景头肩裁切；原有膝前双手基本不可见 |

推荐圆形用于常态MC游玩，横窗作为可选构图。用户可在本地样稿直接切换。新素材准备好后应在同一唯一播放端中切换取景，不再开一个并行有声播放器。

## 2. 开源参考与技术选择

已经从搜索引擎与 GitHub 检索相关项目，完整的按Star排序表和时间快照见[B站留言姬开源选型](B站留言姬开源选型.md)。其中：

- [blivechat](https://github.com/xfgryujk/blivechat)：参考它的连续消息、身份层级、付费消息结构及自定义CSS／HTML扩展方式。
- [Bilibili Live Chat](https://github.com/Tsuk1ko/bilibili-live-chat)：参考浏览器留言组件的展示方式。其当前文档要求开放平台连接自己的直播间，不能把旧教程中的“只填任意房间号”作为接入承诺。
- [blivedm](https://github.com/xfgryujk/blivedm)：当前项目已有采集入口，适合作为统一事件链路的基础；它本身不负责留言美术。
- [神奇弹幕原仓库](https://github.com/iwxyi/MagicalDanmaku)：作者已公告停止维护并归档；本方案不把它或旧Fork作为新系统基础。

以上都不是 DeepSeek Harness / DSH 原生插件。blivechat 的“插件”属于它自己的模板／扩展体系，不能直接等同于DSH插件。我们采用“复用现有采集和节目调度，原创MC留言投影”的方案；没有再添加一个独立回复机器人。

本目录的[blivechat-zhixia.css](blivechat-zhixia.css)按[官方选择器文档](https://github.com/xfgryujk/blivechat/wiki/自定义CSS参考)编写，包含普通消息、身份颜色和醒目留言的外观候选。本地预览通过别名类复用同一套外观。尚未安装上游插件、导入真实blivechat版本或验证完整DOM兼容，因此不能称为“即贴即用、已接通”的插件成品。未复制商业皮肤或他人直播间图片。

## 3. 横屏布局和保护范围

坐标以1920×1080设计画布计，机器配置见[layout-spec.json](layout-spec.json)。

| 元素 | X | Y | 宽 | 高 | 行为 |
|---|---:|---:|---:|---:|---|
| 游戏 | 0 | 0 | 1920 | 1080 | 底图满屏、16:9，不为留言挤出侧栏 |
| 顶部小标签容器 | 32 | 24 | 1856 | 56 | 只有左右标签有半透明底，中间透明 |
| 连续留言 | 32／1480 | 136 | 408 | 480 | 左侧／右侧预设；向上滚动，最多4条 |
| 礼物短通知 | 32／1480 | 632 | 408 | 56 | 跟随留言侧边；最多1条，7秒；无事件时隐藏 |
| 圆形人物 | 1624 | 732 | 264 | 264 | 默认；姓名条少量外伸 |
| 横向人物，替代圆形 | 1568 | 816 | 320 | 180 | 16:9圆角窗，不与圆形同时显示 |
| 当前口播字幕 | 320 | 840 | 1120 | 84 | 最多2行，与两种人物窗均分离 |
| 人物状态 | 随人物水平对齐 | 1032 | 随人物 | 24 | 短句，无大卡片 |
| 横向飘屏，替代留言 | 32 | 108 | 1856 | 104 | 顶部2轨；默认关闭 |

游戏底图仍为100%画布；浮层会遮挡部分世界内容，不能称为100%无遮挡。留言容器没有整块固定不透明侧栏，只有独立消息带半透明背景。进入背包或特殊HUD时应允许导播收起人物、留言、包装。

后台“MC 弹幕位置”设置对应overlay.mc_chat_side，只接受left/right、默认right。切换直接移动留言与礼物容器，保留消息节点、队列和计时；人物、字幕、游戏和顶部飘屏方向固定。位置通过现有Room配置保存并实时同步，离线样稿的本地切换不会冒称后台保存。

| 初始保护范围 | X | Y | 宽 | 高 |
|---|---:|---:|---:|---:|
| 准星与中心操作 | 800 | 380 | 320 | 320 |
| 血量／饥饿／快捷栏 | 480 | 936 | 960 | 144 |
| 原生顶部Boss条 | 576 | 0 | 768 | 92 |

上述保护范围已经体现在样稿，但不构成所有MC界面自动避让的保证。右下持物、声音字幕、服务器插件HUD仍需真实客户端逐项验收；未获得可靠UI状态前提供明确的手动收起操作。

## 4. 留言姬的外观与显示规则

视觉沿用知夏的日光宿舍：浅蓝 #7898B7、植物绿 #547B60、木色 #B38964、纸白 #F8FBFC、深灰蓝 #263D4B。游戏保持自身颜色。留言为深灰蓝半透明小气泡，昵称浅蓝，房管浅绿，醒目留言木色；圆形人物和留言中的圆头像形成呼应。

| 信息类型 | 展示 |
|---|---|
| 普通弹幕 | 占位头像／可信头像、昵称、正文，按到达顺序进入连续留言 |
| 舰长／房管／主播 | 仅依据可信平台元数据标记；未知时保持普通身份 |
| 表情 | 正式版本按可信资源映射渲染，缺失时文字回退；样稿使用文字，不拉取外部头像或表情 |
| 醒目留言SC | 在同一连续流中带独立类型标识；无需另建精选问题卡 |
| 礼物 | 小型临时通知，未来按可信用户ID、礼物ID和时间窗合并；不加人声 |
| AI口播 | 只进入当前播放字幕，和观众留言分开 |

“醒目留言”是平台事件类型，不是“知夏正在看某条弹幕”。本方案不会恢复旧的精选问题卡，也不按AI是否选中决定评论能否显示。没有付费金额元数据时不显示猜测金额；没有身份元数据时不根据昵称推断舰长或房管。示例中的身份、礼物全部是虚构测试数据。

默认连续留言规则：

| 项目 | 当前样稿 |
|---|---|
| 可见上限 | 4条，每条100像素；正文最多2行 |
| 字号 | 昵称17、正文24设计像素 |
| 新消息 | 底部进入，已有消息上移；320毫秒过渡 |
| 消费速度 | 最快每秒1条；超过容量移出最旧一条 |
| 队列 | 最多24条，等待超过20秒丢弃 |
| 展示时长 | 预览活动时钟24秒；暂停时固定便于检查 |
| 文本限制 | 昵称10、正文32个Unicode字符；原文由管理端保存 |
| 安全插入 | 纯文本节点，不解释观众HTML；输入框不会生成房管身份 |
| 减少动态／隐藏 | 暂停预览动画和队列消费，不冒称平台或游戏停止 |
| 页面结束 | 关闭定时器、观察器、动画和事件监听 |

在真实节目中，事件过期按平台接收时间判断。预览的暂停功能用于检查画面；不能让平台断线后把过期事件补放成新消息。表情、真实头像、礼物连击合并、删评撤回与审核仍属接入阶段工作。

横向飘屏保留2轨、140像素／秒、52像素间距、同屏最多6条的规则。两种评论样式默认互斥，不把同一评论同时在两处重复播放。主播端烧录的留言与平台播放器弹幕也可能重复，正式端需检查观众实际看到的密度。

## 5. 统一链路与现有代码差距

建议链路：

~~~text
B站平台连接（沿用单个采集入口）
  → 事件校验／去重／屏蔽／标准化
  → Room统一事件
      ├→ MC留言展示：仅负责滚动、身份、礼物
      └→ DSH节目调度：结合游戏事实决定是否回复
          → 唯一TTS／人物播放端 → 播放回执与当前字幕
~~~

留言显示不会执行游戏命令。观众指令只能作为候选意图进入调度，由游戏权限和当前事实约束；聊天组件不直接调用Mindcraft。采集、展示、选择回复、完成口播分别记录，不能把“已上屏”当成“已经回答”。

本次已读到的实际代码：

| 文件 | 当前能力 | 正式MC版本需要补齐 |
|---|---|---|
| backend/room/defaults.mjs、web/admin.html、web/admin.js | 已实现MC左右位置的校验、后台选项与配置保存 | 按合法设备发布流程启用 |
| web/mc-chat-position.js | 已实现Room状态到留言／礼物位置的投影，并在本地联动验证 | 正式MC输出复用同一控制器 |
| scripts/platform_blivedm.py | 普通弹幕、礼物、SC转事件 | 元数据版本核验；角色、头像、礼物ID、可靠金额、撤回等字段按需增加 |
| backend/room/manager.mjs | 统一publicMessage投影 | 保留经核验的身份元数据、事件类型；不要静默丢掉新字段 |
| web/room-overlay.js | 720×1280竖屏、评论和精选卡、字幕 | 增加独立MC布局配置；MC模式排除精选卡，采用有界滚动渲染 |
| web/room-overlay.css | 竖屏场景样式 | MC命名空间、透明横屏根画布、两种人物容器和留言预算 |
| integration/obs.html | 现有正式源入口，文件名是历史命名 | 复用正式播放权威，增加明确MC输出入口／布局配置 |
| web/dsh-playback.js | 正式播放、回执、取消和epoch相关逻辑 | 保留单一权威，形状切换只改媒体显示 |
| configs/characters/female-a.json | 固定720×1280、25FPS和旧动作库 | 新素材另立版本；不能只改一个宽高字段就宣称整链兼容 |

现有blivedm转发没有完整转发头像和角色；publicMessage也没有这些字段。样稿中的蓝／绿身份不能作为真实接入已经具备这些能力的证据。公共观众页只接收可公开事件，平台Cookie、身份码和密钥留在后端；不采用关闭浏览器网页安全机制的接法。

## 6. 素材重制与推理成本

详见[人物素材重制规范](人物素材重制规范.md)和[50段动作改编清单](motion-reframe-plan.csv)。清单来自现有真实索引：2段待机＋48段手势，每项状态均为计划，未生成、未验收。

可以复用现有MuseTalk／Whisper／VAE、O07／F07及唯一DSH流程，优先制作匹配新取景的动作源并重新预处理，无需仅因为换形状就购买或更换模型。新视频、脸框坐标、动作索引、缓存和媒体尺寸契约都需重新校验；模型是否支持特定新画幅以该版本实测为准。

圆形遮罩只改变浏览器显示，不会自动把GPU推理量从4%降到2.64%。新源候选640×640、960×540也不能按像素比例直接推算速度：脸部处理、批量、编码和游戏竞争共同决定成本。当前FP16 batch4基线保留，不能把旧竖屏成绩用于新素材宣称。

先完成四类短样本的构图／口型／动作验收，再决定是否批量重制48类。旧原图、原动作库、历史成绩和发布指针保留。不同构图的派生素材使用单独版本，避免覆盖当前已接受素材。

## 7. 正式合成与故障处理

正式节目仍规划为下层全屏游戏捕获，上层单份透明MC节目源。人物、留言、字幕、小标签和必要的故障遮罩都由这份节目源协调。样稿含不透明游戏占位图，不能直接当正式透明源使用。

具体推流客户端的网页来源、透明合成、声音路由与支持帧率需在实际安装版本验证。沿用项目既有官方推流工具，不因参考项目README提到OBS就切换推流平台。若网页来源能力不足，应先确定受支持的本机合成方式再实施，而不是启动第二个有声播放器凑图层。

| 状态 | MC观众画面 |
|---|---|
| 日常游玩 | 全屏游戏、连续留言、小人物；实际说话时出现字幕 |
| 弹幕互动 | 布局和人物大小不变；更新真实正在播放的字幕 |
| 暂离休息 | 请求暂停→确认后遮罩；未确认不显示“游戏已暂停” |
| 画面恢复 | 遮旧游戏帧、清失效字幕、静态人物明确标记；弹幕通道独立处理 |

媒体request_id、runtime_epoch、取消版本和正式播放回执仍由唯一权威维护。导播预览、留言层和管理页都不推进口播完成，不增加自动朗读或第二个AudioContext人声输出。私聊不进入观众留言，也不自动转为观众记忆。
