**以撒直播的逐项耗时、两台主机对比与优化顺序**

测量日期：2026-11-09，报告整理至2026-11-10。分支：`issac`。被测部署为 `72e9ea16bf9148256b1e917c032129004ba6e432` / `issac-72e9ea16bf91-59c55ebe`。本文是性能诊断，未修改部署中的游戏、声音、口型或决策代码，未产生新的录播或性能验收结论。早期不同 Python 版本的预试保留，本文的双机数字统一使用 Python 3.13.1、Lupa 2.8、Lua 5.3。

**结论与原因**

已经直接测到两类 CPU 开销：游戏主线程中的 Lua 避险计算，以及 Python 控制进程中的高频存档巡检和外围处理。前者直接挤占游戏更新与渲染，后者增加控制链负担和响应延迟。原渠道 DSH 的秒级决策、主动喝水造成的正常暂停，还会产生另外两类停走体验。

用户确认，本机流畅的运行组合是“以撒自动游玩，未同时运行奶妹和录制”。因此两次体验的负载不相同。同一段当前避险代码、同一组输入和相同解释器的对照进一步显示：4090 主机的执行耗时约为本机的两倍。显卡性能无法补偿这条串行 CPU 路径。与此同时，尚未取得双机同一场真实战斗、同时连续说话和正式录制的完整对照，不能把所有差异精确归为某一个硬件指标。

**1．先区分三个帧率**

以撒的 `MC_POST_UPDATE` 通常每秒30次，`MC_POST_RENDER` 每秒60次。28～30次逻辑更新不能当成距离60次逻辑目标还差一半。依据：[Isaac API 的回调说明](https://wofsauge.github.io/IsaacDocs/rep/enums/ModCallbacks.html#mc_post_update)。

游戏原生渲染、人物25帧、节目容器30帧分别计量。原生交换缓冲次数高，或者成片能解码出9000帧，都不能单独证明游戏区域持续产生了9000个不同画面。

**2．真实300秒录播中的主线程耗时**

来自此前正式录播 `300-20261109-fps-r3/真实录制记录.json` 的第5号样本，录制约第27.07秒、房间未清场。这里是120次 Lua 更新的窗口计时，沿用该片实际源代码；其避险算法与当前 R7 一致。它不是本轮合成回放的数据。

| Lua 更新阶段 | 每次更新平均耗时 | 占所测 Lua 总耗时 |
|---|---:|---:|
| 移动及安全检查 `movement_safety` | 21.750 ms | 75.3% |
| 状态采集与交换 `state_exchange` | 4.892 ms | 16.9% |
| 瞄准与输入守卫 | 1.200 ms | 4.2% |
| 观察守卫 | 0.650 ms | 2.3% |
| 工具与其他守卫 | 0.383 ms | 1.3% |
| **合计** | **28.875 ms** | **100%** |

同一窗口 Lua 更新 P95 为41 ms、最大49 ms；原生 OpenGL 渲染约49.47 FPS，渲染间隔 P95 为53.64 ms、最大122.32 ms。即使其他时间较快，这些长帧也会形成明显顿挫。

每秒30次逻辑更新的周期是33.33 ms，每秒60次显示的间隔是16.67 ms。该窗口仅 Lua 就接近一个逻辑周期，并经常超过一次显示间隔，还没有加上游戏本身的其他工作。之前已测的 `candidate_safety` 3.225 ms、`movement_forecast` 1.250 ms 属于移动检查内部子项，不能再与21.750 ms相加。

整个旧录制非暂停区间的逻辑推进中位数为28.15次/秒，最低19.86次/秒。不能由此宣称每秒稳定60次逻辑，也不能只用渲染中位59.47 FPS掩盖长帧。

**3．移动避险内部，到底花在什么计算上**

本轮把生产 Lua 中的预测函数提取到独立环境，在4090的真实游戏 Lua中使用原生 `Vector` 做可重复测试。游戏保持普通暂停；房间几何采用固定桩，12个敌人、32个弹丸都是合成输入，不向真实游戏生成实体，不改变数值、物品或存档。以下解释计算热点，不冒充上面真实战斗窗口的逐条分摊。

无分段计时的96次重负载预测平均28.869 ms；另一组96次分段计时平均29.121 ms。细分阶段互不重叠：

| 一次重负载预测的阶段 | 平均耗时 | 分段总耗时占比 |
|---|---:|---:|
| 弹丸扫掠碰撞 `projectile_sweeps` | 15.700 ms | 53.9% |
| 敌人接触碰撞 `contact_sweeps` | 6.991 ms | 24.0% |
| 各候选方向的攻击与路线评分 | 2.286 ms | 7.9% |
| 移动轨迹和炸弹预测 | 1.614 ms | 5.5% |
| 三个时点的附加危险评分 | 1.180 ms | 4.1% |
| 最终瞄准、路线守卫 | 0.764 ms | 2.6% |
| 候选方向安全检查 | 0.512 ms | 1.8% |
| 实体准备与路线准备 | 0.055 ms | 0.2% |

当前计算要比较9个候选方向，每条预测10步。仅重负载场景中的一层检查，就涉及 `9×32×10=2880` 段弹丸相对运动检测，以及 `9×12×10=1080` 段敌人接触检测；另外还有多时点评分和最终守卫。反复创建、运算原生向量，读取其属性，求相对距离和轨迹最近点，是这里的主要工作。路径搜索并非这组测试中的最大单项。

原生微测试还记录到 `(origin + vector * 2):Length()` 约1.46微秒/次。单次很短，反复组合后会累积。CPU时间与整段墙钟时间接近，支持这段回放以计算为主；Windows线程CPU计时存在15.625 ms量化，短分段不能用它计算精确占用率。分段耗时采用高分辨率计时器，未由标称CPU频率倒算。

同一原生向量回放里，最初冻结的 `native129` 重负载为31.979 ms，当前为28.869 ms；现有缓存已经有所改善。原实现本来就包含9方向、多步接触预测，因此不能说全部避险开销都是接入奶妹时新加的。

代码位置：`integration/isaac-agent/mods/IsaacJev/main.lua` 的 `predictiveCombatMove`、`contactClearance`、弹丸循环与接触循环。

**4．本机为什么更流畅：相同代码的对照**

本机实际硬件为 i5-12400F，6核12线程、RTX3060 12GB；4090主机为两颗 Xeon E5-2673 v4，总计40核80线程。Lua的这一段计算串行执行，多出的核心数不能自动拆分同一条预测。80个逻辑处理器上一个线程占满，在整机平均数中也仅约1.25%；整机CPU百分比低不能排除它，但本轮也没有据此宣称真实战斗线程始终100%占用。

本轮没有启动本机原项目或修改原项目。只读提取其冻结版 `local-control/releases/isaac-local_native129_2026-11-06_22-22-46/01_成品程序/mods/IsaacJev/main.lua`，与当前函数分别放进相同测试环境。每组5轮、每轮300次更新，下面取各轮平均耗时的中位数。

| 当前代码、相同输入 | 本机 i5-12400F | 4090主机双路 Xeon | 远端耗时/本机耗时 |
|---|---:|---:|---:|
| 1敌人、0弹丸 | 0.943 ms | 2.133 ms | 2.26倍 |
| 4敌人、8弹丸 | 2.888 ms | 5.630 ms | 1.95倍 |
| 12敌人、32弹丸 | 8.103 ms | 16.012 ms | 1.98倍 |

| 原冻结 native129、相同输入 | 本机 | 4090主机 |
|---|---:|---:|
| 1敌人、0弹丸 | 1.345 ms | 2.684 ms |
| 4敌人、8弹丸 | 3.600 ms | 7.004 ms |
| 12敌人、32弹丸 | 10.680 ms | 19.607 ms |

两机使用同一 Python 3.13.1、Lupa 2.8、Lua 5.3，回放脚本哈希一致，方向结果校验值一致。这是受控代码回放，向量在两机均用Lua表实现、房间几何为桩，因此数值不能直接换算为真实游戏FPS，也不能与上一节原生向量耗时绝对比较。它能够确认同一工作量在两台主机上的吞吐差异。

此外，本机原先只有自动游玩；远端还有DSH状态处理、人物动画、声音、口型、浏览器叠层和官方录制等工作。当前用户感受到的差异同时包含机器执行能力与运行组合差异。CPU实际睿频、NUMA跨节点开销和温度是否另有贡献，本轮没有充分测量，不下定论。

**5．另一项实测大户：存档保护巡检**

在实际控制进程上进行了45秒、100Hz的外部只读栈采样，不重启或改写控制进程。该短段含一次喝水暂停，未遇战斗，也没有启动正式录制。采样工具：[py-spy](https://github.com/benfred/py-spy)，使用非阻塞模式；记录有115个采样错误，不把采样占比当作逐函数精密CPU计时。

控制进程 `watchdog` 的主要活跃栈落在 `SaveProtection.admit_current → verify → Path.resolve / stat`。源码每轮先等待250 ms，再在自动模式下调用完整保护检查。本轮随后在游戏正常暂停、相同路径上独立测了12次 `verify()`：

| 巡检项目 | 实测 |
|---|---:|
| 每次完整校验耗时中位数 | **416.601 ms** |
| 12次耗时范围 | 407.419～425.619 ms |
| 保护基线文件数 | 2 |
| 递归根目录数 | 2 |
| 两根目录内的文件数 | 1223 + 3 = **1226** |
| 独立cProfile运行中，路径最终解析系统调用 | 2470次/检查 |
| 同一cProfile运行中，文件状态系统调用 | 1298次/检查 |

完整校验伴随对大目录的递归遍历和每个文件的路径解析。分开的cProfile测试中，最终路径解析自身约233 ms，文件状态调用自身约116 ms；该次带剖析的总耗时约517 ms，不能把这两个数字直接当作无剖析416.6 ms的精确分摊。

250 ms是循环等待间隔，实际检查还要花约417 ms，因此不能说该检查真实稳定运行在4Hz。这也不是“游戏主线程每帧等待417 ms”：检查在独立Python控制进程中。它制造持续的CPU、文件系统操作和控制进程内线程竞争，具体传导到每一帧的份额尚未单独隔离。

实际外部采样区间连同开始恢复共约46.63秒，控制进程累计使用24.00 CPU秒；其中看门狗线程8.172 CPU秒，规则工作线程6.484 CPU秒，声音包络线程2.906 CPU秒。CPU秒可跨线程累加，不等于对应的画面停顿时长。该段包含约26秒主动暂停，不能把平均数外推为全程战斗占用率。

这里的声音包络线程是本机游戏音量会话查询与调节，属于CPU侧系统接口调用，不是声音模型推理。规则工作线程采样主要落在 `build_candidate_set / navigation._route_distances / _neighbors`。它与游戏内的Lua轨迹预测是两份不同工作。

代码位置：`integration/issac/strategy_host.py::watchdog`，`integration/issac/saves.py::admit_current / verify`，`integration/issac/native_audio.py::run / apply`。

**6．Python状态包和DSH的延迟，分别说明**

| 处理路径 | 测量结果 | 对体验的作用 |
|---|---:|---|
| 旧录制第27秒的完整Python状态包 | 32.863 ms/包 | 规则、状态维护与事实更新响应 |
| 其中规则与战略服务维护 | 26.222 ms/包 | 同上，不是DSH模型请求耗时 |
| 其中事实更新 | 4.132 ms/包 | 状态事件与数据库账本 |
| 其中过滤 | 2.391 ms/包 | 状态过滤 |
| 本轮7个非暂停采样点的状态包 | 中位32.935 ms，最高采样值62.581 ms | 说明外围延迟在空房也存在；不是逐包P95 |
| 独立完整控制器回放，同一冻结输入 | 本机2.530 ms，远端4.864 ms中位数 | 新历史、独立日志与数据库，不能代替长期运行结果 |
| 旧录制窗口中37次DSH决策 | 中位3264 ms，P95 5394 ms，最大8148 ms | 决定拾取、路线选择和说话的反应时延 |
| 同一窗口37次工具调用 | 中位18 ms，P95 178 ms | 游戏知识与状态工具调用 |

实际采样在状态处理期间见到目录创建/检查、文件状态查询、数据库到期事件更新和状态复制；完整控制器的独立剖析也确认了大量 `deepcopy`。但是离线控制器回放并没有完整重现实际32～63 ms的开销，剖析本身还会增加耗时。因此剩余差额需要继续按CPU计算、锁等待、文件操作和同步写入的边界计时，不能虚构为“全部是深复制”或“全部是硬盘慢”。实际事件库约1.22 MB、946条事件，本轮没有证明数据库容量本身已成为瓶颈。

游戏内状态发送是非阻塞TCP，收到上一轮回复后按逻辑帧节流，通常最多约10Hz。不能描述成Lua每帧同步等待一次模型请求。背包全量观察每15个逻辑帧刷新一次，约0.5秒；它会遍历约733个道具编号及临时效果，属于状态采集子项，未独立细分耗时，不应把它说成每帧全量扫描。

DSH仍是原 `gpt-6-luna / Responses / 原API渠道`，在另一进程异步工作。几秒的决策时间会导致战略等待或旧台词取消，不能直接加到一次Lua更新的28.875 ms上。旧正式录制完整时间窗口内有39次语音排队、34次取消、4次实际完整播报；这些是窗口内事件计数，跨边界事件并未逐一配对，不能据此直接计算完整转化率。它提示自然解说的调度仍有问题，不能用“已经排队”充当“观众听到了”。

**7．人物、录制与暂停的影响边界**

本轮在相同的暂停游戏、原生向量重负载回放下，先保留就绪的人物服务，再正常停止本轮应用所属服务：重负载预测由28.869 ms降至26.881 ms，约减少6.9%。官方直播姬保持打开。该对照测的是服务已加载、人物基本空闲的状态，没有连续说话和正式录制，不能外推整套音画的最坏竞争只有6.9%。测试后原候选已恢复。

已有显存快照为使用13807 MiB、空闲34816 MiB，GPU利用率55%、编码单元1%，系统可用内存约50.8 GB。它只能说明当时没有容量耗尽证据，不能代替战斗峰值或显卡时序分析。

正式录制日志的渲染滞后为6/9737、编码跳帧为6/9735，约0.06%。底层通过原生OpenGL共享纹理捕获游戏；浏览器只承担透明人物叠层。现有证据支持先处理源游戏长帧，没有显示大量整帧编码丢失是主要原因。成片中游戏区域可见更新不足，仍需在修复后重新实录复核。

主动喝水要求在安全清场状态先真实普通暂停，再放下手柄、喝水、回持柄。此前观察到约25～26秒的这类暂停，期间原生渲染可保持60次/秒而游戏逻辑停止。清场空房往返、等待DSH授权也会表现为停走。它们需要改动作和决策编排，与游戏画面的长帧分别验收。

本轮另一次60秒真实正常游玩只经过空房，1305次非暂停Lua更新平均总耗时约2.290 ms，其中状态交换1.443 ms、移动避险0.352 ms。这个结果说明负载随房间内容变化，不能用空房低耗时否认战斗热点，也不能把受控重负载29 ms套到所有游戏时刻。

**8．建议按这个顺序优化**

| 顺序 | 要改的具体内容 | 保留的约束与核验 |
|---|---|---|
| P0 | 存档保护采用启动完整校验、运行期快速身份/槽位检查、目录变更监听、变更文件精确校验及周期完整复核；减少1226文件的反复路径解析 | 保护范围和失败停机语义保留，新槽1/2、重定向及未授权文件仍须及时发现；先完整实现与审阅再统一测试 |
| P0 | 减少避弹内层原生向量创建和属性读取，单次更新复用坐标、速度、半径和不变量；保守排除确定不相交的轨迹 | 保留9方向、预测时域、所有危险守卫；原生向量浮点精度与Lua标量不同，需验证边界和安全结论，不能直接删检查或降安全采样频率换帧率 |
| P1 | 给完整状态包补齐CPU/锁等待/文件操作分项；让日志、快照、静态地图和目录检查避免重复工作 | 事件因果、过期取消、授权执行和必要持久化保持，不把未量化差额全部归到某一项 |
| P1 | 复用规则候选路线数据，避免同一房间重复建立相同距离场；减少游戏音量会话重复枚举 | 规则继续只承担实时动作和有界执行，奶妹仍唯一决定全部拾取、物品使用和战略 |
| P2 | 处理清场往返、事件合并、DSH决定与台词过期的调度，以及喝水暂停长度与触发时机 | 沿用原模型、原声音、原口型及真实动作交接，不让规则或另一模型静默代做战略 |
| 验证 | 在真实战斗、连续说话、25帧人物和正式录制同时运行时，重新观察原生长帧、节目游戏区域新画面及连续300秒成片 | 同时比较相同负载，不以空房回放、容器30帧或单一渲染均值替代验收 |

首先优化已测的CPU路径和过密巡检，再决定是否需要改变部署。当前没有证据支持继续降低已冻结的人物512×512来解决Lua热点，也没有依据要求替换奶妹大脑或新增本地LLM。
