# 节目动作输出启动修正

候选 B 的整轮回归和原生游戏检查通过，但首次实际节目运行失败。NCM01 和 FlashHead 均完成初始化；三种形态的真实素材解码、H.264 编码与媒体封包独立诊断通过。节目在记录第一段身体动作时，把带有 `kind` 的动作记录展开传给同名位置参数，实际抛出 `Audit.append() got multiple values for argument 'kind'`。这次失败不属于显存不足。

该轮已经结束，原始失败证据保留于目标机 `state/issac-acceptance/programme-startup-b.json`，所有本轮媒体进程正常退出。没有把它写成画面合格，也没有录制成片。

修正轮 C 将原始动作记录完整嵌套为 `body_event`，日志外层保留 `body_clip_started`。真实身体帧、首尾连接、声音模型、口型模型、人物细节、原模型渠道和 MC 布局均沿用冻结约束。媒体错误直接显示为服务未就绪，关闭接收者并请求正常游戏暂停，不产生静态替代帧；错误类型进入私有审计，避免启动器继续空等。

验证覆盖实际节目输出循环的动作切换和错误暂停，之后仍统一执行原有整轮回归、素材准入、真实音画及同机检查。此文档仅描述修正源代码，不代表新候选已验证或300秒已完成。

候选 C 的五项整轮检查通过，实际 NCM01、FlashHead 和节目动作输出也已启动，首段动作错误消失。但完整启动停在 DSH 就绪检查：`/api/dsh/status` 的真实返回将状态置于 `health.dsh_ready`，启动器却只读取顶层。120秒后正常触发退出，所有所属进程完成清理；本轮已关闭，原证据散列见配套 C 记录。

修正轮 D 改用现成的 `/health` 明确健康接口，保留其后的真实原渠道请求、gpt-6-luna/Responses、五项工具和完整 wiki 准入。启动回归覆盖真实 HTTP 的两种不同封装及完整组件启动次序，不能用“端口开着”代替就绪或跳过原渠道验证。仅此次启动修正，不改变角色、模型、声音、口型、动作、节目几何及验收门槛。

运行环境另外确认4090没有可用音频端点，全部旧端点均为未插入或不存在。已从 VB-Audio 官方下载并核验有效厂商及 Microsoft 驱动目录签名，安装本机 VB-CABLE 音频驱动后 Windows 与直播姬均识别到可用端点，未重启系统。安装自动打开的感谢页面已关闭。驱动只提供本机音频通路，既定 NCM01/OmniVoice 不变，仍需检查实际游戏声音、静音预览、麦克风关闭、单播放权威及混音录制。

候选 D 实际完成整套启动、原渠道验证和七扩展加载；首次语音产生61帧真实音频驱动口型，其中44帧张嘴，随后中断。账本显示正式页面没有任何播放回执，同一播放源每约9秒重新取得权限。原因是页面已使用两阶段播放准备协议：请求 `defer_ready`，核验返回的布尔 `ready`，准备本地输出后调用 `playback/ready`。服务端仍是单阶段实现，忽略该参数、不返回 `ready`，也没有准备确认接口。页面因此拒绝返回值，不发续期；8秒权限到期取消台词，下一帧映射被拒绝。不是模型容量不足，也不能把“后端 authority_ready=true”当作观众听到了声音。

D 已关闭，失败原件及散列保留，所属游戏在标题页正常关闭，官方客户端正常关闭，全部媒体进程正常退出；节目停止一度等待连接排空并超过首个45秒截止，未强杀程序。修正轮 E 补齐两阶段协议，未准备的有效租约仍独占，只有同一消费者、同一当前纪元且未过期的租约能确认；准备前不启动台词。原单阶段调用仍兼容，过期、替换和进程重启不接受旧准备。回归直接使用实际 `web/issac/dsh-playback.js` 与真实 HTTP 路由，核对准备、超过旧到期时长的续租、媒体映射和自然播完回执。

E 同时在服务关闭前释放媒体连接，避免长连接挡住正常退出；逐帧错误只记录有限的协议码，不记录任意异常内容，失败口型观察也保留部分帧、状态和明确失败标记。本轮不放宽口型、尖牙、25FPS、音画同步、长时稳定性或官方300秒录制要求。先完成整轮审阅、提交和冻结，再统一测试；本说明不代表 E 验证通过。
