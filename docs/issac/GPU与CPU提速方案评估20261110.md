**以撒直播的GPU与CPU提速方案评估**

2026-11-10，`issac` 分支。依据前一轮逐项耗时报告、生产源码检查、4090实机环境核查和本轮独立计算测试。当前生产候选仍是 `issac-72e9ea16bf91-59c55ebe`；本轮没有部署新控制器、改动游戏或切换声音、口型、奶妹核心渠道。

**结论**

GPU可以承担避弹中可批量计算的轨迹与距离运算，本轮已在4090上运行成功，并测到了收益。文件巡检、状态持久化、线程等待和原渠道模型响应仍需要各自处理。建议先实施巡检减负和CPU批量计算，再把常驻GPU后端作为重负载选项，最终依据完整链路的延迟选择CPU或GPU。

GPU路径新增的是确定性的规则计算程序，新增AI模型权重为 **0 GB**。奶妹仍通过原 `gpt-6-luna / Responses / 原API渠道` 主导全部战略、物品取舍及自然表达；GPU辅助程序只返回几何计算结果。新增程序全部部署在4090的原生Windows中，不使用Docker、WSL或虚拟机。

**1．哪些开销能交给GPU**

| 已定位工作 | GPU适用性 | 应采用的处理方式 |
|---|---|---|
| 多方向、多步弹丸和敌人相对轨迹、最近距离及碰撞评分 | 高，具备数据并行性 | 一次打包，同批计算多个候选方向与威胁轨迹 |
| 游戏实体、房间、地形及物品API读取 | 需保留在游戏合法线程 | 每次更新复用快照，减少反复访问对象；GPU使用快照中的数值 |
| 1226文件的递归巡检，单次中位约416.6 ms | 低，主要是文件系统与控制开销 | 变更监听、增量校验、快速身份/槽位检查与周期完整复核，保留保护范围 |
| Python目录检查、状态复制、锁与数据库维护 | GPU不是直接解决路径 | 静态内容复用、减少重复工作、合适的异步处理并补齐分项计时 |
| 原渠道DSH的秒级请求与工具编排 | 本机GPU不能直接加速远端请求 | 优化事件合并、状态有效期、调用与表达调度，沿用原模型渠道 |
| 人物模型推理、节目合成与视频编码 | 已有GPU路径 | 保证与新增计算共存，继续观察25帧口型和正式录制长帧 |

此前真实战斗窗口中，移动与安全检查占Lua更新耗时75.3%。当前实现反复访问原生向量对象、创建中间向量并做逐段检测。把数字打包后批量计算，既可以由原生CPU代码实现，也可以由GPU实现；需要比较两种实现完整往返的成本。

**2．4090实机环境与32/64位约束**

实读游戏PE文件头：`isaac-ng.exe` 为 `0x14c / x86`，即32位。现有媒体运行环境是64位 Python 3.10.22、PyTorch 2.9.1+cu128、CUDA 12.8、NumPy 1.26.4；CUDA可用。`nvcc` 未在本次进程的命令搜索路径发现，不能据此断言整机未安装编译工具。

32位进程不能直接加载64位DLL，跨进程通信可以连接两种位数的程序，见[微软进程互操作说明](https://learn.microsoft.com/en-us/windows/win32/winprog64/process-interoperability)。CUDA 12及以后的工具包也已移除32位编译，见[NVIDIA Windows安装说明](https://docs.nvidia.com/cuda/cuda-installation-guide-microsoft-windows/index.html)。

因此，沿用现有64位CUDA运行时的推荐路径是“32位游戏内轻量桥接＋同机常驻64位计算进程”。这不是所有GPU接口都禁止32位的判断；采用旧CUDA、DirectCompute或其他接口会引入另一套实现和兼容验证，本轮没有选择或验证这些路线。

**3．本轮CPU/GPU小规模对照**

独立测试使用9个候选方向、每条轨迹10段，对威胁轨迹计算相对运动线段最近距离和碰撞惩罚。每种规模100次，单次提交对应一次计算请求；GPU每次上传输入并取回9个评分，没有通过攒多帧请求提高吞吐来掩盖单次延迟。

| 威胁轨迹数 | CPU NumPy批量计算中位数 | 普通PyTorch GPU调用往返中位数 | CUDA Graph往返中位数 | Graph往返P95 |
|---:|---:|---:|---:|---:|
| 1 | 0.210 ms | 1.284 ms | 0.263 ms | 0.466 ms |
| 12 | 0.339 ms | 1.306 ms | 0.273 ms | 0.421 ms |
| 44 | 0.628 ms | 1.290 ms | **0.271 ms** | **0.444 ms** |
| 256 | 2.513 ms | 1.332 ms | **0.277 ms** | **0.440 ms** |

44条威胁轨迹的Graph方案相对这里的CPU NumPy实现约快2.32倍；256条约快9.07倍。1条轨迹时CPU更快。256条是额外的合成规模，不代表之前录播中实际存在256个敌人或弹丸。

普通GPU调用需要重复提交多道小运算，固定开销较显著；CUDA Graph捕获后重复执行，可以减少重复提交成本，见[NVIDIA CUDA Graph说明](https://developer.nvidia.com/blog/cuda-graphs/)。传输和同步必须计入评估；NVIDIA也建议减少碎片传输并打包，见[CUDA最佳实践](https://docs.nvidia.com/cuda/cuda-c-best-practices-guide/index.html#data-transfer-between-host-and-device)。

44条轨迹的输入是4840字节，返回36字节。数据量小，吞吐带宽并非这组小测试的主要问题，更需要控制固定调度、同步和进程通信开销。

上述测试有明确边界：

- 输入已在CPU端打包，GPU数字包括本进程内上传、Graph/算子执行、取回和等待，**未包括游戏取数与32/64位跨进程通信**。
- 测试仅是简化数学核心，没有实现完整的墙体、反弹分支、临时免疫、激光、地形、目标评分与授权检查。因此不能拿旧录播的21.75 ms直接除以0.271 ms，宣称完整避弹或游戏获得相同比例加速。
- GPU Graph重放的是现有PyTorch算子图，并非自定义融合CUDA内核；本轮没有比较完整原生C/C++实现。CPU原生实现仍可能进一步改善。
- 对这几组输入做了数值容差检查；256轨迹的最大评分差为0.0625，其余三组为0。没有完成临界碰撞、方向排序及完整规则等价验证。
- 人物服务测试前后均就绪、M03/NCM01约25帧，但当时未持续说话，也未进行正式录制。不能据此承诺口型推理峰值与GPU计算共存时仍保持同样尾延迟。

本次PyTorch分配器峰值约1.10 MiB，预留缓存峰值8 MiB；这不包含CUDA上下文等全部进程显存，也不是生产方案的显存预算。测试进程已退出。没有安装新依赖、下载权重或改动已有模型环境。

| 编号 | 方案 | 适用环节与评估 | 新增AI模型权重 |
|---|---|---|---:|
| **1** | 存档巡检与状态链减负 | 必做。先消除每轮全目录扫描和重复维护，减少控制侧负担；保留完整保护与失效停机语义 | 0 GB |
| **2** | 游戏内原生C或其他批量CPU计算 | 优先建立。游戏API读取留在主线程，把纯数值运算成批传给原生函数，减少Lua与向量对象之间的细碎调用；作为轻负载和故障恢复的基线 | 0 GB |
| **3** | 常驻64位CUDA Graph计算进程 | 已有小核心可行性证据。适合较密集轨迹；使用现有CUDA运行环境，下一步重点验证取数、IPC、完整语义和音画共存 | 0 GB |
| **4** | CPU/GPU按完整成本选择 | 推荐最终组合。先落实1，再比较2与3；只有GPU的完整往返和尾延迟达标时才分配重负载，轻负载用CPU | 0 GB |

**5．方案3/4需要怎样接入**

1. 游戏合法线程每次建立当前数值快照，附带局、房间、帧和观测修订；保留危险、地形和授权守卫。
2. 使用固定容量的紧凑缓冲、共享内存及事件通知，把纯数值交给常驻64位进程。原生API、Lua对象和内存指针不直接交给GPU线程。
3. GPU缓冲与Graph提前初始化并复用；一次传输一批数据，不按每颗弹丸发请求，不为每次更新重建CUDA上下文或计算图。
4. 返回带同一身份与观测修订的候选评分；游戏端验证时效、数值及适用范围，再通过原有规则执行有界动作。跨房间或过期结果丢弃，GPU不决定道具和掉落物取舍。
5. 若当前动作需要当前计算结果，异步提交仍有结果等待成本。不能简单改成使用上一帧结果；必须有经过验证的时效检查和截止时间。GPU超时可由已验证CPU后端处理同一当前状态，无可靠结果时按原有失效流程停止自动并普通暂停。
6. 根据两种后端的实际完整延迟选择路线，并避免频繁切换。不能直接将本次44轨迹的小测试结果冻结为生产切换阈值。

GPU计算与口型模型共用4090。显存有余量不等于调度没有竞争；即使设置流优先级，也不能保证抢占已经运行的任务，见[CUDA流优先级说明](https://docs.nvidia.com/cuda/cuda-runtime-api/cuda_runtime_api/group__CUDART__STREAM.html)。需要在原有声音、25帧口型和官方录制同时工作时检查P95/P99，而不是只看数学运算均值。

**6．合理的收益边界与验证顺序**

假设把旧战斗窗口中整个21.75 ms移动阶段统一提速，其他7.125 ms保持原状，并理想地忽略新增取数/传输开销：

| 假设整个移动阶段的提速 | Lua更新的理想耗时 | 相对28.875 ms的整体提速 |
|---:|---:|---:|
| 2倍 | 18.000 ms | 1.60倍 |
| 4倍 | 12.563 ms | 2.30倍 |
| 10倍 | 9.300 ms | 3.10倍 |

这只是按阶段占比计算的条件分析，未证明整个阶段都能搬到GPU，更不是游戏FPS承诺。文件巡检、状态链、原渠道决策、人物推理和编码均在其他路径上，不能与上表相加成一个串行帧总耗时。[NVIDIA对整体加速上限的说明](https://docs.nvidia.com/cuda/cuda-c-best-practices-guide/index.html)

建议实施顺序：方案1与2形成可验证的CPU基线；再完成方案3的完整后端；达到规则等价、当前状态时效与完整往返要求后，启用方案4。每一轮先完整实现、审阅、提交和冻结，再统一验证。

正式验收要覆盖真实战斗、密集弹幕、房间切换、危险临界条件、物品授权、持续解说与人物25帧，并重新录制完整300秒。同步检查原生游戏长帧、节目游戏区域的新画面、声音口型、状态包CPU/等待/IO耗时；以完整运行结果决定最终后端。本轮仅交付方案评估与计算原型证据。
