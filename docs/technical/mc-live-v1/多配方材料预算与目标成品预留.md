## 1. 解决的业务问题

此前默认材料采集器按目录名称分别计数。“任意木板一块”和“橡木板一块”可能都把同一块橡木板算入已满足材料。采集器因而不再采集，实际合成却仍缺料。另一个问题是目标集合中已有的成品，也可能被后续配方或嵌套工作台、工具制作消费。

现在默认CollectRecipeCataloguedResourcesTask交给ControlledRecipeResourcesTask统一计算所有待制作配方的材料容量；实际CraftPlan也使用同一MaterialAllocation。正在执行的资源合成任务登记目标成品保留量，子任务的实际配方分配同时遵守当前活跃祖先的保留量。背包子类自定义collectRecipeSubTask继续保留。

## 2. 配方组和实际缺口

| 编号 | 处理 | 约束 |
|---|---|---|
| M01 | 内部目标仍为绝对总库存 | 使用实际现存产物计算缺口，再按单批产量向上取整。 |
| M02 | 合并相同材料匹配集合 | 同一集合跨材料格、批次及配方的数量相加；名称不同不代表两份独立库存。 |
| M03 | 容量分配 | 同一背包槽位的每个单位最多分配一次，允许重新分配灵活材料以满足更严格的要求。 |
| M04 | 保留已有目标成品 | 同物品的多个绝对目标取最大值，保留量最多为当前主背包实际现存量；不凭空预留未获得物品。 |
| M05 | 选择采集增量 | 在上游实际可见库存总量上增加真实缺口，装备等不可供容器消费的库存不能让新子任务提前满足。 |
| M06 | 重新核对完成状态 | 工作台等消耗材料后，原默认采集器重新检查当前分配，可继续补料。 |

例如，目标要求保留一块橡木板，同时制作需要两块任意木板的物品。现有一块橡木板和一块云杉木板时，只能消费云杉木板，还需要再采集一块木板。两种木板都在背包里，不代表三份需求已经满足。

同产物、同配方的重复目标合并为较大的总量；同产物却指定不同材料意图或单批产量时明确拒绝歧义。未登记材料没有可用采集入口时在本地以固定错误中止，不标记材料已齐。048时这些材料错误的公开终态仍归为GAME_EXECUTOR_FAILED；049已补入[固定原因上报、后台解释与主播事实](任务失败原因、后台解释与主播事实.md)，完整资源链及真实效果仍待验收。

## 3. 共享容量分配和组件

MaterialAllocation先满足成品保留量，再为材料需求分配剩余容量。保留总量不可被后续材料占用，但算法可将保留记录分配到另一份等价物品堆，为组件要求更严格的真实材料格腾出容量。这只是内存中的分配，不会移动游戏物品。

采集预算使用目录声明的物品匹配集合，作用是选择还需获取的材料。实际合成仍读取当前服务器配方、Ingredient.test及原堆栈组件，见[内部合成确认](资源链内部合成与库存确认.md)和[合成事务](合成事务与服务器同步核验.md)。目录预算满足不能替代实际配方、组件和服务器效果核验。

保留记录参与真实CraftPlan分配，成品保留部分不会出现在材料搬运额度中。公开craft继续使用原新增数量协议；其配方和确认规则保持。实际点击仍由ConfirmedCraftTask逐步等待服务器完整库存、产物、余料和空光标确认。

## 4. 原任务生命周期和采集入口

ResourceMaterials绑定原Session、主线程、世界、玩家及连接。ControlledResourceCraftTask开始时登记自身目标，停止时只移除自己的记录；其他仍活跃的祖先或子任务记录保留。恢复时重新登记当前任务。取消后的清理不搬库存、不关窗、不发物品使用或停止包；根关闭统一忘记原材料状态。

材料采集每次只保留一个具体子任务。优先使用匹配集合完全一致的已登记目录；没有对应目录时选择一个明确可采集物品，按该物品现存量加缺口执行。固定上游的未登记多物品ItemTarget会递归构造同一集合，当前入口避免调用该路径。自定义采集器不被强行改成默认采集器。

子任务结束后检查物品种类和数量是否变化；只在槽位间移动同一批物品不算采集进展。没有数量进展则明确失败。选定次数属于原根，任务重选、停止、恢复或清空活跃记录均不重置次数；原根已有期限继续生效。

## 5. 固定容量边界

| 项目 | 上限 |
|---|---:|
| 每个配方组的目标 | 64 |
| 同时活跃的资源合成记录 | 64 |
| 活跃记录的目标物品种类并集 | 4096 |
| 实际可消费库存 | 主背包36格 |
| 同次分配的要求数量 | 640 |
| 分配算法边访问次数 | 2000000 |
| 同一根任务的材料采集选择 | 256 |
| 单个内部目标的新增产物缺口 | 4096 |

目标物品种类表只保存有界目标；只有主背包中实际存在的目标成品进入容量图。因此64个父目标仍能建立包含新物品的子任务，不因一个过小的全局种类限制误拒绝合法嵌套制作。
