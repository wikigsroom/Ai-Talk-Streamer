# 回基地目标绑定与到达核验

第017轮实现记录。属于[完整交付规划](08-完整交付规划.md)内的工程进展；真实MC验收、路径可达性及完整生存执行仍待完成。唯一基地登记源是A端游戏账本，唯一实际玩家由B端游戏桥控制；本功能不引入第二个玩家、人格写入者或推理进程。

## 1. 目标与数据权威

模型、管理页和弹幕建议只指定`goal={skill:"return_base",base_id}`。公开任务/查询接口拒绝`base_target`及调用方提供的基地坐标。基地必须由操作者在停控、新鲜观测和已知玩家位置下登记；归档与选择仍使用已有双版本约束。登记源是`operator_observed`，不是模型猜测或视觉估计。

| 记录 | 生成方与字段 | 生命周期 |
|---|---|---|
| Base | A的world_bases：世界、编号、修订、位置、半径、登记会话/序号及归档标志 | 位置不提供原地改写接口；需要新位置时归档并重新登记 |
| BaseRef | A的已核验目标投影：game_instance_id、world_id、base_id、base_revision、world_revision | 公开TaskCreate与check_action.params可选提供，用于检查到受理之间的版本绑定 |
| BaseTarget | A从当前登记解析：BaseRef、position、radius、source、registered_world_session_id、registered_seq | 只在A→B的query/task_start及持久Task中携带；任务受理后不可改写 |

BaseRef包含实例，防止迁移到其他安装后借用同名世界；BaseTarget保留登记来源，允许同一稳定世界在新会话使用旧会话登记的基地。登记会话不要求等于当前会话，当前任务的world_session_id仍必须与游戏观测和控制Permit一致。

公开goal不增加任意指令、传送或键鼠参数。基地半径沿用登记的整数1–128；位置沿用Position范围，不额外扩大世界坐标限制。

## 2. 完整调用路径

1. `WorldService.resolveBase`在当前观测世界内查询基地，检查安装、归档、维度及可选BaseRef。解析失败时不创建任务/查询操作，不向B发导航。
2. A的`check_action`把BaseTarget作为独立线协议字段发送，公开QueryRequest仍只有goal及可选ref。B在游戏线程把它解析为不可变`BaseTarget`，核对goal编号、当前安装/世界/维度与可选ref，再交给端口检查，并原样回传该目标。
3. A核对回传目标与发出目标完全相同，再重新读取当前登记。查询期间世界/基地修订改变、基地归档或维度改变时，操作失败，不能进入任务提交。
4. DSH的`game_start_task`与审核后弹幕建议均把成功检查的目标投影为TaskCreate.base_ref。即使检查结束后到提交前发生登记变化，任务受理也会拒绝。直接管理请求未提供ref时，在受理时解析当前登记。
5. A先持久保存原Task.goal、BaseTarget、幂等请求与建议/世界目标引用，再发送task_start。B先持久接受，再在实际执行前两次复核原控制Permit、世界/会话、期限、界面及基地绑定。
6. `MinecraftPort → SurvivalGameExecutor → ExecutorTaskSession → ControlledAltoClefDriver → ControlledTaskFactory`传递同一个类型化目标。Factory再次检查base_id与实际维度，构造同一玩家的GetToBlockTask；不接收独立裸BlockPos基地参数。
7. 执行器结束信号只开启等待。完成信号所在观测及旧/重复序号不能作到达证明；只有之后的新观测确认实际玩家在原维度、三维登记半径内才标记succeeded/verified。证据保存会话、序号、基地及世界修订。未到达为failed/unknown，撤权/换会话为cancelled/unknown。

目前路线仍指向登记位置；登记半径用于后置核验，未宣称已实现按半径优化路径、跨维度旅行或不可达目标自动修复。执行器结束不证明途中安全、没有副作用或能从任意地形到达。

## 3. 修订与重试的边界

A的世界标签、规则及基地登记/选择等会推进world_revision。即使只是标签变化，检查到受理之间也保守拒绝旧ref，重新检查。**任务受理后的BaseTarget固定**；B不持续访问A的SQLite，也不能独立证明自己所见修订仍是A的最新修订。任务执行时的世界/会话/控制围栏与不可变目标是B的依据。基地归档/选择本身仍要求停控，没有“后台改坐标后偷偷把正在执行的路线切到新地点”的接口。

A的task_update与task_ledger核对同时比较原goal和完整base_target，删字段、改坐标、半径、来源或修订均不能覆盖已受理目标。B收到同请求重复task_start时，除原请求hash和task_id之外还比较持久目标，防止线协议独立字段绕过请求hash。

A重启后尚未连接B时，幂等查找使用持久bound_instance恢复请求作用域；因此重复请求仍能返回原任务与目标。新的副作用继续要求新鲜状态、明确AUTO及有效租约。读取原任务不授予AUTO，重试不会重新解析基地或重新派发。

旧轮证据和产物收据保持历史快照。当前MC工程尚未形成可安装发布版；本轮新增此前未声明的return_base候选能力，桥/执行器接口必须成对重建，不声称与旧候选二进制混用兼容。正式发布版本与迁移仍在D01统一完成。

## 5. 已受理但未启动任务的接管收尾

任务持久接受、running持久提交与实际port.start之间存在排队窗口。此时端口可能尚未登记完成回调；仅调用port.cancel不能保证原任务形成终态。本轮串行检查复现了running后接管被误记为GAME_MODE_BLOCKED的具体竞态。

[BridgeCore](../../../game-adapters/minecraft/fabric/src/main/java/dev/aitalkstreamer/mc/core/BridgeCore.java)现在先标记原任务撤权，使用停止时的epoch清理原输入，确认清理后再兜底提交该任务的cancelled/unknown。旧排队执行遇到已撤权epoch时不再抢先提交failed。端口回调与兜底收尾都受同一任务对象约束，迟到完成不能覆盖新任务，旧epoch的清理也不能释放新授权的输入。

另在journal.accept结束、task变为可见后立刻复核epoch：若接管发生于落盘期间且当时停止处理器尚看不到该任务，重新安排原任务收尾，不把已落盘任务留在accepted。该落盘窗口做了代码路径核对，未宣称完成真实磁盘故障注入验收。

两项新增Java↔Node检查用测试夹具显式保留排队动作，并确认B的持久接受或running后再触发模拟接管，最后释放旧动作；不依赖固定延时猜测执行窗口，也不放宽生产租约和期限。这些检查仍不是物理键鼠接管。中途一次未建立B受理屏障的失败及先前间歇问题原报告继续保留；修复这一具体竞态不能证明015轮全部GAME_MODE_BLOCKED、连接新鲜度、弹窗等待或高I/O/ACK问题均已解决。
