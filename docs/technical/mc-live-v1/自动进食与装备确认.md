# 自动进食与装备确认

044将上游FoodChain的异步装备、长按使用改为原公开任务拥有的ControlledEatingTask。它与内部补给、烟熏烹饪、紧急防御共用原玩家和控制许可；不新增公开技能，不把吃一口当作公开任务成功。当前只完成代码和本地原生/协议核对，真实MC验收仍为0/68。

## 1. 原任务与选食

实际FoodChain选择进食子任务，正常优先级60，高于普通任务50和补给/烹饪55；原紧急避险判断继续先执行。烹饪未完成清理时不能启动进食，进食未完成恢复时不能登记补给、采食或原任务正常结束。

只从玩家36格主库存选择实际食物堆栈，读取当前FOOD组件的营养、时长和效果；继续排除有害/不确定食物、紫颂果、迷之炖菜效果和受保护材料。真正发出使用前再次检查已装备的实际堆栈和保护状态。这里不以Item默认食物属性替代组件事实。

当前效果模型适用锁定1.21.1中经过读取的Item、AliasedBlockItem和HoneyBottleItem确切类。未知模组的finishUsing覆盖不自动套用原版模型；蜂蜜瓶额外返还玻璃瓶，且自定义usingConvertsTo不与蜂蜜特殊路径混用。其他特殊食品和全部模组支持仍须逐项接入。

## 2. 一口进食事务

```mermaid
flowchart LR
  A[锁定实际食物与原装备] --> B[交换至快捷栏并等完整库存确认]
  B --> C[原许可内只发一次主手使用]
  C --> D[等待结束或被危险中断]
  D --> E[服务器确认零份或一份消耗]
  E --> F[一份消耗还需饥饿值更新]
  F --> G[交换恢复并确认库存]
  E --> G
  G --> H[恢复原选中栏并继续原目标]
```

- 玩家handler固定46槽，包含装备、副手、合成区和光标。开始和每次动作检查原世界、玩家、连接、屏幕、线程、存活、焦点与非创造模式；合成区和光标必须为空。
- 主库存食物使用原GUI仲裁入口SWAP到已记录快捷栏。已经在快捷栏的食物也请求一次无副作用的完整状态同步。只在完整服务器库存匹配后使用，客户端预测不能确认装备。
- 通过原输入账本持有使用键，经SurvivalActions发一次主手interactItem，避免对准箱子时误开容器或意外使用副手。MC原生重复使用入口对这次事务禁用；暂停后允许紧急用物路径继续。
- 动画结束或中断后，先发送本任务拥有的原生停止使用请求，再在空合成结果槽执行一次受控无副作用点击，请求完整服务器同步。只接受两种精确状态：没有消费，或消费一份且返还物正确。数量、组件、光标或任何其他槽变化都不构成本次完成。
- 消费一份还需要使用请求之后收到的原生饥饿值更新，至少达到本次初始值加营养、上限20。更新先于库存确认到达也能配对；只有动画结束、客户端营养预测、单槽包或原有饥饿值均不足以完成。
- 原库存交换须再次得到完整服务器确认，才能恢复原选中快捷栏并释放子任务。这里的服务器确认指库存交换；原版没有独立的选中栏位确认回执，实际选中栏位/网络时序仍须实机检查。

完整库存请求使用已有点击revision钩子，至多一个待确认操作，检查15位revision前进和回绕。接收到的完整库存包由InventorySyncMixin应用后，经McBridgeClient、MinecraftPort和原执行器进入子任务；饥饿值经ItemUseSyncMixin沿同一路径记录。包回调只写事实，不获得游戏动作权限。

原版协议没有任务nonce，复用玩家handler和sync ID后的迟到包关联仍是未完成项；本地检查不声明解决这一限制。

## 3. 返还物与空间

FoodInventory按实际组件令牌计算一份消耗。食物最后一份直接在手中变成碗/瓶；仍有余量时，按锁定原版顺序合并：选中槽、副手、玩家主库存，再寻找主库存首个空位。快捷栏的映射次序和背包handler槽位次序不同，计算使用实际PlayerInventory顺序。

不同组件不合并，保留其余所有槽位。开始前预检返还空间；如果堆叠食物的碗/瓶无处容纳，就拒绝这次使用，不丢弃物品腾空间。原版蜂蜜瓶有无空间时丢弃玻璃瓶的路径，当前事务不会进入该路径。带复杂额外容器、特殊剩余物和未知服务端插件行为继续待完成。

## 4. 中断、撤权与期限

| 约束 | 当前行为 |
|---|---|
| 单口总期限 | 10000毫秒，包含装备、使用、确认和恢复 |
| 同次补满总期限 | 120000毫秒，重选和中断不重置 |
| 同次尝试数 | 最多20次，服务器确认无消费仍计入 |
| 每次库存确认 | 1500毫秒，不自动重发 |
| 新补满会话 | 只有本次确认消费且服务器饥饿值为20后才可重新计时 |

紧急链停止这口食物的使用，保存原阶段和期限。客户端动画结束也不省略停止请求，避免服务器在零消费读取之后继续完成旧进食。其他紧急物品仍在使用时等待其结束，不停止它；原期限继续计时。若服务器确认零消费，可恢复后结束该次尝试；确认一份消费则核对饥饿值并恢复。结果不明不直接重放，超时按原可靠任务结果失败。装备后尚未发出使用就中断，也必须确认并恢复库存。

人工撤权或原任务关闭后的清理只忘记绑定和关闭本地交换记录，不发送移动库存、关闭GUI、停止新操作员物品使用或重试包。输入仍由原所有者账本释放；不是服务器端回滚保证。危险期间若其他物品已开始使用，不以旧食物名义停止它。

GAME_EATING_SERVER_TIMEOUT、GAME_EATING_SERVER_DIVERGED、GAME_EATING_CONTEXT_CHANGED、GAME_EATING_LIMIT保留为内部具体原因；库存交换与预检也保留原细分拒绝原因。完整操作员接管、服务器限制、延时及低TPS效果仍须联验。

## 5. 检查与交付边界

本轮的验证结果以[044证据](../../evidence/mc-runtime-round-044.json)和[实现进度](实现进度.md)登记为准。新增检查覆盖精确返还物、容量和组件、中断后零/一消耗、原预算不重置、次数上限、饥饿值与库存双确认，以及实际编译FoodChain/驱动/桥/Minecraft类的调用路径。

这不等于真实游戏、Mixin加载、装备/连续进食的服务端效果或物理接管已经验收。完整武器/盾牌/投射物、所有容器与加工链、材料预留、真实服务器包时序、整场MC互动直播和D01–D15继续待完成。无条件preLaunch拒绝、完整生存能力关闭、冻结横屏设计及100条新人物素材要求保留。
