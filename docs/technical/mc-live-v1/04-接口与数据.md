## 1. HTTP约定

游戏路由前缀`/api/dsh/game`，挂在现有DSH宿主，经8010/8020同源代理。保持现有免登录应用模式；状态修订、epoch和租约用于并发与生命周期一致性，不作为新增用户鉴权。

JSON UTF-8、Cache-Control:no-store、普通请求≤128KiB；整数要求安全范围。写操作含request_id，配置采用expected_revision。枚举/未知字段/超限参数拒绝，不静默纠正为另一个游戏动作。

查询kind为recipe、check_action、observation、task_ledger。库存和近期事件分别从state及SSE/事件缓存取得，不对外开放SQL或任意查询代码。observation仍受视觉开关/能力约束。task_ledger须B声明对应能力、当前非AUTO且输入已释放，params.task_ids一次恰好一个A端已知任务；在既有128KiB帧上限内核对，不向B发送新动作。

BaseSelectRequest包含request_id、当前bridge_boot_id/world_session_id、expected_revision与expected_world_revision。必须是当前新鲜世界，非AUTO、输入已释放、无有效租约/活动任务，基地未归档；世界与基地版本同时匹配。幂等请求返回原World；同key不同body冲突。该操作只改账本，不启动回基地任务、不切换存档、不取得控制权。GET /tasks的world_id为空、格式错误或未登记世界时明确拒绝，不能静默返回另一世界任务。完整历史浏览和操作边界见[09章](09-全端实现蓝图.md)。

Task.recovery是A端核对元数据，具有独立revision，不是B端任务version。断线、换世界或A重启时保留最后确认的任务状态和版本，标记required；不能自行增加版本并伪造B的failed。B账本结果的外层绑定当前安装及世界会话，内层保留原任务boot、世界、request、epoch和goal，逐项核对后才采用遗漏的版本。终态核对成功为verified，仍运行则waiting_terminal；missing/conflict继续阻止AUTO。自动只读核对间隔至少2秒，每次宿主恢复中每任务自动最多3次；人工可请求重新查询。人工未知结果处置存入独立Task.disposition，只有新鲜停控、B无活动任务、双版本及观测上下文一致时允许；不改原任务状态/效果/证据，也不授予AUTO。旧任务重新报告为活动时重新拦截并请求PAUSED，详见[会话与复核](世界会话与后台复核.md)。

GameState.world_ledger供现有DSH只读工具及规划上下文使用，包含当前世界、活动基地、最近检查点摘要和未解决的任务核对记录。历史检查点不能当作当前库存。基地来源operator_observed仅证明操作者登记时的实际位置，不证明房屋、床或箱子已建成。检查点保存观测和引用，不是Minecraft存档备份、传送或自动续跑指令。

查询请求必须携带当前bridge_boot_id和world_session_id，params随kind校验；结果绑定原世界/帧，换世界后不得投影为当前结果。Operation.result按kind处理：control包含mode/epoch/inputs_released/automation_ready；cancel包含task_id及终态；query包含kind/world_session/依据序号或frame_id及结果；panic包含game和room各自的确认/错误。只有全部必要分项确认才将panic标succeeded。Schema仅约束该结果为对象，以上语义由实现按类型验证。

建议创建来自已过滤平台事件的内部归并，不开放任意文本直接执行游戏的入口。decision.action为accept/reject/cancel；accept仅采纳候选，真正任务转换须再次核对AUTO/世界/能力/前置条件，成功后置converted并关联task_id。proposal过期或换世界不得自动执行。

具体格式、容量、来源复核和故障语义见[互动闭环](观众建议投票与任务闭环.md)。TaskCreate可附suggestion_ref（suggestion_id/expected_revision），其关联与任务幂等记录同事务提交，再发给B。dispatch的Operation.kind为audience；成功表示本地受理任务，失败但已有task_id时保留dispatch_unknown与真实未知效果。GameState.audience和GET /audience投影实际任务、独立核对记录及证据；speech_status读取对应任务回应候选，无候选才为not_scheduled。附narration_id、speech_request_id、speech_reason及speech_completion_event_seq；answered必须有正式完成证明，不根据任务终态或生成成功推定。以上对象使用既有SQLite schema3的objects集合。

投票options具有唯一option_id和固定goal，计票只认稳定user_key与去重平台事件；每人一票。房间绑定当前实际平台会话，不允许请求任意房间计票。vote.revision用于状态并发，tally_version独立随计数递增；选项创建后不可修改。关闭冻结计数，平票的winning_option_id为空，只有后台以新revision提交明确selected_option_id或取消才能结束歧义；选择必须属于最高票的平票选项，无人投票时同样明确记为导播选择。tied保留是否原始平票，取消时清空结果。胜出目标仍经建议/任务链核验，不绕过控制授权；记录suggestion_id/task_id，无法执行则保留结果和原因。建议、投票写操作同样使用request_id幂等及expected_revision；创建无旧revision。冲突返回GAME_VOTE_CONFLICT/GAME_SUGGESTION_CONFLICT，已活动投票冲突返回GAME_VOTE_ACTIVE。

幂等任务重试返回同一task_id，不同body返回`GAME_IDEMPOTENCY_CONFLICT`。control、cancel、query和panic的request_id亦在各自操作域去重；同key不同参数也冲突。POST超时后查原操作或重试同key，不能换key盲目提交。

观察query先由A登记operation并发到B；B在游戏渲染线程取得原始帧，再在工作线程编码JPEG，通过frames上传。上传头为X-MC-Operation-Id、X-MC-Bridge-Boot-Id、X-MC-World-Session-Id、X-MC-Seq、X-MC-Captured-At、X-MC-Width、X-MC-Height。A核对该操作仍待处理、boot/世界/观测匹配后接收，不能用任意frame_id建立无关联截图。

图片最多4MiB、1920×1080，实际解码尺寸与声明一致，处理时再次限制解码像素；只保留最多2帧/8MiB，默认30秒过期，Content-Type:image/jpeg、no-store。该路由不走128KiB JSON解析器；A8010、3092与B8020均已有独立的有界读取/流式转发入口，并检查声明长度和分块累计长度。相同frame_id/内容及元数据可返回原引用，不同内容冲突；图片本身不进入普通SSE或长期记忆。Java上传显式HTTP/1.1，避免被现有WS升级入口误判。帧时效、实际JPEG解码、本地运行锁与取消边界见[原始帧与视觉适配](原始帧与视觉适配.md)。

023轮在既有配置操作中增加`patch.narration`，保持expected_revision/CAS及45项HTTP总数。OpenAPI版本1.7.0，schema新增NarrationSchedulerConfig和NarrationSchedulerStatus；旧GameConfig可缺少narration并补默认值。GET narration的新字段及配置范围详见[调度专项](回应调度与严重事件打断.md)。

## 4. SSE与后台同步

游戏SSE使用独立view_revision（安全整数）作为event id。新连接或重连总是先完整snapshot，不回放历史礼物/口播；后续状态只作为投影。snapshot含GameState、世界列表、带核对元数据的任务、操作、当前建议和投票摘要；另有world/base/checkpoint事件。suggestion/vote事件携带各自revision，计票更新另带tally_version。客户端去重各对象ID；序号不连续时重取state及对应列表，不重算选票或重新派任务。

心跳15秒，单客户端缓冲初始256KiB，超过关闭慢客户端并让其重连取快照；最多24个客户端。后台可复用Room的连接管理风格，但不能将游戏高频tick塞进Room历史消息。

SSE断开时显示连接问题；后台模式控件不能仅依赖本地按钮状态。游戏快照年龄由服务端计算并返回，浏览器基于收到快照后的本地经过时间继续增长，不拿浏览器墙钟推断跨机时间。

## 5. 公共错误

游戏错误响应为`{error,request_id,retryable,details?}`，details只含可公开字段。所有POST不自动无界重试。

| HTTP | code | 客户端处理 |
|---|---|---|
| 400 | GAME_REQUEST_INVALID / GAME_UNKNOWN_FIELD | 修正参数，不重试原请求 |
| 404 | GAME_TASK_NOT_FOUND / GAME_OPERATION_NOT_FOUND | 重新取列表或明确显示不存在 |
| 409 | GAME_CONFIG_CONFLICT | 获取最新配置，保留人工输入再提交 |
| 409 | GAME_MODE_BLOCKED / GAME_CONTROL_CONFLICT | 读取实际模式/epoch，不自动进入AUTO |
| 409 | GAME_WORLD_CHANGED / GAME_BOOT_CHANGED | 丢弃旧上下文，重新获取快照 |
| 409 | GAME_IDEMPOTENCY_CONFLICT / GAME_TASK_BUSY | 查原任务，禁止重复副作用 |
| 409 | GAME_PRECONDITION_FAILED | 显示实际缺少条件，交给重规划 |
| 413 | GAME_BODY_TOO_LARGE | 降低大小；图片不走普通JSON |
| 429 | GAME_QUEUE_FULL | 合并/舍弃候选，有限退避 |
| 503 | GAME_DISABLED / GAME_DISCONNECTED / GAME_STATE_STALE | 不启动新动作，人工接管仍可用 |
| 503 | GAME_CAPABILITY_UNAVAILABLE | 禁用相应功能，不静默假装支持 |
| 504 | GAME_OPERATION_TIMEOUT | 查操作与游戏状态，不能假定命令未执行 |

传输断开或504不证明无副作用。A必须先按task_id/request_id查询B账本；若不能确定，则标记unknown effect并停止重发。

## 6. 配置设计

GameConfig独立持久化，默认enabled=false、planner.enabled=false、vision.enabled=false；重启实际模式固定PAUSED，不从上次AUTO自动恢复。

| 组 | 字段与初始值 | 范围/语义 |
|---|---|---|
| 顶层 | schema_version=1、enabled=false | enabled只启用服务，不授予控制权 |
| planner | enabled=false、min_interval_ms=3000、max_call_ms=30000、candidate_limit=16 | 最小间隔1000–60000；超时1000–60000；候选1–32 |
| control | state_stale_ms=2000、heartbeat_ms=1000、lease_ttl_ms=3000 | 过期500–5000；心跳250–2000；租约1000–10000，且租约≥3×心跳 |
| control | accept_within_ms=1500、max_task_duration_ms=120000、enabled_skills=[] | 接收窗250–2000且不大于状态过期阈值；任务1000–600000；技能取已验收交集 |
| programme | layout_id=mc-landscape-v1、avatar_variant=circle、comment_mode=feed、scene=play | 圆形/横窗，feed/fly，play/interact/break/recover；显示配置不改变控制权 |
| vision | enabled=false、max_concurrency=1、min_interval_ms=1000、timeout_ms=8000 | 并发固定1；间隔1000–60000；超时1000–30000 |

改变控制时限/技能白名单必须先停控，再保存并应用；正在执行时返回GAME_CONTROL_CONFLICT，不边执行边缩短租约。显示配置可以热更新。受控依赖、模型地址、凭证、运行路径与世界登记由私有运行锁/本地设置管理，不混入可导出的公共配置。

MC使用权威布局的四条留言；现有竖屏overlay.max_comments默认3不会覆盖MC四条定稿。MC后台应明确标注通用旧设置的适用范围，不能暗中把通用上限5应用到MC。

## 7. SQLite与持久化

新增A端库位于当前设备已核验state root下`game/game.sqlite3`；B端控制账本位于该安装独立`receiver-b/state/mc-control.sqlite3`（同机候选使用独立游戏控制子目录）。目录在正式运行锁中解析，不在仓库写死跨机绝对路径。

以下为完整目标的逻辑结构，并非所有保留/恢复功能均已实现。当前A库schema为4：schema2的world_registry、world_bases、world_checkpoints、task_recovery，schema3的world_sessions、world_goals、world_goal_tasks、task_dispositions，以及schema4的bridge_history/history_partial；`objects`仍保存B任务权威投影和独立导入进度。完整历史与实时事实、会话/目标/人工处置分别维护；保留预算与联合运行恢复仍待落实，见[实际模块说明](../../../backend/game/README.md)。

## 8. 保留、迁移与备份

初始保留预算：原始关键事件按7天/50000条较先到达者清理，近期限额外保留当前未结束任务依赖；任务和转移保留30天/20000任务；基地、世界目标和有效检查点保留到明确归档。时间指标日志按100MiB×5滚动。清理先形成必要摘要并保证引用可解释，不删除当前恢复所需证据。

图像默认仅短时内存，磁盘诊断由操作者显式开启并设数量/时限。公开证据脱敏，不含Cookie、签名URL、私人聊天或活动数据库。

选票身份映射仅保留计数去重所需，投票关闭24小时后可去身份化，只留匿名计数和结果；观众删除请求提前清理相应个人关联。投票/建议不能成为绕过Humanity删除的第二份个人关系库。

迁移先一致备份并记录schema版本，使用事务创建表/索引；失败回滚、保持游戏PAUSED。旧二进制遇到新数据库主版本拒绝写入，不通过切换Git分支假装回滚数据库。恢复使用SQLite备份接口或停写一致快照，不单独复制仍活动的主文件。

当前A端v1→v2→v3各次已有数据库迁移均先用SQLite VACUUM INTO生成包含已提交WAL的一致快照，再事务建表；备份位于数据库旁backups目录。v2登记仅导入其最后已知会话并标记legacy_registry，不伪造boot/序号/连接次数。更高schema版本在认领写入者前拒绝。迁移备份已有CPU检查，完整运行备份、保留清理及恢复演练仍需另行完成。

B端另有原生SQLite backup/restore核心，备份包括已提交WAL、哈希收据与最多8份的拒绝新增边界；恢复只在独占账本关闭后对同安装执行，并先保存恢复前快照。B当前任务硬限20000、全部可靠历史硬限50000、活跃未确认窗口256；触顶保留证据并停控，不自动删除。上述硬限不等于已完成7天/30天保留清理。跨库、MC世界文件、记忆删除、后台维护与次日实机演练仍为必需工作。
