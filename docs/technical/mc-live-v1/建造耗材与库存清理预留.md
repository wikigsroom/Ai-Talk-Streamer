# 建造耗材与库存清理预留

055补入[替代目标与共享库存条件](替代目标与共享库存预留.md)，本页单物品规则扩展到候选集合；相同库存可覆盖多个绝对目标，消费仍须同时遵守全部上限。下文054计数保留为历史。

054将既有材料容量用于普通建造方块、临时垫脚方块和GUI垃圾丢弃。目标是让资源采集树在准备炉具、搭路和整理背包时保留已有任务成品，避免“合成入口保留了，另一个消费者又用掉”的问题。完整全局材料图、所有物品用途与真实服务器效果仍未闭合。

## 1. 选择与实际操作采用同一材料约束

| 原生入口 | 现行规则 |
|---|---|
| StorageHelper.getNumberOfThrowawayBlocks | 只计普通、未保护且符合原重要物品规则的可消耗方块；多个候选共同分配预留，不能逐槽重复计数 |
| StorageHelper.getSlotWithThrowawayBlock | 在主背包或指定快捷栏内找实际可消耗的一份方块，跳过已被预留的堆栈 |
| StorageHelper.getBuildingMaterialCount | 延续稳定建材排除沙、沙砾的规则，数量来自共同容量 |
| PlaceBlockTask.getMaterialCount | 合并明确结构方块与允许的替代垫脚方块，再按共同容量计数，重复候选不重复计算 |
| StorageHelper.getGarbageSlot | 保留原有垃圾、较差工具、未使用物品三条排序路径；候选必须能够整组移除，不能因只剩部分可用就把整组丢掉 |
| SurvivalGui.block / beforeUse | 直接交互及原生合成使用键在放置前复查实际手持材料；正常打开已支持的工作台/炉具继续走原界面归属路径 |
| SurvivalGui.slot | 发出实际GUI丢弃点击前，再按当前槽位或光标、单份或整组数量检查预留 |

ControlledMaterialUse只负责筛选、计数及检查，不直接点击、不移动库存，也不创建新根任务、控制器或授权。全部计算仍归属ResourceMaterials的原会话、世界、玩家和连接，随原根撤权清理。

## 2. 可移除数量与光标

ResourceMaterialsPlan.removable将现有成品保留和“从指定主背包槽移除N份”共同交给MaterialAllocation。移动保留额度可以换到同类堆栈，但消费只能使用指定槽；没有任何足够容量时返回不可用。

光标和副手位于36格主背包之外。若只在主背包预留，物品从背包拿到光标后可能错误地显示成“不再需要保留”。externalUsable使用同类主背包数量、候选外部堆栈数量及原目标计算外部可消费上限，不因为拿到光标而降低目标。

| 库存例子 | 允许的结果 |
|---|---|
| 主背包5份木材，任务保留2份 | 可用于逐份建造的数量为3；整组5份不能当垃圾丢弃 |
| 5份木材全部拿到光标，主背包为空，保留2份 | 外部可用量仍是3；整组丢弃5份被拒绝 |
| 光标剩2份木材，主背包为空，保留2份 | 不允许继续丢弃 |
| 主背包另有2份同类木材覆盖保留，候选槽有3份 | 允许移除候选槽整组3份 |
| 目标5份而当前只有2份 | 当前2份都保留，不将尚未满足目标视为可随意消耗 |

垃圾筛选仅接受能映射到当前实际玩家主背包的槽，排除光标、护甲、副手和外部容器别名。实际GUI丢弃检查额外处理光标、非主背包槽及单份/整组按钮，使用其当前候选数量。

这里检查的是当前原生客户端库存事实与原根预留；它没有给通用GUI点击新增完整服务器事务。服务器迟到包、预测与真实状态差异、所有容器及全部原始物理丢弃入口仍须实机审核，不能把这层检查当成全量操作覆盖证明。

## 3. 方块与保护规则

临时方块选择保留ItemHelper原有重要物品和保护判断，并额外要求普通组件。明确结构方块按该任务允许的方块集合计数；实际手持放置仍检查普通组件、保护状态和可消费数量。主手按当前选中主背包槽核对，副手按外部候选数量核对。

合成使用键可能尝试两只手，预检会检查可能参与的两只手。若其中有不能消耗的方块，操作会停止；不会为了放置而自动清空操作员的手或放宽预留。已支持且未蹲下打开的工作台、普通熔炉、高炉和烟熏炉属于不消耗手持物品的既有界面路径。

本轮不声称覆盖任意模组覆写、多份消耗、自定义物品用途、所有交互方块、工具耐久消耗、交易、容器转移或全部直接丢弃方法。完整范围继续由[全部待办](实现进度.md)约束。

## 4. 失败反馈与不重放

固定原因新增GAME_RESOURCE_MATERIAL_RESERVED，对应“物品正由当前任务保留”。它表示本次放置或GUI丢弃会侵占原任务保留量；组件或保护规则不允许的方块沿用材料不可用原因，不混称为库存预留。

Java固定原因、中文后台和主播事实采用同一个原因编号。反馈保留原任务、原始原因、已有部分效果及证据，不将早先效果撤销、不宣布成功、不重新派发旧任务。真实模型与DSH全节目联调仍待完成。
