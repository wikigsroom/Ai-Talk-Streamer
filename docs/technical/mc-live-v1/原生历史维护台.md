# 原生历史维护台

适用`mc`分支、038。同一完整版本内的D07/D08实现，与[完整总纲](13-完整方案实施总纲.md)、[A/B协调](A-B历史维护协调.md)及[机器状态](implementation-status.json)共同阅读。独立维护台已接固定离线协调操作；完整统一停启、长期归档、全端备份恢复及真实MC联合验收继续为必须项。

## 1. 进程和访问路径

维护时A业务服务和MC必须停止，所以维护页面由独立原生Python进程提供。它不成为GameStore、DSH或Humanity写入者，不加载模型、不启动游戏、不取得自动输入许可。A应用的`/mc-maintenance`按[公共监听配置](../../../configs/mc-maintenance-console.json)重定向到独立页面，游戏后台侧栏提供入口；进入后A退出不影响维护台继续查询和执行。

默认监听`127.0.0.1:3093`，直接访问`http://127.0.0.1:3093/mc-maintenance`。配置允许明确选择`0.0.0.0`及1024–65535端口；页面和接口不新增应用登录或token。原有8010/3092/8020及设备profile保持其职责。完整应用的端口表、统一安装与启动器仍须纳入D01。

从实际安装根运行：

```powershell
python scripts/mc_maintenance.py serve --journal "C:\实际安装\config\ai-talk-streamer-bridge"
```

与既有离线命令共用`configs/mc-maintenance.private.json`，固定实际JDK21/维护JAR及依赖hash；示例全零摘要不能运行。A数据库仅从当前3080应用profile推导。启动核对真实源码来源、profile、A/B路径和原生文件；每项新作业再次核对来源及运行锁，文件变化后拒绝派发。维护台本身启动成功不等于A已停止、B可独占或某份计划仍可执行。

## 2. 固定HTTP接口

所有字段以[Schema](contracts/game.schema.json)的`Maintenance*`定义和[OpenAPI](contracts/openapi.json)1.13.0为准。以下接口由独立进程提供，不能误发到DSH游戏桥。

| 方法与路径 | 作用与完成语义 |
|---|---|
| GET `/api/mc-maintenance/state` | 当前连接、容量、停止/存储故障和统一生命周期尚未接通的实际状态 |
| GET `/api/mc-maintenance/plans` | 有界计划列表、原文件摘要、来源匹配、保留理由、拟处理计数和过期时间；坏文件单列并保留 |
| POST `/api/mc-maintenance/jobs` | 持久受理dependencies/status/preview/apply/reconcile；新请求202，原请求同内容200 |
| GET `/api/mc-maintenance/jobs` | 每页20份，以through/before固定高水位向前查阅 |
| GET `/api/mc-maintenance/jobs/{job_id}` | 原作业状态和经过筛选的结果，查询不执行维护 |
| GET `/api/mc-maintenance/requests/{request_id}` | 页面失联后按原编号查找受理记录 |
| POST `/api/mc-maintenance/jobs/{job_id}/cancel` | 空对象请求，仅取消尚未运行的排队作业；运行中返回409 |
| POST `/api/mc-maintenance/stop` | 空对象请求，停止受理、完成当前作业、其余排队记录标中断；202不代表进程已经退出 |

POST只接受不超过4096字节的JSON，拒绝重复键、未知字段、路径覆盖、命令、任意环境/参数以及不完整计划名/hash。静态文件仅四个明确页面/样式/脚本，不能经HTTP读取配置或数据库。返回计数、时间、计划摘要和安全副本收据，不返回原任务正文、保护任务ID列表、私有渠道或本机数据库/原生运行绝对路径。请求和作业不依赖前端是否保持打开。

## 3. 持久作业和独占

作业账本位于A状态根的`game/maintenance/console/jobs.sqlite3`，与业务`game.sqlite3`分离。OS文件锁保证同一安装只能有一个维护台；所有作业由一个工作线程串行执行。SQLite受理记录先提交，执行前再持久记录running，随后才进入既有A围栏和B原生协调。

| 状态 | 实际含义 |
|---|---|
| accepted | 已持久排队，还未派发；可以取消 |
| running | 已开始该固定操作；apply从此保守显示unknown，等待实际提交查证 |
| succeeded | 此查询/协调作业已取得其结果；apply仍以当前B账本确认为依据 |
| failed | 固定操作没有正常完成；按outcome区分未派发与不确定 |
| interrupted | 上次运行或正常停止留下的中断记录，不自动重放 |
| cancelled | 排队时取消，未派发 |

请求编号在账本内唯一，同编号不同内容409，同内容只返回原作业，即使已结束或已中断也不再执行。重启时accepted标中断/未派发，running的apply标中断/unknown，其他已开始查询标不适用执行删除；绝不自动续跑旧队列。结束记录无法落盘时，停止工作线程并保留原running；下次启动仍保持不确定，不能凭HTTP或异常退出改成“没有执行”。

一份apply的unknown记录不会被后来的成功查证覆盖，reconcile另建作业并保存当前观察。“当前未找到”可能发生在旧B备份恢复后，不能证明历史上从未执行。已提交计划的新请求仍由协调器先查B，不增加安全副本或再次apply。

## 4. 导播完整操作

正常停播并释放输入，停止A和MC后打开或保留独立维护台。先检查维护条件或查看保留依据，再生成实际预览；核对“保留依据/拟处理内容”、原计划编号/hash及有效期，勾选核对后执行这份计划。确认窗绑定打开时的计划，即使后台随后出现另一份预览，也不改为执行别的计划。

执行沿用037的A完整快照、A/B保护关联、实际运行文件、计划过期、A一致安全副本、B一致副本及原子提交、独立result查证。页面刷新、关闭和失去POST响应后，用原请求编号查询；浏览器不自动重新POST。失联提示可以收起，原作业仍在账本内，开始另一操作前应核对列表。

过期计划仍可查证当前账本，不能从页面批准执行；服务端仍独立校验期限和所有依赖。排队可以取消，运行中只等待结果。停止维护台等待当前作业结束，未开始的队列保留中断记录；再次启动也不重放。随后恢复A和MC仍走既有来源/设备门禁和新的现场观察，不恢复旧AUTO。

页面沿用知夏导播台青灰色系，保留/处理并列展示；窄屏改为上下阅读，按键有明确焦点，记录使用文本节点呈现。页面没有音视频元素、不取得正式播放权；隐藏/离开时停止轮询并取消在途读取，恢复可见时重新查询。

## 5. 容量和证据边界

作业同时最多16份待完成，账本最多512份/16MiB，单份公开结果16KiB，接近容量拒绝新作业；既有编号仍可查询。每次变更有独立事件，账本不自动删记录、不自动VACUUM。预览16份、原生日志128份、维护尝试/查证各64次、安全副本及磁盘预算继续按A/B协调规范核验。达到上限后长期归档与管理员恢复流程仍属于D07/D08，不能以有限拒绝代替完整运维。
