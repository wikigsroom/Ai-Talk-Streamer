# 多人回应记忆与删除恢复

本专项落实[完整执行规划第17节](10-全量执行与资源计划.md)中的部分工程闭环，属于同一完整版本。026轮的范围是实际来源绑定、按来源召回/候选、共享上下文依赖和持久删除投影。本地SQLite、宿主工具回调、Room HTTP/SSE与协议夹具可以核对这些行为；真实DSH/Humanity、平台、MC、声音和一致备份联合验收仍未完成。完整证据以[实现进度](实现进度.md)为准。

## 1. 一次回答涉及谁

合并回答不把第一条弹幕的账号当成所有人的身份。调度器先从实际Platform事件及当前Room消息核对来源、正文、可见性和有效期，再将最多32条来源绑定到既有StateStore。同一请求的绑定、每条独立`input.accepted`和`audience.bound`在一个事务内完成；任何来源写入失败，事务回滚，未绑定的合并请求取消。

| 来源 | 个人记忆边界 | 公开回应 |
|---|---|---|
| blivedm/open_live采集、平台稳定账号已核对 | 按平台/房间/稳定账号的既有主体分区 | 可以共同回应；同名不代表同一账号 |
| 身份未知、只有显示名或中继自报身份 | 不建立个人分区，不召回或提议个人记忆 | 仍可作为当前公开事件 |
| 同一账号的多条有效来源 | 同一主体，保留各条原始事件引用 | 来源重试不重复登记个人输入 |
| 不同账号的合并来源 | 各自独立，禁止以合并锚点代替 | 只有一份正式口播及播放完成事实 |

个人源事件附平台事件hash、来源指纹和Room账号hash，不再复制原UID、昵称或密钥。正文存在既有可删除事件载荷中。`runtime_meta`的去重索引使同场候选重试能复用原输入；旧场、已删除或来源指纹变化均拒绝复用。MC标记请求缺少权威绑定时拒绝生成记忆上下文，不能退回旧的首位观众捷径。

## 2. 召回、模型工具与预算

共享上下文顶层使用公共记忆；`audience_memory.participants`按来源列出各账号已经确认的记忆和少量已确认历史。模型只能用当前绑定的`source_event_id`选择其中一个主体，不接受自行填写viewer_id、subject或partition。多人或含身份未知的请求不带选择器时只召回公共记忆；全部有效来源属于同一已识别账号时，可以省略选择器。

| 约束 | 当前实现 |
|---|---|
| 来源 | 最多32条，每条正文最多1500字符，绑定前校验唯一事件key |
| 记忆上下文 | 既有canonical上下文整体最多7800字符，包含来源分组与记忆；超限裁剪可选记忆/历史，不能扩充原预算 |
| 私人召回内容 | 多人共享500字符预算；私人历史共享1200字符预算，每人最多4条、每条最多200字符 |
| 游戏事实 | 另有既有16Ki字符来源快照预算；不把整个模型入参误称为7800字符 |
| 工具候选 | 由选定的真实来源决定主体；仍经过现有校验与候选流程，不直接写Humanity |
| 播放事实 | 共享回答只登记实际完成一次；未播完、取消或迟到生成不成为已播经历 |

每次工具调用及生成使用前重新核对权威来源。隐藏、屏蔽、撤回、删除或正文变化使来源不再匹配时，拒绝旧记忆工具和迟到媒体。MC合成输入本身不作为个人偏好证据；各账号真实说过的话保留独立来源，后续提取不串到别人的分区。

上下文来源清单不仅记录本轮输入，还记录实际注入的已确认记忆来源和私人历史。这样，删除较早的个人记忆也能使后来引用它的多人回答上下文失效。其他账号的独立输入与独立记忆继续保留；受污染的共享派生文本整体清除，不做字符串替换。

## 3. 删除怎样贯通各端

删除沿用既有管理入口和唯一DSH/Humanity写入者。按主体删除包含该主体的历史来源；选定memory_id删除按其实际来源定位，不因此禁止该账号后来提交的新消息。普通非MC平台请求也通过持久request关联找到原平台/Room来源。

| 存储/消费者 | 当前删除动作 |
|---|---|
| canonical StateStore | 清除实际源载荷及受影响的共享请求/派生载荷、记忆值/修订/引用、待审候选、摘要、上下文和相关维护结果；取消受影响排队请求 |
| 删除账本 | 保存原操作及代次、来源引用和最小投影计划；正文、原UID和昵称不写进投影计划 |
| Platform | 写每事件墓碑及按主体删除的截止围栏；清除正文、昵称、UID、详情和会话引用；实际完成的历史状态可以保留 |
| Room | 删除原消息，清理其板卡引用/待播/字幕并广播新快照；它不是可用“恢复消息”重新显示的SC撤回 |
| GameStore | 撤回关联选票，删除来源支持记录及建议上的已删来源，推进修订并重核候选；保留真实任务及已发生效果关联 |
| DSH/Humanity | 取消在途生成、清理相关会话，并等待既有mirror outbox的REMOVE确认，不能以排入重试队列充当已删除 |

canonical事务先持久化`privacy_redaction_pending`及`privacy-projection:<operation_id>`。后续跨库投影可重复执行；同一operation_id、同一参数重试不会增加删除代次。跨库没有伪装成一个SQLite事务；中途故障保留待完成状态，后台轮询或同操作重试继续完成。

删除主体非空且最多300字符，先于任何取消或持久计划写入校验，避免保存无法重放的非法计划。最终Room通知成功之后才清除待完成标记；通知失败仍保留可供重启/重试的持久记录。

## 4. 部分失败时的可见行为

删除待完成时，Room状态/SSE将留言、板卡个人内容和字幕投影为空；平台状态不回传旧事件，采集提交和Room写操作返回503 `MEMORY_PRIVACY_PENDING`，规划与维护生成暂停。只读状态和事件订阅继续可用。已知来源会先删除，未确认完成的其他投影不能对外报告成功。

平台、Room、Game或Humanity不可用时保持待完成，故障恢复后按持久计划重放，完成后重新发布实际剩余消息。无法映射账号的历史Room行触发`MEMORY_PRIVACY_COVERAGE_INCOMPLETE`，不能根据相同昵称猜测归属、也不能声称完整删除。Humanity REMOVE未确认则为`MEMORY_PRIVACY_MIRROR_PENDING`。

这些状态表示删除恢复尚在进行；真实媒体取消回执、跨进程故障、长时资源和运维可诊断性仍需联合验收。

## 5. 启动、旧备份与重放

桥启动先加载原存储及删除记录，重放全部投影计划，再启动Room/采集定时器和HTTP就绪。GameStore延迟加载时，也先重放历史删除，再启动游戏管理器；这只加载账本和管理代码，不会因此启动Java、模型或AUTO。

Platform库版本从2兼容升级为3，增加`privacy_deletions`、`privacy_fences`。打开比3更高的版本立即拒绝，不能用旧代码覆盖版本。已有SC撤回墓碑保持其独立语义。

每事件隐私墓碑在原事件行清理后仍能阻止重放；按主体删除的截止围栏同时覆盖旧备份恢复的账号历史，截止之后的新消息可正常进入。旧Platform/Room/Game投影恢复后依据canonical计划重新删去原来源，而不是将旧缓存当作新的事实。

本地检查覆盖旧行恢复、重构管理器继续未完成操作、再次插入旧选票和正常新消息。它们不等同于已完成A/B/MC一致备份包的恢复激活。B→A完整历史、7/30天保留与清理、历史归属补齐、删除计划容量/保留、真实Humanity会话及跨次日联合恢复仍列D07/D14/D15。

## 6. 完整系统的关闭条件

本专项本地通过后，仍须在同一最终候选完成H02/H06/H07/H09/H12：不同账号/同名/匿名混合、真实工具召回与候选、现场声音取消、并发弹幕与维护、跨库断电/重试、旧备份与次日续接，并证明其他观众的独立事实保留。全部15域、68项真实验收及完整人物素材按[全量执行总表](全量交付执行总表.md)共同关闭。
