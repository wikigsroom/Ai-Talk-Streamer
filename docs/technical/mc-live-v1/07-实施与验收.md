## 2. 验收环境与证据

每次运行登记源码commit、分支mc、设备/应用profile、CPU/GPU/RAM、Java/MC/Mod/执行档、世界种子/难度/装备、媒体profile、官方客户端版本、网络与测试模式。

证据目录拟为`outputs/mc-validation/<run_id>/`，包含manifest、事件/任务日志、前后状态、官方本地录像、音轨结果、截图、资源曲线及result.json。对外只发布脱敏副本，活动SQLite/私有配置不进Git。

result逐项记录pass/fail/not_run、实际样本数、门槛、观测、失败路径与证据位置。没有执行的项目标not_run，不填写推测成功率。GUI测试结束关闭所创建的页面、上下文和服务；正式客户端是否关闭按进程归属与使用状态判断。

## 4. 性能与质量门槛

下表均是待实测的候选验收目标，不是现有成绩。记录真实机器后可以用有依据的版本变更调整，但不能在测试失败后隐藏原门槛。

| 项目 | 候选目标/方法 |
|---|---|
| 本地接管 | 热键进入仲裁到合成输入释放目标≤250ms；报告分布与最大值，20次无残留 |
| 状态通道 | 应用状态P95≤500ms；以进程耗时/RTT与已声明校时误差报告 |
| 游戏呈现 | 初始1080p、60FPS上限；目标平均≥30FPS、1%低分位≥20FPS，保留帧时间 |
| 人物呈现 | 源25FPS；稳定段目标实际呈现≥22FPS，不能用canvas绘制计数冒充呈现 |
| 媒体完整性 | 完整4小时测试内检查有效人声连续、媒体包与解码；包含原60分钟稳定段，异常注入与稳定段分组，不隐藏失败片段 |
| 事实正确性 | 固定库存/配方/任务用例逐条核对；不允许“任务已受理”被播为“已完成” |
| 长期稳定 | 4小时完整负载与跨场/次日恢复纳入统一交付；随机世界普遍成功率需额外样本，不冒充已知 |
| 语音延迟 | 分别报告事件→候选→生成→首播→观众端，不承诺即时出声 |

资源记录不只取空闲截图：保存峰值、稳定段和突发段。单机与双机、标准Baritone与AltoClef、新旧人物素材分别成组，不混报结果。

## 5. 单一完整版本的完成定义

唯一发布完成条件：W00–W13对应全部必需产物齐备，V01–V44与C01–C24全部有通过证据，D01–D15全部满足，代码、Schema、素材、数据库与运行锁一致。模块完成仅更新内部工作状态，不另行标记用户交付版本。

视觉、普通生存执行、两套完整人物、平台/观众证据与恢复均必须完成；任何必需项failed或not_run均使整套保持未完成。运行时开关仍只开启通过的技能与媒体profile。

## 6. 开发检查与交付包

文档/契约检查相对链接、JSON与OpenAPI结构、本地引用、样例Schema验证和跨字段约束；不启动模型、游戏或浏览器。实现检查优先覆盖会导致真实副作用的围栏、幂等、过期和恢复。全端实现责任、运行参数和交接路径见[09章](09-全端实现蓝图.md)。

游戏实现交付必须包含源代码、锁定依赖、契约/迁移版本、配置说明、预检/启停、自动化用例、真实游戏证据、官方本地录像、失败样例、回滚步骤与未通过项。新人物交付另含源/索引/脸框/遮罩QA。

实际源码、模块检查和待完成项见[实现进度](实现进度.md)。Fabric桥和部分服务端已有实现；真实游戏、完整生存、新人物、完整媒体/视觉、平台及整体运行仍待实现或验收。规划修订和文档校验只更新设计依据，不改变68项真实验收状态。
