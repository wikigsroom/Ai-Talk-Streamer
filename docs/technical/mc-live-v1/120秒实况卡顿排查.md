# 第085轮：120秒实况卡顿排查

2026-11-03，mc分支。只读检查第084轮的原始官方录像、交付录像、人物计数、带时间日志和实际播放回执。所有视频探测与解码均在3080原生Windows执行；未重新启动游戏、模型或公开直播，未改变运行源码和参数。

## 结论

主要问题在人物媒体链路：说话时推理速度低于25帧目标，随后播放器欠载恢复采用4秒重缓冲，造成可见停顿和语音进度中断。人物25帧与成片30帧的节奏差异也会带来轻微不均匀。游戏采矿时直接转动视角会增加突兀感，但不能与真正的卡帧混为一谈。

本次没有保留逐时GPU占用、磁盘延迟及浏览器audio_underruns历史曲线，因此尚不能把供帧不足的全部责任分配到GPU、磁盘、CPU或回执写入中的某一项。原始录像已出现问题，导出不是主要来源；这也不能排除用户当前播放器另外存在性能影响。

## 已确认的证据

| 编号 | 核对项 | 实际结果与边界 |
|---|---|---|
| 1 | 原始与交付录像时间戳 | 各核对连续120秒、3600帧；帧时间间隔33.333毫秒，无超过50毫秒的时间戳断档。恒定时间戳不能证明每一帧都有新画面 |
| 2 | 人物说话推理日志 | 录像窗口内有9条带时间的actual avg infer fps，约19.81–22.68帧/秒，低于25帧目标 |
| 3 | 人物动作索引生产计数 | 本场128.004秒计数采样平均22.25帧/秒；约6秒的采样窗口最低14.45帧/秒。此计数是生产进度，不冒充游戏FPS或最终呈现FPS |
| 4 | 三次正式播放进度停顿 | 19.698→23.698秒：墙钟4.000秒，仅推进0.010625秒PCM；46.198→50.205秒：4.007秒，仅推进0.178625秒PCM；94.201→98.218秒：4.017秒，仅推进0.210625秒PCM |
| 5 | 人物区域实际连续画面 | 原片约53.7秒起有3.93秒近乎不变，115.7秒起约3.47秒。交付片也存在相应长静止区间；单靠区域静止不能排除素材本身静止，须结合生产与播放证据 |
| 6 | 播放器缓冲逻辑 | web/local-stream.js默认缓冲4秒；next落后音频时钟时，将播放位置重设为当前时钟＋4秒，人物画面亦按该时钟排程。正常MC节目连接没有传入更短buffer_ms |
| 7 | 媒体发送延迟 | 片内108.352秒处，单个已关联语音的媒体包处理耗时0.374秒，明显超过每帧40毫秒预算；日志没有把编码、数据库映射和调度分开计时，不能断言均由数据库造成 |
| 8 | 游戏运行边界 | maxFps=30，垂直同步开启，视距8、模拟距离6；状态序号约20.02Hz推进。状态消息频率不等于渲染FPS或服务器TPS。最新游戏日志的单次落后警告发生在片前，不将其冒充片内故障 |
| 9 | 镜头动作 | 导航每tick转向最多25度；采矿aim直接设置目标角度。后者缺少渐进转向，可造成镜头突然跳动，即使录像没有时间戳断档 |

播放回执反映实际消费者的播放进度，但仍不是独立麦克风录音或逐字听写。本场三次近4秒的进度停顿、供帧不足及4秒恢复逻辑互相支持“欠载后长重缓冲”判断；历史浏览器计数已随服务退出而失去，不伪造其数值。

## 修复顺序与验收方法

| 编号 | 要处理的问题 | 具体实施与验证要求 |
|---|---|---|
| 1 | 人物链路持续供帧不足 | 保持已批准FP16/batch4，记录推理、素材读取、贴回、编码和映射各阶段耗时；优化实际超预算阶段，使连续节目供帧稳定达到25帧并留余量 |
| 2 | 同机输出仍使用跨设备4秒恢复 | 为同机节目独立设置有界缓冲与恢复策略；防止轻微欠载就再次等待4秒。缩短缓冲不能替代供帧修复，必须同时核对连续PCM、口型和正式播放回执 |
| 3 | 媒体映射在逐包发送路径上等待 | 增加分阶段耗时，评估有界提前准备/批量持久化；仍须先持久化映射再允许播放，不丢样本、不绕过完成证明、不新增发声者 |
| 4 | 帧率节奏和游戏镜头 | 人物保持真实25帧并稳定呈现；固定30帧输出接受有规律的重复帧，不能以插帧掩盖欠载。为采矿等瞬时转向增加有界平滑，保留瞄准效果与控制权限 |
| 5 | 只有“30fps/3600帧”检查不足 | 补录原档真实连续节目，同时保留生产FPS、客户端呈现FPS、欠载次数、最大到包间隔、音频缓存、各阶段耗时与资源曲线；核对原片中的停顿和声音连续性 |

本轮是原因排查，未部署上述性能修改。此前331项业务检查不验证流畅度，不能替代本项复测。全部D01–D15、正式0/68和新人物0/100仍按[实现进度](实现进度.md)保留。
