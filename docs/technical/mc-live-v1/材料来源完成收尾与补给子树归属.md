## 1. 原问题与实际修改

资源任务包装层可能只按物品数量判断完成。材料数量已经增加时，内部确认合成或炉具事务仍可能在回收余料、等待服务器确认或关闭界面。旧路径计算也可能尚未退出。此前正常完成分支在外层立即登记进展并选择下一来源，未使用失败回溯的退出等待。

本轮修改实际的 `ControlledRecipeResourcesTask` 和 `ResourceBranchRecovery`，覆盖以下四条路径：

| 路径 | 当前行为 |
|---|---|
| 子任务正常完成 | 先确认相关事务和界面允许收尾，停止实际子树，重读库存后登记净增；本tick返回，进入等待 |
| 子任务完成但没有材料净增 | 完成相同收尾后保留原无进展记忆；旧工作退出前不选择另一来源 |
| 来源工厂返回null | 完成相同收尾后登记无进展，不再在同tick连续创建其他来源 |
| 固定规划失败 | 继续使用原十项原因白名单、原来源记忆及最近采集节点，进入相同等待状态 |

子任务报告完成、但实际事务或界面尚不能收尾时，继续运行原子树，让已接入事务完成原有确认和清理。不会把物品数量达标当作服务器事务完成，也不会创建替代任务绕过未完成的清理。

清理前后均核对原根授权和边界。正常路径在清理之后重新取得 `ResourceMaterials.stock()`，并以此登记完成；不会使用停止子树之前的旧库存。后续是否达到目标仍由原计划和真实库存重新判断。

## 2. 补给准备的归属

`ControlledFoodCookingTask` 的准备阶段需要先收集原料或燃料。准备对象此时仍为busy，但实际库存转换尚未开始。若只看这个全局busy标记，内部材料子任务就无法结束或回退。

新增 `ControlledFoodCookingTask.within(subtree)`，执行真实 `Task.thisOrChildSatisfies` 的对象身份检查：

| 实际关系 | 收尾限制 |
|---|---|
| 要停止的子树就是活跃食物准备对象 | 保留保护，不停止整段准备 |
| 子树包含活跃食物准备对象 | 保留保护，不撕掉准备上下文 |
| 材料子任务位于准备对象之下 | 准备对象不属于待停子树，允许材料节点独立收尾或回退 |
| 准备已完成、原根已失效或没有活跃准备 | 不以该准备对象阻挡另一子树；原权限检查仍独立生效 |

原 `retains` 行为继续保留，准备对象本身不因自己的存在而永远等待自身。确认合成、实际炉具转换、进食、装备和盾牌事务的保护未放开。光标、合成格、炉具三格、原GUI归属及炉具完整服务器空库存快照仍按原规则核对。

## 3. 停止前后两次计算隔离

收尾顺序为：

1. 核对原权限、实际子树、事务与GUI状态。
2. 作废旧计算代次，避免 `onStop` 同步触发路径回调时应用已排队的旧结果。
3. 停止实际子树；来源工厂没有创建子任务时省略此步。
4. 再作废计算代次，将旧子树清理期间提交的计算一并隔离。
5. 取消所属路径，清理原路径事件、按键队列、交互和允许关闭的空界面，再核对收尾条件。
6. 重读库存，登记原来源完成或失败；清除本节点旧分支引用并进入settling。
7. 等原 `SurvivalAsync` 的jobs及pending均为零，再重新规划材料。

当前代已经记录的真实计算异常仍终止原根，不能用第二次作废隐藏。两次隔离均不重置8个并发工作额度；仍在执行或尚未投递的旧工作继续计数。结果队列64项、原根256次来源选择、原授权、原截止和中断恢复规则不变。

这只覆盖已接入材料来源收尾的寻路计算及结果队列。其他任务的正常切换、通用订阅、线程、容器和网络迟到响应仍需完整审查，不能据此宣称所有副作用已经覆盖。
