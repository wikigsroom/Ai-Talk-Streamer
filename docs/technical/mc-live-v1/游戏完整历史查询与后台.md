# 游戏完整历史查询与后台

适用分支：`mc`。完整交付范围继续遵循[一次完整交付总计划](12-一次完整交付总计划.md)，本说明落实 D02、D07、D08 的历史接线。033、036为内部实现记录编号。B当前数据库schema3（035新增[保留与离线维护](B端历史保留与离线维护.md)及schema2迁移）；A游戏库仍为schema4。代码及本地检查与真实MC、Humanity和直播验收分别登记于[实现进度](实现进度.md)。036已接入B维护后的全部摘要、防重凭据及维护结果历史投影与后台；A自动维护协调继续待接通。

## 1. 查阅范围与权威

游戏端历史包含五个分别扫描的数据源。旧桥未声明维护历史能力时，继续扫描原有两个源：

| 数据源 | 包含内容 | 保留的原始身份 |
|---|---|---|
| `reliable` | 已 ACK、已归档、尚未确认的事件及任务递送记录 | 原 boot、world session、流、delivery sequence、记录时刻、ACK 时刻和归档原因 |
| `task_versions` | 每一个已持久化的任务版本，包括缺少对应递送行的旧迁移记录 | 原 task、version、boot、world session 和记录时刻 |
| `retention_summaries` | 全部保留汇总的当前内容版本，按日/世界/类型计数 | 原世界、UTC日和时间范围；没有原boot或递送ACK |
| `retired_tasks` | 全部任务防重最小凭据 | 原world/request/task、请求摘要、终态摘要和清理时间 |
| `retention_runs` | 全部维护执行结果 | 原run、计划摘要、计数和备份文件名；跨世界，不虚构世界会话 |

B 的 tasks、任务版本和递送账本保持权威。A 将查到的历史写入独立 `bridge_history`，仅供查阅；导入路径不更新实时 tasks、game_events、stream_receipts、恢复核对游标、口播或 Humanity。历史任务显示成功只说明原记录包含成功证据，不证明当前库存、当前世界状态或观众听见过这条反馈。保留汇总按内容SHA区分版本，同一汇总内容变化后另存历史版本；重复读取相同内容去重。不同版本的累计计数不能相加。防重摘要不是完整Task，不能成为当前任务恢复、执行成功、口播或记忆写入依据。旧备份恢复后，A已查阅的旧汇总仍作为历史留存，不宣称它仍存在于当前B账本。任务当前结果复核继续由原 `task_ledger` 闭环承担。

同一安装只绑定一个 game instance。历史记录允许原 boot、world session 不同于当前连接，载荷和元数据中的原身份仍须相符；传输信封和查询结果的外层身份必须属于当前连接。

## 2. 原生 B 查询与传输

[JournalHistory.java](../../../game-adapters/minecraft/fabric/src/main/java/dev/aitalkstreamer/mc/core/JournalHistory.java) 经 [LocalJournal.java](../../../game-adapters/minecraft/fabric/src/main/java/dev/aitalkstreamer/mc/core/LocalJournal.java) 的同步只读入口调用。表名只接受上述五项到固定表的映射，SQL 的值使用绑定参数。查询运行于桥 I/O 线程，不调度玩家输入或重新执行持久任务。

[BridgeCore.java](../../../game-adapters/minecraft/fabric/src/main/java/dev/aitalkstreamer/mc/core/BridgeCore.java) 在 hello 增加可选能力 `features.journal_history=true`。旧桥未声明该能力时，A拒绝历史导入。036新增可选`features.journal_maintenance_history=true`：导入在原两源之后读取保留汇总、防重凭据和维护结果。未声明新能力的旧桥仍完成原两源流程，不发送不支持的查询。

查询仍使用既有 `query/query_result`，kind 为 `journal_history`：

```json
{
  "source": "reliable",
  "after": 0,
  "offset": 0,
  "through": null,
  "limit": 20
}
```

首次查询为该数据源读取最大 rowid，作为固定 `through`。后续页必须携带同一上界；新增行留待下一次显式导入。`after` 是最后一个完整接收的行，`offset` 是下一行已接收的原始 UTF-8 字节数。完整一行后推进 after 并将 offset 归零；部分行保持 after 并推进 offset。每个源分别取得上界，不宣称各表属于同一时刻的联合数据库快照。

| 边界 | 值与行为 |
|---|---|
| 单页行数 | 1–20，部分行也占一项 |
| 单个原始条目 | 最大 131072 字节；超过上限明确拒绝 |
| 单块原始字节 | 最大 24576 字节 |
| 单页原始字节 | 最大 49152 字节 |
| 编码和校验 | 原始 JSON 的 UTF-8 字节 → Base64；完整条目核对 SHA256 后解码及结构校验 |
| 现有 WebSocket 上限 | 保持 131072 字节，不因历史查询放宽 |

条目 key 使用规范 JSON 数组的 SHA256：递送行由 `[原boot, 原world_session, 原stream, 原delivery_seq]` 生成，任务版本由 `[task_id, version]` 生成。传输 rowid 只用于扫描，不充当跨安装业务身份。每块携带原身份、载荷摘要/总字节、偏移和 final。不能用新 boot 将旧载荷伪装成实时消息。

维护记录使用独立`JournalMaintenancePayload`/`JournalMaintenanceChunk`，不冒充事件或Task。业务key由`[source, source_key, 原始载荷SHA256]`确定；`source_id`只用于本次分页，恢复后变化不产生重复业务记录。保留汇总的boot为空、防重记录保留原boot/world、维护运行的boot/world均为空；`sequence=0`表示没有递送序号，ACK/归档字段均为空。A逐项核对分组key、时间范围/UTC日、任务与摘要身份及日期、运行实例及实际时间。摘要记录的代数变化不会导致未变的汇总、防重和维护结果重复存储。

## 3. A 后台导入与原子写入

[history.mjs](../../../backend/game/history.mjs) 管理单个后台导入。导入将本次能力确定的`source_order`持久化，按reliable、task_versions和可用的三个维护源完整扫描，进度与每页落盘事务绑定。[manager.mjs](../../../backend/game/manager.mjs) 负责当前连接、操作超时及模式围栏。

```mermaid
flowchart LR
    B[B 只读历史查询] --> C[分块及固定扫描上界]
    C --> V[A 字节摘要与身份校验]
    V --> H[A 独立历史库]
    H --> U[后台摘要分页与原文]
```

启动须有新鲜观测、当前 boot/world context、桥能力、暂停或人工游玩模式、输入已释放且无活动任务。每次继续取页与接收结果时再次检查。查询必须属于当前导入；自由提交 `journal_history` 查询不能绕过后台任务管理。

断线、连接 generation/boot/world 改变、观测过期、游戏恢复操作、取消或超时会终止本次导入。明确恢复 AUTO 会先中止导入，不阻塞导播接管。页面关闭不终止服务端导入。服务重启将未完成导入标为中断并移除未完成的分块；完整条目保留，重新导入会去重，不自动继续旧查询。

每页先核对源、起点、上界、分块顺序、总字节、Base64 规范编码与原始载荷 SHA256，再验证事件或任务契约。页内任意冲突均回滚整个页，已提交的早先页保留。维护条目也分别校验专用载荷与实际来源；无效日期、身份错配及自洽传输摘要下的伪造分组都拒绝。任务原 instance/boot/world/version 与递送序号均须相符。

相同 key 的原始载荷摘要和固定身份不能变化。重复条目仅更新查询时刻与可补充的确认信息：已有非空 ACK/归档值不被空值覆盖；两个已知值冲突时保留先前值，并显示差异标记。传输用 source_id 变化不会改变业务 key。历史页操作结果只保存有界摘要，避免把分块载荷再次堆入操作日志。

## 4. A 数据库和容量

[store.mjs](../../../backend/game/store.mjs) 为已有 schema3 安装先执行一致 `VACUUM INTO` 备份，包含已提交 WAL，再在事务中创建 schema4；新空库无需生成旧版本备份。更高版本仍拒绝打开，不通过降级编号绕过检查。

| 表 / 记录 | 用途和约束 |
|---|---|
| `bridge_history` | instance/source/key 联合主键；保留原世界、载荷摘要、载荷字节及原文；跨世界维护运行的内部world索引槽为空字符串，公开元数据仍为null，不借用当前世界 |
| `history_partial` | 每个活动导入最多一个未完成条目；最终摘要通过前不发布为完整历史 |
| `objects.history_import` | 导入运行状态、源、扫描上界/偏移、累计页数/字节及新增/重复条数 |

独立历史库上限 200000 条、原始载荷合计 256MiB，导入记录上限 256 次。触顶拒绝新写入并保留已有证据；不自动清空、不移除未知效果或幂等记录。256MiB 是载荷计数，不是数据库、Base64 暂存、WAL、索引和备份的实际总磁盘预算。

B的7天事件/30天任务离线保留、确定性摘要及本地依赖保护已于035实现，036接入全部维护历史投影。A自动依赖导出、维护协调、历史投影/导入作业保留、长期磁盘预算与告警仍需完成。本次不修改A schema4，也不自动删除旧投影；所有内容版本计入现有200000条/256MiB预算。它不能替代MC存档与A/B/人物/记忆的一致恢复。

## 5. HTTP、SSE 和后台

接口在现有同源代理下，无新增应用登录要求；请求字段与响应结构见[JSON Schema](contracts/game.schema.json)、[OpenAPI](contracts/openapi.json)及[示例](contracts/examples.json)。

| 方法与路径（前缀 `/api/dsh/game/history`） | 行为 |
|---|---|
| `GET /status` | 最近导入、运行进度、容量；离线或游戏功能关闭仍可读，存储故障则拒绝 |
| `GET /entries?kind=&limit=&cursor=` | 原世界历史摘要倒序分页，limit 1–100；kind仅events/task_deliveries/task_versions/retention_summaries/retired_tasks/retention_runs |
| `GET /entries/{record_key}` | 完整原文及原身份/确认/归档信息，不触发游戏或发声 |
| `POST /imports` | 当前上下文和 request_id 启动导入，202 返回导入记录；同请求幂等 |
| `POST /imports/{history_import_id}/cancel` | 取消指定导入，重复取消返回该记录，不会误取消后来的导入 |

`history` SSE 仅发送有界状态与容量摘要，不携带全部历史原文。后台[MC世界管理](../../../web/mc-control.html)提供五源历史列表、各源进度、导入/取消、六类筛选、翻页及原文弹窗。维护资料显示原世界或“跨世界维护”和查阅时刻，不显示为尚未确认的游戏递送。汇总各版本分别显示，防重记录不显示为当前执行成功。未展开时首屏保持20条；显式加载更多后保持当前分页窗口，仅更新已显示条目的信息，后续大量新增记录不插入旧窗口而造成中间记录缺口。点击“刷新列表”或切换类型后，从最新20条重新分页；操作期间禁用加载及刷新按钮。23条展开后再导入到48条的检查核对全部key。旧世界名称/载荷使用 textContent；原文不解释为 HTML。断线或停用后仍可查看已保存历史。窄屏排列换行，原文可滚动。

后台历史区与正式节目独立；本改动保持既有横屏布局、圆形人物、留言左右切换及正式播放权威。没有“正在看的弹幕”卡片。

## 6. 检查范围与未关闭事项

检查覆盖原生 SQLite 的原身份、ACK/归档/未确认行、任务版本、固定上界、多字节分块、错误与只读性；A 的真实 HTTP/WS/SQLite 检查覆盖去重、冲突回滚、部分传输、取消/重启/离线、容量与存储故障；无头 Java 互通和原生 Chrome 后台检查单独留证。

这些检查使用协议/界面夹具，不能记为真实 MC、正式推理、官方直播姬播放或观众验收。各轮实际结果、原始失败及证据以[实现进度](实现进度.md)登记为准。036增加原生维护历史查询、真实SQLite维护后Java→Node导入/再次维护/旧备份恢复、API版本去重与错误回滚、后台筛选/分页/离线/窄屏及文本转义检查；未执行的项目不预填通过。完整系统仍一次交付，真实68项验收、新100段人物、完整生存与媒体链、长期资源和次日恢复继续按总计划关闭。
