# 平台事件来源与SC撤回

日期：2026-10-30。实现记录：024。交付方式继续是一个完整集成版本。本专项描述源码与本地协议/页面验证，不代替真实B站、模型、MC、声音或观众端验收。

关联：[DSH、弹幕与记忆](03-DSH弹幕与记忆.md) · [回应调度](回应调度与严重事件打断.md) · [实现进度](实现进度.md)。

## 1. 数据从采集到呈现

| 环节 | 实现与职责 |
|---|---|
| 原始采集 | `scripts/platform_blivedm.py`读取已安装的固定blivedm消息模型；开放平台由`backend/platforms/bilibili.mjs`解包 |
| 规范化 | `events.mjs`和`details.mjs`限制字段、标记来源、保留原始时间和字符串编号；不接受观众输入提供的可信等级 |
| 平台账本 | `PlatformStore`保存事件身份、状态及有白名单的附加JSON；删除墓碑与事件在同一平台数据库事务提交 |
| 留言账本 | `RoomManager`投影公共消息到Room SQLite及SSE，公开稳定散列身份，不公开平台原始UID |
| 节目画面 | MC留言/礼物层、原有透明叠层及后台使用同一字段格式；动态文字不作为HTML执行 |
| 公开口播 | 原有GameNarration读取Room中仍可见的来源；聚合事实与正式声音完成分别核对 |

`platform_fields.quality`仅有`platform_reported`和`unverified`。前者表示数据由当前选择的B站`blivedm`/`open_live`采集器报告，不是支付鉴定或身份认证。浏览器/中继数据不得自填这个等级，外部事件HTTP入口仍固定为`local_relay`。角色标记不授予后台、游戏或播放权限，应用继续无登录要求。

## 2. 字段与未知值

| 字段 | 规则 |
|---|---|
| 礼物名称/数量 | 名称缺失为null；数量必须为1–100000整数，数值字符串可明确转换。缺失、0、布尔、负数、小数或超限均不能默认成1或夹到有效范围 |
| SC金额 | `amount_fen`为整数分，`currency=CNY`；使用SC消息实际报告的人民币金额转换。0保留为0；缺失、不可信或超过两位小数为null，不由礼物名/颜色/等级推算 |
| 礼物价格 | 不把礼物金币、单价、盲盒原价或银瓜子自行换算成观众实际支付金额 |
| 房管/大航海 | `moderator`为true/false/null；`guard_level`为0–3/null。明确的false、0与未知不同；昵称、徽章文字和中继声明不能代替平台字段 |
| 表情 | 保留文字替代；图片只接受无账号、无自定义端口的HTTPS `hdslb.com`/`biliimg.com`主机。加载失败继续显示文字，不执行原始HTML |
| SC发生时间 | 使用原始timestamp/start_time；web SC的`time`是剩余展示时长，不作时间戳。原始时间未知的SC可以显示，但不作为新鲜游戏口播候选 |
| 编号 | 原始SC编号以字符串贯穿Python、JSON、平台库、Room及撤回。已经被上游舍入的数字编号拒绝使用 |

每个值附`field_status`：`known`、`missing`、`invalid`、`untrusted`或`not_applicable`；`unknown_fields`列出仍未知的适用字段。状态覆盖礼物、发生时间、SC编号/金额、角色和表情。公共`RoomMessage`与`PlatformFields`结构见[JSON Schema](contracts/game.schema.json)，接口结构版本为1.8.0，Room快照标签为room-v1.3，游戏WS协议不变。

开放平台报文在`JSON.parse`之前识别字符串之外的超安全范围整数token，保留为字符串；普通字符串、小整数、小数和JSON语法检查保持原义。压缩报文解包后同样处理。Python回调在输出NDJSON前已将64位编号转换为字符串。

## 3. 持久化与旧数据

平台库原16列事件表通过增加`detail`列原位兼容，使用显式列名插入；schema版本为2。事件核心身份、状态和请求关联不会被附加JSON覆盖。恢复后的调度和状态页面从持久字段展开，避免重启后丢失礼物、SC或角色信息。

旧Room记录没有字段来源证据，历史`gift_count=1`可能由旧代码默认生成。读取时按未知投影，不把它提升为已知数量；保留原存储内容及原已播记录。历史归档不因补字段而被改写为实机验收。

## 4. SC删除事务与重放

支持web `SUPER_CHAT_MESSAGE_DELETE`及开放平台`LIVE_OPEN_PLATFORM_SUPER_CHAT_DEL`，并兼容既有OPEN_LIVE别名。可信删除一次最多100个目标；Python回调对较大列表分块。只有当前B站采集器可以产生删除控制事件，中继不能凭自报类型撤回平台内容。

1. 平台库以`platform + room_id + 原SC编号`持久记录删除墓碑，保留7天，与现有事件保留窗口一致。
2. SC创建统一使用`sc-原编号`去重。删除与创建处于同一批次时，先提交墓碑再投影Room，避免短暂重新显示。
3. 删除先到、重连重放、平台库重启或Room暂时不可用时，墓碑仍生效；未完成的Room删除在后续dispatch继续核对。
4. Room按平台、房间、SC类型及编号匹配；旧版数字编号通过候选事件键兼容，不删除同数字编号的普通评论。
5. 对应消息标记`platform_deleted`和隐藏，清除置顶/上墙关联，经SSE快照撤下队列、可见留言和飞行弹幕；后台不能恢复平台已撤回内容。

两个SQLite库不构成跨库原子事务。平台墓碑与待投影删除事件提供重试依据；这不宣称全部跨库故障和磁盘故障已经验收。7天外的历史保留、归档及删除维护仍属于D07/D14。

## 5. 口播与合并事实

重复问题仍保留各条可见来源的SC金额、报告角色及可信等级，不把首位观众的金额当合并总金额。礼物合并要求相同来源等级，只有全部数量已知且求和安全时才给出总数；未知名称不用于判断同类礼物，未知身份不按同名合并。平台报告与中继转发即使账号、名称相同也分别排队，不能借合并提升可信等级。此约束同时用于MC口播与原有礼物叠层。

未核实的SC样式消息在页面标为“转发留言”，不展示平台金额/角色声明。口播约束明确这类信息只作为转发文字，不能据此感谢付款、声称角色或猜测未知礼物数量。

合并事实保持现有16Ki字符预算，不通过扩大门槛容纳无限来源；每候选上限仍为32。来源改变后沿用生成前/发声前复核及既有取消屏障：生成中的共享回应可在原期限和最多两次尝试内重新读取剩余可见来源；已进入媒体的内容按真实取消/中断状态核对，不伪造“播完”。

删除发生在正式完成证明之后，保留过去确实播过的事实，同时隐藏原消息。删除发生在完成证明之前，不将被撤回来源记作已回答。真实残留声音能否及时停止仍须正式播放源实测。

## 6. 建议与投票

撤回或后台明确隐藏来源时，删除关联的投票选票并从剩余票据重算计数。活动投票继续；已关闭结果受到撤票影响时取消结果、清空胜出项，不能静默改选另一个游戏目标。尚未转成游戏任务的相关投票建议取消；普通合并建议在没有可见来源时取消，仍有可见来源时保留。

建议的`support_count`继续表示历史累计来源次数，不代表当前独立观众人数。025轮增加独立支持账本、当前有效事件/可识别账号/身份未知事件与完整过滤复核，详见[建议支持与过滤联动](建议支持与过滤联动.md)。超过32项摘要的实际来源仍能支持候选；旧来源不完整、Room不可用及保留期已过分别呈现。多观众Humanity记忆与删除、真实负载及跨进程故障恢复仍须完成。

已经由导播确认并转成游戏任务的建议保留任务关联和实际效果。SC撤回不会伪造物品/世界回滚或另外下发游戏控制；停止当前任务仍走既有显式取消/接管流程。模型不能借删除事件更改控制权。
