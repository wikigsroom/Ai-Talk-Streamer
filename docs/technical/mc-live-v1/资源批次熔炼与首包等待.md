## 1. 批次选择

ControlledSmeltingTask继续从当前服务器配方读取实际输入、输出、组件和加工时长。先选择允许消耗的原料槽，再从实际燃料表中选择能覆盖整批加工的一份普通、未保护且无余料的燃料；高炉、烟熏按原先折半后的燃烧刻数计算。批次取满足下列全部限制的最大数量，燃料弱时可以降至更小批次。

| 限制 | 规则 |
|---|---|
| 炉具数量 | 普通熔炉、高炉1～4份；烟熏1份 |
| 目标缺口 | 按实际每份产量向上取整，允许最后一份配方的固有多产物，不无限超采 |
| 原料 | 必须能从同一组件兼容槽中分配完整数量，并保留已有目标成品 |
| 燃料 | 每批最多一份，其实际燃烧刻数必须覆盖全部投入的配方刻数 |
| 输出 | 整批实际产物不超过该产物栈上限；开始前检查整批可回收空间 |
| 期限 | 加工期限不超过63000ms；原GUI与根任务绝对期限继续适用 |

若没有原料，既有采集器按不超过四份的片段补料。候选材料可能对应不同实际产量，采集片段取各候选所需份数的最小值，避免为高产量候选要求不必要的数量；后续仍重选真实库存，允许继续分批。没有足够燃料时走原燃料采集与失败路径，不循环添加第二份燃料来延长本批次。

ResourceMaterialsPlan.conversionFuel把现有成品保留、指定槽N份原料和允许候选槽一份燃料同时交给MaterialAllocation。原料与燃料在同一堆栈时必须至少有N+1份可消耗容量；保留量可移到其他同类堆栈，但不能把自定义或保护组件当作允许燃料。任何缺口返回无解，由既有任务处理，不返回半份计划。

## 2. 投料、加工和服务器同步

ControlledCookingTask每次右键仅投入一份原料，累计计数直到本批所需数量；不能用当前炉内剩余数推断已经投了多少，因为剩余燃烧时间可能在投料过程中完成加工。每次点击继续强制完整服务器库存回包，禁止本地预测视作确认。

CookingExchange将构造时的每份实际产物与投入数相乘，固定整批目标。完整回包必须保持光标和主背包与当前点击的预期一致，炉内原料只能减少、产物只能增加，且“剩余原料份数＋已生成配方份数＝累计投入份数”。产物必须保持实际组件、栈上限及每份配方产量的整数倍；燃料只允许原一份消耗为空。

服务器可能先发输入槽再发产物槽，也可能反向发送。单槽回包分别核对单调数量及组件，暂时不满足上述守恒时暂停后续点击，等另一个槽或完整回包补齐。只有全部原料已经投入、输入槽为空且整批实际产物齐备才允许取出；部分产物不提前宣布成功，也不发取出点击。

加工期间已有剩余燃烧时间的处理沿用既有能力，本轮扩展的是多份加载及部分产物确认。若加工未消耗新燃料，任务仍确认取回该燃料，防止留在炉内。

## 3. 首包等待与固定期限

资源炉具和补给烟熏准备任务在识别到目标界面后，必须先等SurvivalGui记录原界面的完整初始InventoryS2CPacket，然后才能清除旧采集器状态、判断目标已满足、判断缺料或关闭空炉具。仅出现界面不表示服务器库存已到，避免用空的预测背包误判。

转换槽位仍在准备后重新捕获；制作炉具消耗了旧原料时，按既有规则关闭自有空炉具后补料。没有新公开技能、独立控制器、任务编号或根授权。

| 时间规则 | 值 |
|---|---|
| 单次点击确认 | 1500ms |
| 资源批次加工 | `配方刻数×50×投入数＋3000＋(投入数−1)×1500`，最多63000ms |
| 普通200刻配方，四份 | 47500ms，包含三份新增投料的确认余量 |
| 高炉100刻配方，四份 | 27500ms |
| 1200刻慢配方 | 单份63000ms，不允许两份批次 |
| 补给烟熏 | 仍为8000ms，单份 |
| 炉具GUI上限 | 普通熔炉/高炉绝对75000ms，烟熏15000ms |

批次加工期限从第一份原料投入时固定。收到部分产物、任务暂停或最后一份投入均不能续期；原选择次数、补给总期限及撤权优先级继续存在。撤权不自动清理操作员界面或重放旧点击。

## 4. 验证及完整交付边界

新增30项检查：批次计划与计数分配11项、服务器事务15项、实际编译接线4项。分配检查内有一项独立穷举7056种小库存、保留、投入数量及燃料候选配置，与独立的剩余容量判断比对；这些配置不额外计作独立用例。事务覆盖加工中加载、分包顺序、合并回包、组件及产量变化、无对应产物的原料丢失、数量回退、额外燃料/投料、整批取出及固定超时。
