## 已修复的实际问题

公开回复抢占游戏规划时，原DSH主机能够取消规划会话，但已进入应用回调的工具只持有规划入口原始信号。主机内部抢占信号和SDK工具超时信号没有传到正在等待的游戏查询。迟到的 `check_action.allowed=true` 因而可能使已经被打断的规划继续登记并下发任务。

修复前新增的5项回归全部失败，其中两项实际观察到本地持久任务及 `task_start`。这些证据保留于本轮 `cancellation-before-001`。这是生产工具接线缺口；修复不依赖更改模型提示词。

## 信号和工具执行路径

| 环节 | 实际实现 | 取消后的行为 |
|---|---|---|
| DSH注册工具 | `backend/dsh-bridge/host.mjs` 合并主机有效信号与SDK的 `exec.signal`，作为第三个回调参数传入 `{signal}` | 调用前、等待返回后均检查；取消的迟到结果不返回给模型，也不调用 `concludeTurn` |
| 游戏规划 | `backend/game/planner.mjs` 合并规划入口与工具执行信号，交给既有 `GameTools.invoke` | 游戏前置查询停止等待并移出pending；未受理动作不会继续下发 |
| 规划上下文 | 同一规划记录world session、control epoch、bridge boot和connection generation | 新鲜AUTO状态中只要这些绑定变化，也取消旧规划；不再仅检查模式和新鲜度 |
| 观众建议理解 | `backend/game/audience-intents.mjs` 合并理解入口与工具执行信号 | 中断登记为cancelled；本次未完成理解不产生建议或游戏任务 |
| 公开回复 | `backend/dsh-bridge/server.mjs` 将合并信号交给直接读取及narration读取 | 取消的游戏查询不提交口播媒体、不把原弹幕标记为已回答 |

第三参数是主机提供的执行元数据，不进入模型的JSON参数。既有两参数回调兼容。SDK信号契约与本机已存在的 `@deepseek-ai/dsh-tools` 0.2.0-rc.2公开类型核对；本轮没有安装、启动原生DSH SDK或调用真实模型。

`GameTools.query` 与 `GameManager.waitOperation` 原本已有信号清理；此次接线让它们接收到实际的抢占/工具超时信号。取消后查询保留终态 `GAME_QUERY_CANCELLED`，已结束查询的迟到结果不能改写它。公开回复无需等待旧游戏查询回复即可使用模型。

取消工具等待不等于撤销已经生效的游戏操作。已经受理的任务仍保留原task ID、accepted状态、unknown效果和证据，走已有显式取消、任务回执或对账流程；不自动重发，不伪造成功或撤销。

## 正常流程与权限

未取消且前置检查通过的规划仍下发一个任务；accepted继续只表示受理。未取消的自然语言理解仍产生带来源的proposed建议，保持人工审核、AUTO、lease及实际动作前置检查，不直接授予游戏控制。公开回复的声音完成仍由正式输出的PCM播放回执确定。

未增加工具、技能、API、记忆写入权限或应用鉴权。横屏布局和左右弹幕配置不变。生存preLaunch拒绝、15151处静态入口UNREVIEWED及全部完整生存/PvE/资源能力门禁继续保留。
