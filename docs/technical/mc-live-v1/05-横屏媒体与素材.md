# 05 横屏媒体与素材

## 1. 三种尺寸分开管理

| 尺寸 | 当前/目标 | 约束 |
|---|---|---|
| 节目画布 | 目标1920×1080 | 游戏全画布；留言、人物、字幕叠加 |
| 人物传输媒体 | 当前720×1280/25FPS；完整版本包含新素材profile | 同版完成新尺寸协商及旧媒体流回归 |
| 人物显示区域 | 圆形264×264；备选320×180 | 不等于推理分辨率，不把整条人物流升为1080p |

完整版本同时交付新圆形/横窗素材、显式尺寸协商和旧流兼容。旧视频裁切可用于内部定位，但不满足完整素材验收。游戏画面始终来自真实游戏捕获，不以设计占位图替代。

整幅缩放统一使用1920×1080坐标系；720P为2/3比例。人物圆形在720P直径176像素，不能承诺所有手指细节可读。最终手机观看还需实际截图/录像评审。

## 3. MC正式页面

第021轮已实现正式地址`/mc/programme?renderer=livehime`及静音预览`/mc/preview`的源码与本地A/B路由检查，详见[实际接入与边界](横屏节目与媒体接入.md)。尚未部署到官方客户端或完成真实直播验收。URL参数本身不授予播放权，仍通过既有正式消费者租约及实际回执校验。

正式页组合现有人物媒体消费者、RoomClient、GameClient和MC叠层。不要同时挂载旧竖屏RoomOverlay与新MC留言，也不使用iframe创建第二个完整人物播放器。预览可以使用静态/静音媒体，但不确认正式播放。

官方直播姬以游戏捕获作底层，1920×1080透明浏览器素材承载人物、留言和字幕。网页body、canvas外区域及包装默认透明；圆形通过显示遮罩裁切人物，不把方形背景涂黑。鼠标/键盘焦点不因后台或浮层点击意外抢走游戏操作。

透明网页素材、游戏捕获和源内音频是完整方案必须在官方客户端验证的接口能力。若当版客户端不能满足，记录证据并修订同版合成实现，不静默改回竖屏、不启动OBS，也不擅自安装额外采集驱动。

## 4. 留言与礼物

四条留言，行高100、间距10、进入间隔至少1000ms、过渡320ms；待显示队列24条、等待TTL20秒，显示寿命24秒。昵称最多10个Unicode字符、正文最多32个、最多两行，长内容使用明确截断。生产TTL依据真实经过时间，不因隐藏页面或动画暂停延长平台消息时效。

后台`overlay.mc_chat_side`通过Room保存和SSE生效；复用`web/mc-chat-position.js`移动留言及礼物容器。不替换DOM、不清队列、不镜像文本、不使其穿过准星做横向动画；人物/字幕/游戏不动。

顶部飘屏为备选两行、右向左，与feed互斥；换边保留feed设置而不改变飘屏方向，礼物仍跟随所选侧。SC只使用可信类型/金额；礼物提醒合并且不额外合成声音。

渲染只使用文本和可信本地资源。表情/头像若后续增加，先有明确平台字段和资源契约；本轮不抓取用户提供任意URL。删除/屏蔽同时清理待显示和互动候选；已经开始播音的内容按既有取消链路处理。

## 5. 媒体协议与新素材尺寸

`web/local-stream.js`的v2兼容分支保留原固定AVC配置；第021轮新增v3实际配置、尺寸/关键帧协商和reset清理。不能只改CSS或角色JSON就接入新的方形推理流；真实推理和官方客户端仍需验收。旧流取景仅用于内部对照，不作为另一个交付版本。

拟新增媒体init至少含stream_id、media_profile_id、protocol_version、width、height、fps_num/fps_den、codec、AVC配置描述、PCM格式/采样率/声道、时间基与音视频起点。具体载荷与现有v2向后兼容策略在实施时冻结新版本，不能将新字段无版本地插入旧二进制布局。

第021轮已实现`/api/studio/stream?v=3&codec=h264`源码：新增media.init/media.reset JSON文本控制帧，类型见[MediaInit/MediaReset](contracts/game.schema.json)，后续H264/PCM二进制外层继续采用现有v2包格式与样本映射，不将尺寸字段插进其字节头。v2保留Annex-B，v3视频转换为AVC长度前缀NAL以匹配真实avcC。新客户端先等待init，再按二进制分支解码；接收器保持透明转发。不能对新尺寸静默回退旧硬编码。init中的AVC description从实际SPS/PPS产生，示例AA==仅验证结构，不是可解码参数；真实NVENC和人物推理尚待验收。

流尺寸或codec变更必须先取消旧代、排空/关闭解码器、清旧帧映射、配置新流并等待关键帧；跨流时间戳不得复用。显示端的圆形/横窗切换若使用同一媒体源，仅改变取景，不触发TTS、音频重播或消费者更换。

继续使用现有H264/PCM链与回执围栏。所有有效人声样本仍携带既有request/utterance/runtime_epoch/generation映射；裁切与缩放不改变采样计数。正式编码帧率25或30由官方客户端实测锁定，不从人物25FPS推断观众端帧率。

## 6. 音频、字幕与同步

| 音源 | 路径 | 验收 |
|---|---|---|
| 人物人声 | 唯一正式浏览器源内PCM | 有效采样连续、取消准确、自然结束回执 |
| BGM | 既有Room混音 | 沿用实际PCM时钟的人声压低，恢复无跳变 |
| 游戏 | 官方客户端实际支持的单一路径 | 无物理扬声器时仍有声；不与桌面重复录制 |
| 麦克风 | 按实际人工节目用途配置 | 无用途时不混入环境噪声或回声 |

人物语音驱动BGM压低已存在；游戏音量压低是新增待验收能力，不能把两者混称已完成。先保证游戏声音可靠进入录制，再决定是否需要独立音量包络。

字幕沿用已提交口播文本及真实播放进度分页；这不是ASR逐字对齐。request不匹配、取消或无有效人声时隐藏。恢复场景清理失效字幕但保留独立留言连接状态。

所有游戏事件、语音首样本、人物呈现与正式录制保留时间关联。既有人物首播5–8秒记录不作为游戏控制或观众端时延。先用晚到口播改写、丢弃过期现场语句；若需要观众侧游戏缓冲，再验证官方客户端支持与双路对齐，不延迟操作者本地游戏窗口。

## 7. 素材交付

林知夏身份、黑长发、浅蓝卫衣和日光宿舍线索保留。圆形母版720×720、候选推理640×640；横窗母版1280×720、候选960×540，均以25FPS试验。尺寸是待测候选，不是已通过MuseTalk配置。

同版交付圆形与横窗两套完整派生包，每套2段待机＋48逐项改编动作，各段按8秒/25FPS规划，共100段。制作中的待机、说话适配、倾听、招呼小样属于内部质量检查，不单独交付。圆形检查头部/发丝、轻点头极值和手不挡嘴；横窗检查小手势和最终320×180脸部大小。每项保留遮罩后的动态片段与接缝检查。

素材包含manifest、neutral、clips、motion-index、crop-safety及qa。记录源SHA256、实际尺寸/帧数/FPS、语义、新脸框、预处理版本与兼容状态。旧48动作和两段待机不覆盖，派生缓存按素材版本隔离。

复用K02及已有权重；不为圆形窗口下载新模型。先离线媒体与CPU结构验证，再经正确设备契约做静音、受控口型、正式播放及联合负载验收。CSS裁切不自动减少推理负载。

## 8. 完整视觉服务与运行开关

既有研究候选为Qwen3-VL-4B GGUF Q4_K_M＋F16投影、llama.cpp原生CUDA，仍未安装或测评。本轮不下载。后续获准部署后，以运行锁记录构建、文件hash、输入像素上限、端口和超时。

视觉属于完整交付必需实现，运行时允许关闭；未安装、仅模拟或只实现开关均不满足完整验收。具体交付范围见08章。

只分析原始MC帧，带frame_id、world_session、capture time、purpose和裁图坐标，不分析直播姬合成后的弹幕或人物。单并发，默认最多1帧/秒；观察目的限定建筑、当前界面或可辨文字。

本版本取完整原始游戏帧，坐标为全帧范围；经[frames独立上传路径](04-接口与数据.md)交给A的短时缓存，再由本地视觉读取。游戏渲染线程仅负责取得图像，不等待JPEG编码、HTTP上传或视觉推理。后续裁图参数需扩展query契约，不默认允许任意截图来源。

结果保存caption、依据帧与unknown说明；不把模型生成的confidence数字当校准成功率。图像过期/超时只失败该查询，不能阻塞本地控制。视觉推断不得覆盖更新的结构化状态，不用于逐帧战斗闭环。

上述采集/三层上传/短时缓存、真实JPEG解码、本地适配与DSH取消已有源码和CPU协议检查；实际行为与边界见[原始帧与视觉适配](原始帧与视觉适配.md)。这不代表候选模型已安装、真实MC画面已通过或完整负载已验收。
