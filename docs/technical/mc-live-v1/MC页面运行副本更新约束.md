# MC页面运行副本更新约束

第083轮在3080正式服务中发现：`integration/dsh_bridge.py`已经登记生存提示模块，但8010页面仍返回404。LiveTalking实际从`src/LiveTalking/server/dsh_bridge.py`导入代理，既有源码更新只更新公共源码，遗漏了该副本。隔离浏览器通过不能证明正式服务已加载新代码；v29的失败证据保持原样。

## 唯一映射与停止约束

当前[运行副本更新器](../../../scripts/mc_runtime_projection.py)只管理以下映射：

| 已审查源码 | 实际导入位置 | 检查 |
| --- | --- | --- |
| `integration/dsh_bridge.py` | `src/LiveTalking/server/dsh_bridge.py` | 内容SHA-256相同，Python语法有效，映射与安装根目录匹配 |

该映射属于应用源码。[源码更新器](../../../scripts/mc_source_update.py)在同一原生操作锁内确认DSH、人物、语音、接收器、游戏和视觉六个进程锚点都已停止，再更新源码与此副本。既有原生依赖导入清单继续保留原导入事实，副本更新另写`mc-runtime-projection.json`，不能将新副本伪装为旧依赖导入时已有。

首次接管只接受当前审查源码、已核验依赖导入值，或代码内固定的v26已审查代理哈希。v26包和源码快照的固定值写在更新器中。未知修改被拒绝并留在原处；已有副本记录后，下一次更新前还必须与记录匹配。其他LiveTalking模块、模型、K02补丁、账号、用户配置和主播持久状态不在此映射范围，其他模块的源与副本差异仍需分别审计。

## 事务、准备和正式页面

更新前保存原副本及原副本记录；后续源码身份提交失败时，同时回滚副本与记录。旧环境准备与就绪检查由原更新流程归档，再重新执行本次就绪、环境准备和设备核对。新安装可在完整依赖导入后、环境准备前运行此投影步骤。

[安装就绪检查](../../../scripts/mc_readiness.py)增加实际导入副本检查；[原生准备](../../../scripts/mc_deployment.py)将副本与记录哈希写入运行文件集合。副本过期、记录缺失、安装路径不符或源码变化都会阻止准备或启动。上述检查不加载推理模型，也不授予游戏AUTO权限。

服务启动后，还要通过真实8010地址读取`/mc-player-safety.mjs`，确认成功状态和JavaScript类型，再打开正式后台核对当前原生生命、暂停提示、桌面和手机显示。浏览器必须在结束时关闭，原用户标签保留。API测试或文件相等不替代这一步。

## 验证边界

[副本事务测试](../../../tests/test_mc_runtime_projection.py)覆盖六进程停止条件、未知副本拒绝、旧记录变化、失败回滚、导入清单保留及源/副本差异；[代理测试](../../../tests/test_game_proxy.py)检查固定模块路由与类型。全部执行在3080。

此修复解决MC页面代理的运行副本遗漏。完整安装器、其余复制模块审计、许可证材料、干净Windows复现、真实死亡/重生及正式68项验收仍分别记录在[实现进度](实现进度.md)，不得由此记为完成。
