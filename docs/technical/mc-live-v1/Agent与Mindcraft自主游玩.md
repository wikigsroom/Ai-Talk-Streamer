# Agent＋Mindcraft 自主游玩增补

用户最新要求为完全由 Agent 配合 Mindcraft 自行游玩，不以人工接管作为日常执行或失败处理路径。本增补替换章节09及冻结章节13中“Mindcraft只作参考”的技术选型；历史版本和冻结摘要保持可追溯。当前测试仍使用3080上的 NAIMEI 与原离线世界，不开局域网、不增加第二玩家。

旧文档中的人工接管不能再作为自主功能缺口的补救或通过依据。后续对阻塞、资源不足、死亡和断线的正向验证要求 Agent 自动决策、恢复并核对效果；停止与输入释放检查单独保留，不把停止成功计为自主恢复成功。尚未完成这些恢复能力时明确记为待实现，不转交人工完成。

## 当前实际使用Mindcraft的范围，以及适配工作的来源

当前确实运行了Mindcraft的真实物品依赖求解代码，固定上游提交和原文摘要见[来源锁](../../../backend/game/mindcraft/upstream.lock.json)。移植只替换模块依赖注入；ItemGoal／ItemWrapper算法及原文保留。它根据真实库存和客户端收到的配方，将石镐等总目标拆成当前可执行的一小步。这是实际求解器接入；完整上游代理、Mineflayer寻路、自保与全部技能没有整体运行，不能用“完整Mindcraft已接管”概括当前状态。

当前控制链为：应用Agent调度目标 → Mindcraft拆解物品依赖 → 原生固定技能检查与执行 → 当前NAIMEI客户端 → 服务端效果回执和新观测 → 下一轮。没有已采纳弹幕建议时，内置启动目标优先推进工作台、木镐、石镐、石斧、熔炉和少量面包；不是每次动作都重新询问模型。已批准世界目标、已采纳建议及启动规划无法处理的情况沿同一DSH模型工具链处理，紧急生存检查优先。模型使用既有外接渠道，Mindcraft本身不是新下载的推理模型；3080负责现有数字人/语音、本地游戏及执行器，保持唯一人格和输入所有者。

上游[安装说明](https://github.com/mindcraft-bots/mindcraft/blob/develop/README.md)采用LLM加Mineflayer机器人，并以开放本地世界到LAN后连接为基本运行方式。当前约束要求在3080的既有未发布离线世界中，直接操作现有NAIMEI玩家、保留真实客户端画面，因此当前采用原生控制端口。上游机器人连接并不直接等价于操作这一个已经启动的图形客户端。更换成完整上游运行链会改变连接方式和控制架构，不能当作同一套已完成适配直接替换。

游戏使用1.21.1 NeoForge与大型整合包。版本号本身不是这里的主要问题；模组配方、方块碰撞、菜单和服务器结果需要按实际环境解释。上游[FAQ](https://github.com/mindcraft-bots/mindcraft/blob/develop/FAQ.md)说明会改变游戏机制的模组不在其支持范围。实际已发现木板标签613项、土径15/16格表面、半格落脚和墓碑死亡后物资变化等情况。原生执行层必须处理这些事实，再把受限、明确的数据交给求解器。

直播还增加了上游游戏机器人以外的工作：B站事件收集、弹幕建议/投票、主播语音优先、游戏事件讲述、横屏画面和唯一官方音轨。这些属于直播系统集成。另一方面，着火即全局暂停、部分道路无法走通等故障属于当前自研执行层的问题，需要由本项目修复，不能统称为Mindcraft本身的限制。

因此当前策略是继续完成同一玩家原生执行闭环，先证明采集→工作台→木镐→圆石→石镐，以及危险打断后自动恢复，再扩展长期食物与熔炼。已有木材、木板、木棍、工作台、木镐和圆石的分场真实效果；v81已在原离线档实际制作并保留石镐、石斧，连续生存仍未通过。停机、输入释放和协议检查单独记证，不能代替自主游玩达标。原生直接控制既有玩家是本项目选择的架构，也意味着本项目负责补齐这些执行能力，不能把其成本或故障都归咎于上游。
