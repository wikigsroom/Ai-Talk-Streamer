# 单人世界首帧与暂停保护

当前验证对象为 3080 原生 Windows 上的 `MC Live Offline 083` 普通生存存档，玩家为 `NAIMEI`。服务器地址由用户后续提供；当前保持单人模式，不连接旧服务器，不修改原始交付包存档。

## 问题与证据边界

v41、v42 的冷启动现场出现过桌面游戏客户区白屏。此时原生事实仍持续更新，报告 `PauseScreen`；单人世界时钟在五秒观察内保持不变。恢复游戏后再正常暂停，可以显示菜单。这些事实说明暂停和桌面显示必须分别验证。

读取 v42 第一次入世界时保留的渲染目标 PNG，可以看到游戏菜单、血量和物品栏；对应桌面截图则显示白色客户区。两个文件的生成时刻和采集层不同，不能仅凭内部 PNG 声称桌面一直正常，也不能直接据此认定显卡驱动或某个模组是根因。

对设备上自带 Minecraft 1.21.1 / NeoForge 21.1.248 库进行只读字节码核对，确认客户端 tick 在游戏渲染与窗口显示提交之前执行。原暂停策略仅检查玩家、世界、已有界面及输入清理，没有首批游戏帧回执。v43 增加这项时序保护；实际是否改善白屏，由正常完整启动后的现场证据决定。

## 实现

| 编号 | 行为 | 约束 |
|---|---|---|
| R01 | 记录同一世界、玩家、连接对象下三个连续合格的 `RenderFrameEvent.Post` | 只接受游戏已加载、无覆盖层、允许渲染、游戏界面关闭且窗口活动的帧；不调用渲染或输入回调制造回执。 |
| R02 | 冷入世界时等待首批帧，再请求普通暂停菜单 | 始终要求 `PAUSED`、任务为空、自有输入与控制清理完成；不授权 `AUTO`。 |
| R03 | 首批帧等待上限为两秒 | 没有回执时转入已有普通暂停保护并显式记录超时；避免因渲染异常无限期运行生存世界。已有加载界面仍由原游戏处理，不强关界面。 |
| R04 | 世界、玩家、连接更换后清空首帧回执 | 不把上一世界、死亡前玩家或断线前的帧当作新会话回执。正常暂停菜单可以保留同一对象范围内已得到的回执。 |
| R05 | 加载覆盖层、`noRender`、未完成加载不作为可操作游戏画面 | 仍由既有唯一控制仲裁器决定任务与输入；死亡界面、多人、开放局域网世界和人工操作规则保持优先。 |
| R06 | 输出原生显示诊断 | 包括覆盖层、渲染开关、加载完成、窗口活动、FPS、首帧计数、对象范围代次和等待超时。渲染回执明确不等于 Windows 桌面呈现证明。 |

实现入口为 [暂停策略](../../../game-adapters/minecraft/fabric/src/main/java/dev/aitalkstreamer/mc/core/SingleplayerPausePolicy.java)、[首帧记录](../../../game-adapters/minecraft/neoforge/src/main/java/dev/aitalkstreamer/mc/neoforge/NativeWorldFrames.java)、[原生端口](../../../game-adapters/minecraft/neoforge/src/main/java/dev/aitalkstreamer/mc/neoforge/NativeGamePort.java) 和 [客户端事实](../../../game-adapters/minecraft/neoforge/src/main/java/dev/aitalkstreamer/mc/neoforge/NativeClient.java)。

## 验证路径

1. 在 3080 的隔离源码目录，以实际随包 Minecraft / NeoForge 库编译。验证首帧失效、对象更换、计数上限，以及暂停、人工操作、死亡、多人、已有界面和超时保护边界。此步骤不启动游戏或模型，不计真实游戏验收。
2. 从已正常保存并退出的主菜单状态，执行正式停止、受审查整包更新、编译、八组就绪检查、本机准备、设备校验和完整启动。禁止修改运行中类或模拟物品。
3. 读取真实启动参数，确认指定现有具名离线世界、没有联机参数；核对相同世界、新会话、正常生存和作弊关闭，以及先前保存的库存。
4. 核对真实三帧回执、暂停等待未超时、普通暂停菜单、五秒时钟冻结、无任务和输入释放，再独立检查桌面截图。白屏复现即保留失败，不通过模拟按键把冷启动本身算作成功。
5. 需要恢复时使用精确归属、创建时间和最新截图保护下的真实 Windows 操作；恢复结果与冷启动结果分开。正常保存退出后再核对服务、存档和官方直播姬原有进程。

现场结果继续写入 [实现进度](实现进度.md) 与 [当前运行证据](../../evidence/mc-runtime-round-083.json)。本项不替代 D14 的长时负载和显示稳定性验收，也不改变正式验收数量。

## 显示空闲路径与 v44

v43 的实际复载确认了三个合格帧、约 30 FPS、普通暂停及五秒时钟冻结；Windows 窗口可见、未最小化、未挂起且未被 DWM 隐藏。GDI 与 MCP 两种桌面采集仍白屏，内部 PNG 则有菜单、血量和库存。因此首帧保护不能作为白屏修复结论。

随后只读查询显示：交流电源闲置 600 秒关闭显示，当时最后输入已过去 2,142,313 毫秒。保持同一受控暂停世界，只调用一次 `ES_DISPLAY_REQUIRED` 复位显示计时，没有键盘、鼠标、恢复游戏、修改电源方案或存档，桌面立即出现游戏菜单。该现场证据确认显示空闲是本次白屏的一条直接影响路径；不据一次恢复穷尽所有驱动、远程会话和显示设备组合的原因。

v44 在 [受控游戏服务](../../../scripts/mc_game_service.py) 中接入 [Windows 显示保持](../../../scripts/native_windows_display.py)：通过设备、供包、配置和进程归属检查后，主线程申请 `ES_CONTINUOUS | ES_DISPLAY_REQUIRED`，再启动自己拥有的游戏。游戏正常退出、启动失败或进程族清理都在同线程恢复原有执行状态；诊断分别记录申请和释放。它不修改系统电源计划，不模拟用户输入，不请求 away mode，不切换窗口，不授予游戏控制权。

接口语义依据 [Microsoft SetThreadExecutionState 文档](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-setthreadexecutionstate)。持续显示输出需要应用主动说明显示需求；该接口不能阻止用户主动让设备睡眠，也不代替屏幕保护程序策略。本项目仅保持自有游戏服务线程的显示需求。

[生命周期检查](../../../tests/test_native_windows_display.py) 覆盖主体异常、原执行状态恢复、申请失败、重复申请、跨线程误释放和释放失败；3080 还执行实际原生申请与成对释放。冷启动是否显示、长期无输入是否持续显示、退出后是否释放均需分别有实机证据，不能由这些边界检查代替。

首次 v43 复载检查器把未序列化的可选空覆盖层字段当作必填而失败；保留原始错误，r2 在同一未恢复/未输入会话中，结合明确的 `overlay_open=false` 重新核对通过。这是检查器修正，不计作第二次世界复载。

## 持续申请与显示计时复位的区别

v44 的完整启动和离线复载通过，生产线程已持有持续显示请求。只读 `powercfg /REQUESTS` 也实际列出自有 Python 进程的 DISPLAY 请求，没有请求覆盖配置。但内部渲染目标已有暂停菜单时，两种桌面采集仍滞留在 Mojang 加载画面；额外一次 `ES_DISPLAY_REQUIRED` 复位后，桌面立即显示实际菜单。因此 v44 的持续申请、库存复载与暂停可以分别计为通过，其冷启动桌面呈现不能算通过。

v45 在同一自有服务线程增加每五秒一次的原生显示计时复位，并记录最近成功时间、成功次数、失败次数和当前错误；已有持续请求和退出恢复保持配对。未到间隔不调用，释放后或其他线程不能复位。单次失败明确记录并按间隔重试，不因为显示维护失败而强制结束正在运行的生存世界。该维护不模拟键鼠、不切换游戏界面、不修改系统电源计划，也不向其他应用发送窗口消息。

验证需重新走正式整包启停，检查实际复位次数和新鲜时间，再独立目视首次入世界与超过原显示关闭阈值后的桌面。诊断性复位造成的恢复不能当作生产冷启动成功，四小时稳定性与其他远程/显示组合继续单列。

v45 已通过3080隔离的十项生命周期检查，以及实际 Windows 申请、计时复位和释放三次调用；其后按正式停机、整包更新、实际供包编译、八组就绪、准备和设备核验完成六服务启动。现有具名离线档的新会话核对到正常生存、作弊关闭、生命和饥饿20、两块橡木及一份原讣告；三帧和无超时回退、普通暂停及五秒世界时钟冻结通过。首次桌面截图已实际显示菜单、HUD与库存，没有使用额外显示复位、恢复游戏或键鼠入场助手。

同一游戏进程随后持续显示维护706.1秒，139次成功、0失败；最后键鼠输入已过去1513.2秒，超过交流电源600秒关闭显示的阈值。再次取得的真实桌面截图仍有普通暂停菜单，世界会话、玩家与库存保持。原自动观察器在610秒因尚未物化的临时依赖报文件缺失，保留原始失败；随后在同一未输入、未恢复的会话正确启动只读观察器取得上述证据，不计作第二次冷启动或长期运行。

最后正常保存退出，最新原生事实与实际桌面均确认TitleScreen；再经正式整套停止，自有游戏优雅退出、六项自有服务及端口关闭，同一显示申请已释放。退出前195次显示维护均成功；停止前后已保存具名世界的level.dat散列一致，原官方直播姬进程保留。以上是本次离线和显示路径的子项结果，四小时稳定性、其他远程/显示组合及完整业务验收仍待完成。
