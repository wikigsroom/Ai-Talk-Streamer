## 1. 接入的实际入口

| 入口 | 本次实际行为 |
|---|---|
| [launch.py](../../../scripts/launch.py) start-avatar / start-tts | 从设备与准备校验到创建、登记进程，共用本安装操作锁；冷启动期间已有有效PID也拒绝重复创建 |
| [start_studio.py](../../../scripts/start_studio.py) | 人物、语音按原顺序串行初始化；整组启动共享事务，后续创建、端口等待或O07/F07健康核验失败时回收本次新增服务 |
| launch.py stop | 操作互斥；新记录按PID及原生创建时刻核验归属，收取其已观察子孙进程，未确认退出时保留记录 |
| [dsh_control.py](../../../scripts/dsh_control.py) start / stop | 创建与登记、停止均纳入同一锁；原有精确server/root匹配、旧owner退出确认及开播中拒绝关闭继续执行 |
| [receiver_control.py](../../../scripts/receiver_control.py) configure / start / stop | 配置更新和启停互斥；配置、进程记录原子写入；先取操作锁，再加载接收器Web依赖；新记录停止时核验创建时刻 |
| [mc_deployment.py](../../../scripts/mc_deployment.py) prepare | 先取统一操作锁，再执行原准备锁、完整预检及凭据更新；不与上述入口的启动/关闭交错 |
| [mc_runtime.py](../../../scripts/mc_runtime.py) operation-status | 只读报告操作是否占用、动作、阶段及恢复需求；明确service_readiness_checked=false |

所有入口保留原有安装来源、mc分支、设备、GPU/batch、唯一DSH状态、模型/运行文件和准备证明校验。本轮验证没有生成真实安装准备成功凭据，没有执行下载、推理、游戏或直播姬启动；实际调用启动入口仍要求原准备检查通过。接收器继续支持独立B端角色，操作锁本身不加载人物或语音模型。

## 2. 互斥与创建归属

[native_operation.py](../../../scripts/native_operation.py)在`.setup/native-runtime.operation.lock`的首字节持有Windows内核文件锁。文件一直保留，不以文件是否存在或PID是否存活代替互斥；操作结束不删除锁文件。同一线程的嵌套入口共享事务，其他线程或进程立即返回MC_NATIVE_OPERATION_BUSY。

同一文件首字节之后保存操作元数据：操作ID、动作、阶段、控制PID、本次新进程PID及不可变的原生创建时刻。元数据只用于记录和恢复判断，实际占用由内核锁决定。路径检查拒绝越出本安装及符号链接/junction；锁、私有配置和进程记录继续由Git忽略，不进入公共源码包。

[native_windows_process.py](../../../scripts/native_windows_process.py)使用Windows Job Object与PROC_THREAD_ATTRIBUTE_JOB_LIST创建新进程。服务在执行第一条指令之前已经属于本次Job，子孙进程继承归属，不允许breakaway；标准输入为DEVNULL，仅显式复制的输入/输出/错误句柄传入子进程，不继承Job句柄。实现依据[Microsoft创建时加入Job说明](https://devblogs.microsoft.com/oldnewthing/20230209-00/?p=107812/)及[Job Objects文档](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects)。

事务提交前启用KILL_ON_JOB_CLOSE，控制进程意外退出时由系统回收本次新进程族。058原实现成功后解除清理标记；063改为显式移交Job和根进程句柄给独立worker，并保持清理标记。worker确认持久COMPLETED才进入RUNNING；父入口确认移交后退出，worker继续监督。提交失败回收worker和新增进程；COMMITTING异常与无法核实的旧owner仍需要恢复核验，不能仅凭旧记录宣告成功或已清理。

## 3. 失败处理与保留边界

事务失败先终止本次Job，并查询实际ActiveProcesses到零，再移除本事务写入的精确记录。只在记录内容仍等于本次写入时移除；同一登记文件中原有其他服务保持原值。原子登记使用同目录临时文件、flush/fsync及replace，登记异常也触发进程回收。

嵌套入口异常即使被上层捕获，也会使整组事务不能提交。端口尚未开放但登记中的精确进程仍活着时拒绝再次创建；旧格式仅有PID的记录遇到在用PID也拒绝重复创建，不能冒充新的精确归属证明。PID被复用且创建时刻不同，不视作旧owner，也不会因此终止另一程序。

清理失败保留ROLLBACK_INCOMPLETE；异常退出时的STARTING/COMMITTING记录也要核验精确owner。存在未退出owner时拒绝新启动，stop入口可进入恢复路径；未全部退出继续报告恢复未完成。只有确认旧owner已退出才可继续，不根据端口关闭推断SQLite写者已经退出。

操作记录损坏或身份无法核验时拒绝操作，不自动清空或以成功记录覆盖；损坏记录的自动修复不在本轮实现中。

原有DSH接口在开播期间拒绝shutdown的行为保持原样，不能借操作锁强行关闭开播会话。已有服务没有加入本次Job；人物/语音整组失败只回收本次新增进程，保留启动前的已有服务。

## 4. 操作与就绪分开检查

下列查询可在原生安装内使用，不启动服务：

```powershell
python -X utf8 -B scripts/mc_runtime.py operation-status
python -X utf8 -B scripts/mc_runtime.py status
```

operation-status检查操作状态；status仍检查安装准备凭据。二者均不代表节目、模型或游戏已就绪。独立start-avatar/start-tts/DSH/receiver启动命令只证明创建和登记；start_studio继续执行端口等待、O07/F07两工作者ready、service及参考音频SHA核验，并在等待中检查本次新增进程是否提前退出。人物完整媒体就绪、DSH业务就绪、MC连接、视觉及官方输出仍需要统一生命周期接线。

## 5. 实际验证与明确未完成范围

本轮在既有原生Python3.10.22中运行真实的临时标准库进程：跨进程锁争用、同线程嵌套/其他线程拒绝、父子孙三层回收、控制入口被终止后的系统清理、提交后进程存活、登记/提交写入失败、PID复用、中文环境与输出句柄、退出码259、状态查询及整组启动失败。模型、设备、端口和健康接口在入口测试中使用明确的测试替身，不把这些结果计作真实推理或MC运行。

初次入口测试发现兼容验证环境没有aiohttp；控制模块已延迟加载接收器Web依赖，锁争用可先拒绝，不新增或下载依赖。初次准备回归有两项旧断言要求操作日志字节不变，现改为仅允许新增操作日志变化并检查ROLLED_BACK；其余所有文件包括旧凭据、来源及准备锁仍须字节一致。初始失败输出与修正后记录分别保留。
