# MC整套服务启动、就绪与停止

本说明更新至第083轮的原生服务协调器。完整交付范围仍以[实施总纲](13-完整方案实施总纲.md)及[全端蓝图](09-全端实现蓝图.md)为准；横屏定稿、3080 K02/O07/F07、唯一DSH写入者、人物重制及68项验收要求继续适用。当前使用[现有离线本地世界](离线本地世界联调.md)，实际版本和最新终态以[实现进度](实现进度.md)为准。

## 统一操作入口

在当前安装目录内，用其已准备的原生Python运行：

```powershell
& .\runtime\livetalking\Scripts\python.exe -X utf8 -B .\scripts\mc_runtime.py application-status
& .\runtime\livetalking\Scripts\python.exe -X utf8 -B .\scripts\mc_runtime.py application-start --timeout 1800
& .\runtime\livetalking\Scripts\python.exe -X utf8 -B .\scripts\mc_runtime.py application-stop
```

`status`原有含义仍为安装准备凭据核对；`application-status`读取当前服务事实，不创建目录、操作锁或进程。`application-start`、`application-stop`共用安装级Windows操作锁，不允许与准备、安装、单服务启动及停止交叠。不同线程或进程竞争立即返回忙；同线程内部入口复用同一事务。

这些命令只在3080当前受控安装目录执行；本机继续用于编辑与打包。启动前核对设备、来源、准备凭据、resident-local、O07/F07参考、同机loopback接收器、官方客户端配置、视觉锁及明确的世界选择。缺失时不加载服务，不自动下载模型，不凭空生成来源凭据。修改源码或运行配置后，先走正式停止、受审查更新、供包编译、就绪检查、重新准备和设备核验，不热修改运行副本。

启动依次组织DSH唯一写入者、人物/双语音工作室、接收器、锁定的本地视觉和当前模式的MC。人物和语音的先后关系由原有 `start_studio` 维护，防止模型加载峰值重叠。工作室既有900/180/360秒分段等待继续有效；本命令的1–1800秒期限在前置校验之后计算，每阶段返回和后续轮询均复核期限。它不会中断原有阶段的内部等待，因此不承诺在调用者传入的秒数内强制结束一个既有模型加载阶段。校验和整合包加载期间不因一次状态查询超时重复拉起服务，应核对操作记录、准确控制进程和分项进度。

第083轮已将MC及本地视觉接入同一生命周期，实际管理六项服务。MC由精确登记的自有服务启动Java，视觉由精确登记的自有服务启动锁定的原生程序；不接管原有游戏或用户直播姬。完整安装包、节目端权威就绪、人物重制及全部异常恢复验收仍须完成，六项服务就绪不能据此宣布整套系统交付。

## 就绪事实和输出含义

| 检查 | 必要事实 |
|---|---|
| DSH | 当前安装登记的准确进程和监听者；状态存储、宿主、人格注入、记忆及镜像同步均就绪；未进入停止 |
| 人物工作室 | 已登记的准确进程/监听者；真实工作室接口就绪，人物ID匹配私有配置，使用本地JPEG/PCM媒体 |
| 语音 | 已登记的准确进程/监听者；resident-tts、O07/F07均就绪，参考摘要匹配 |
| 接收器 | 已登记的准确进程/监听者；角色、接收器ID和8010上游匹配同机配置 |
| MC | 当前DSH返回已连接、fresh、具有世界会话、PAUSED且输入已释放的游戏状态 |
| 视觉 | 锁定的本地可执行文件/模型/投影器逐一核对大小和SHA；本地 `/props` 的build、模型绝对路径、视觉能力、单槽及非休眠状态匹配 |
| 官方画面 | 尚无本协调器可消费的正式采集权威确认，明确返回未验证；安装了客户端、端口开放或接收器自报指标均不代替确认 |
| 新人物包 | 圆形50条及横屏50条尚未制作并验收，明确返回未完成 |

TCP端口开放本身不构成进程归属。登记需有创建时间身份、准确可执行程序和项目脚本；监听PID必须属于该根进程或其当前子进程。原进程仍在加载但端口未就绪时拒绝重复加载；不接管外部程序或旧式无法确认的PID记录。

视觉服务仅允许明确端口的127.0.0.1或IPv6 loopback HTTP；拒绝凭据、其他路径、查询和跳转。不发送图片或推理请求。文件摘要在当前查询进程内按文件身份缓存，大小/时间/身份变化均重新计算；状态查询可能读取大模型文件，但不导入模型或加载GPU。

所有命令只输出一份JSON。`application-start`的 `ok=true` 表示启动事务已提交；`services_ready=true`要求上述六项受管服务事实全部通过。`application_ready`另包含正式画面及新人物包要求，这两项当前明确为false。实际返回 `MC_APPLICATION_SERVICES_STARTED_REQUIRED_INTEGRATION_PENDING`，不能改写为“已可开播”。`complete_application=false`、真实验收0/68继续保留。正常保存退出至标题后，游戏桥接可为未连接/旧观测，MC就绪项随之不通过；这与游戏进程仍存活是不同事实。

## 回收、运行监督及停止

启动中的根进程退出、后台健康期限届满、配置检查或持久提交失败，均退出本次事务。现有Windows Job和独立监督器回收本次新增的准确进程族；既有服务和其他安装保持运行。结果分别给出实际新增数量、操作阶段和是否完成回收；创建过进程后失败不谎报“从未启动”。同一新事务内任一根进程提交后异常退出，仍由既有监督器关闭该事务内其余根进程。

改变服务状态必须调用当前安装自身的脚本；跨安装目录启动/停止在分派控制器前拒绝，状态查询仍可只读核对指定目录。显式停止先核对全部待停止服务身份及DSH广播状态；广播尚未结束或状态不可确认时，在停止任何依赖前拒绝。准确的预期退出登记覆盖整个受管停止过程，避免正常停止被误判为依赖故障。

停止顺序为自有MC、自有视觉、DSH、接收器、语音和人物。游戏仍在世界时，正式入口先请求PAUSED并等待输入释放，再向精确归属的游戏服务发停止标记；游戏服务请求关闭自己的窗口，等待优雅退出，超时才回收自己的Job。视觉同样先发自有停止标记并等待服务退出。DSH关闭接口继续复核广播竞争。恢复入口不要求重新通过GPU/准备校验，因此来源修改后仍可停止属于当前安装的准确服务。

联调结束须先通过游戏普通菜单保存退出，并核对新鲜`TitleScreen/in_world=false`、无任务、输入清空、规划和内部会话关闭，再执行整套停止。停止后检查六项准确归属及端口、保存文件、原官方进程和显示请求释放；原有未受管MC、视觉、直播姬及用户浏览器保留。跨事务故障、中途失败恢复、完整后台按钮及正式开播/结束的业务验收仍须继续完成。

## 游戏显示维护

自有MC服务在启动Java前申请线程范围显示需求，退出或异常清理时在同线程恢复原执行状态。第083轮的实机反例表明，持续显示请求被Windows接受仍可能有桌面滞留，因此增加每五秒节流显示计时复位及可见失败记录；单次维护失败按间隔重试，不因此强制杀死生存世界。它不模拟键鼠、不修改全局电源计划，也不授予AUTO。

`.setup/mc-game-process.json`记录自有Java身份及申请、复位次数、最近成功和错误；`.setup/mc-game-exit.json`记录对应申请的释放与退出结果。后台原生首帧或FPS并不证明Windows桌面已经呈现，必须独立查看实际截图。方法、已保留的失败和验证边界见[单人世界首帧与暂停保护](单人世界首帧与暂停保护.md)。
