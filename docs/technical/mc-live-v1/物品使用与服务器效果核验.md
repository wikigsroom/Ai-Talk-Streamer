# 物品使用与服务器效果核验

第020轮工程记录。分支：`mc`。本文说明已接入源码的真实客户端执行路径与仍须实测的边界，不表示Minecraft、Mixin、服务器或完整系统已验收。

[技术入口](README.md) · [游戏协议](02-游戏桥与控制协议.md) · [实现进度](实现进度.md) · [第020轮证据](../../evidence/mc-runtime-round-020.json)

## 1. 接入位置与支持范围

`MinecraftPort`将五种固定游戏goal接到同一个真实玩家：navigate/gather/craft/return_base由受控执行档处理，use_item由原生`NativeItemUse`处理。两者共享同一活动任务、ControlArbiter、固定Permit和InputOwner；不会同时拥有输入。现有用途枚举和HTTP/WS契约保持不变。

| 用途 | 本轮接入的物品与行为 | 明确拒绝或尚未支持 |
|---|---|---|
| eat | 原版命名空间内具有正营养、有效食用时长的食物；主背包寻找指定ID，必要时交换到热栏，执行一次使用 | 其他命名空间、无营养/超长使用、已在使用、无食物、饥饿条件不符；非食物饮品和其他专用用途 |
| equip | 原版玩家盔甲、鞘翅、盾牌；固定穿戴槽或副手，可核对已经穿戴的目标ID | 动物BODY槽、普通手持工具/武器的选择、其他自定义装备；绑定等条件不允许换装时拒绝 |
| activate | 原版普通BlockItem中的完整立方体，固定当前准星命中及实际放置位置；短暂受控潜行后仅发送一次放置交互 | 准星没有方块、超出距离、不可放置/未加载、目标已是同种方块、非完整立方体、多种特殊BlockItem和Mod物品；不提供无限制右键 |

完整系统仍须补齐其余支持物品、其他容器、规则与完整生存链。`item_uses`声明的是已存在的用途适配器；每个具体请求仍做物品、场景和服务器条件预检查。候选生存包的preLaunch无条件阻挡继续保留。

## 2. 原上下文和库存准备

准入和启动分别核对：游戏线程、真实玩家/世界/连接、原Permit、存活/焦点/暂停、普通生存模式、无阻塞GUI、具体PlayerScreenHandler、空光标及空合成格。实际库存总量必须与任务起始观测一致，防止把排队期间的变化算成任务效果。

主背包中的物品通过固定玩家handler槽位和热栏编号做单次SWAP。逐项保存物品与组件副本，确认前后46个槽位和光标完整状态；不按物品名忽略组件、不丢弃现有物品。准备阶段的交换不计作进食、穿戴或放置成功。

所有写入在原控制许可内执行，当前screen、handler、世界和玩家对象有任一变化即退出。内部不打开背包画面，使用当前玩家handler进行受控库存操作；服务器不支持该操作时失败，不猜测已交换。

## 3. 一次动作与服务器核对

| 用途 | 实际动作 | 服务器事实和结果条件 |
|---|---|---|
| eat | 选定原物品、持有使用键并只调用一次interactItem；观察该次使用结束后释放使用键 | 指定物品总数恰减少1；实际客户端结束状态经全量服务器库存核对；普通食物须有本次窗口内饥饿更新达到预期。满饥饿且允许始终食用的食物以服务器确认的一次消耗为食用条件 |
| equip | 将确定的热栏物品交换到确定的盔甲/副手槽；先检查canInsert/canTakeItems | 完整交换后的库存得到服务器确认，目标槽存在请求物品。已经穿戴时也取得全量核对；不捏造物品消耗 |
| activate | 固定命中/放置位置，受控潜行确认后仅一次interactBlock，再释放潜行键 | 服务器BlockUpdate或ChunkDelta包含该位置和目标方块，库存完整状态确认恰好一次物品消耗；客户端本地放置预测不能单独证明成功 |

食物转换出的碗等剩余物沿用真实客户端本次结束后的完整预测状态，再与服务器全量状态逐槽比对；不只核对原食物数量。异常组件/额外变化或不同步使任务失败/未核验，而不是宣布已正确处理全部特殊物品。

全量核对沿用固定1.21.1点击修订不匹配的同步机制。准备交换或空结果槽的无副作用核对点击，只在原任务许可内将本次revision改为-1；服务器执行该点击后返回InventoryS2CPacket。每次最多一个等待结果，1500ms超时，禁止重发。空结果槽核对要求合成格和光标均为空。

`ItemUseRepeatMixin`在原生物品任务仍有效时阻止vanilla持键自动再次调用doItemUse。真正动作由专用适配器发送；撤权后恢复普通vanilla入口，让操作者按物理键鼠继续操作。该Mixin的真实应用和时序仍须实机验证。

整个物品工作流另有10秒单调时钟上限，潜行准备最多600ms，单次库存同步1500ms；外部任务期限、原控制租约和主线程进度约束仍可更早终止。该工作流替换旧的热栏进食100tick检查，不能将新增完整流程上限描述为旧进食时限完全未变。

## 4. 收据、后续观测与收尾

`ItemUseReceipt`固定原task_id、world_session_id、epoch、物品、用途、起始量、已确认消耗、目标槽/位置、最后服务器库存修订、专用效果和干净结束标志。实际输入和选中热栏恢复后，才保存cleanEnd并通知执行器结束。

`ExecutorTaskSession`冻结当时的不可变收据，继续等待更晚的同上下文观测。缺收据、用途/任务/世界/epoch/基线不符或未完成收尾不能报告verified；进食/放置还要求后续数量与已确认消耗相容。普通库存变化、已受理和运行中均不能代替该结果。

取消/接管/断线/异常保留已确认消耗或已确认方块/装备效果为partial，不撤销已发生副作用。穿戴交换的全量服务器确认若已到达、而执行器下一tick尚未运行，取消仍保留这次库存/穿戴变化，不误记为无效果，也不报告完整成功。InputOwner按原代次恢复持键、移动输入和原选中热栏；操作者已改变的选中项保留。失败的恢复保留所有权以供重试，旧任务不能清理新任务的输入。

撤权在ControlArbiter内原子保存该代次的原因。游戏线程自行退出可能早于排队的显式取消，因此ExecutorTaskSession按原Permit查找第一次撤权原因，保留换世界、物理接管、GUI阻挡、断线或控制变更的具体事实；后续撤权不覆盖第一次原因。内存仅保留最近64次记录，历史已淘汰时返回未知而不借用后一次原因。该记录不授予控制权、不延长租约，也不代替实际输入释放。

## 5. 验证范围及未关闭项

本地检查包含：完整库存交换状态机、组件/光标/其他槽位不匹配、单条待确认、超时/撤权/迟到/跨线程、不可变收据、任务结果与后续观测、部分取消和失败，以及真实Java桥和Node持久任务的三种用途往返。物品/服务器效果在夹具中明确模拟。

锁定的真实Minecraft类另做无初始化的字节码接口核对；新Mixin的最终打包和intermediary映射逐项检查。它们不证明Mixin已在实际客户端应用，也不证明真实服务器保留原版处理流程。

原版库存/饥饿/方块更新不包含本项目task nonce。对象/连接/世界/许可、单条等待与时间窗口可以限制归属，但同一handler/sync/位置复用后的迟到包及服务器主动修改仍须真实异常用例证明；本轮不声称取得服务器签名的语义回执。实际食物剩余物、装备组件/诅咒、方块属性/位置、物理持键/选中恢复、插件限制、接管和服务器拒绝均保留D03/D04/D14门槛。
