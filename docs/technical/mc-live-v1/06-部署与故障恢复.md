本章包含实施要求与已明确标注的实际入口，不表示本轮启动任何服务。尚未实现的完整启停、安装与恢复入口不作为现成运行命令。

## 1. 当前分支与设备边界

当前开发在mc，继承rtx3080目标；设备选择仍要求deploy/rtx3080。029新增[MC原生应用profile与准备](MC原生应用profile与准备.md)，通过真实mc源码清单、本机程序和文件证明接入原有启动检查。未完成真实本机准备时仍拒绝启动，不能修改`.setup/deployment-origin.json`或切换分支规避。

完整MC发布需绑定source_branch=mc、layout_id、完整运行锁、执行档、媒体版本与实际设备映射，并纳入现有预检的显式校验路径。已实现的[mc-native-3080-v1](../../../configs/deployment-profiles/mc-native-3080-v1.json)只证明本机环境准备路径，完整媒体/视觉/素材/负载和发布包仍需补齐。完整功能推荐双机目标，见[08章](08-完整交付规划.md)；候选配置为`configs/releases/mc-split-a4090-b3080-v1.json`及`configs/deployment-profiles/mc-split.json`，均尚未创建。单3080采用完整功能的前提是通过同一验收，不另设减少功能的交付版本。

MC profile必须与真实来源构建记录一致，由正常准备流程生成来源证据；不得仅添加“允许mc”分支例外跳过检查。当前继承FP16 batch4与`state/female-a-3080-k02`不擅自变化；未来双机profile必须绑定其真实A4090/B3080角色、对应参数及独立状态根。任何状态根不同时运行旧版和MC版DSH，启用前做一致备份。

4090仍暂停，现有契约是48GB规格的A推理/B接收、batch8，不适用于普通24GB4090。双机MC profile、K02激活、依赖安装和控制恢复属于完整版本内待完成的运行准备与验收，不由这套文档自动执行。

## 2. 原生环境清单

032已接通[项目源码包导出与无Git原生安装](MC源码包导出与原生安装.md)：新目录按已审查整包摘要和全部文件核验，独立来源记录绑定安装位置；环境依赖/模型准备与既有设备启动检查继续单独执行。该源码ZIP不包含完整应用依赖和媒体，完整安装及干净环境验收仍待完成。

## 3. 运行锁与准备产物

运行锁至少含：源码commit和branch、设备target与应用profile、GPU规格、推理batch/state root、Java/MC版本、Mod文件/hash、执行档、规则能力、正式媒体profile、官方客户端版本、预检结果与测试证据。

准备过程只下载获准依赖；新视觉模型保持未安装状态，不能因文档列出候选自动下载。游戏资源/平台账号由现有合法安装流程处理，不写入公共Git。

单机联合试验可从1080p、游戏60FPS上限、8区块视距、6区块模拟距离、Java堆上限6GiB开始；这是研究起点，CPU/RAM未知时必须调整并记录，不是性能承诺。

## 4. 启动顺序

1. 核对mc、工作区改动、设备契约和来源，取得一致备份及本地运行锁。
2. 执行既有部署预检及未来MC profile检查；不匹配则停止，不加载模型。
3. 启动既有宿主/接收器和MC GameManager，初始PAUSED；模式与自动任务不从历史恢复。
4. 启动独立MC实例，Fabric握手、能力核对、完整快照；先以task_ledger只读核对中断任务。missing/conflict或仍非终态时保持停控，不重发旧动作。
5. 在官方客户端加载游戏源与正式MC素材，静音预览不取得权威；先做本地录像。
6. 连接实际平台采集，确认事件来源/房间正确；本地准备态不声称公开直播中。
7. 先人工陪玩；只有中断任务已核对、技能验收和显式操作满足时才开启AUTO。历史检查点只供事实参考，不自动恢复输入。

这些步骤不等于本次已执行。没有正式播放源时可以做只读游戏开发，但不能将其视为完整互动直播就绪。

## 5. 下播与正常停止

停止接收新目标 → 请求B停控并核对inputs_released → 取消/排空口播按既有生命周期处理 → 保存任务终态及检查点 → 结束本地平台会话与记忆候选 → 关闭本任务创建的预览/连接/测试服务。

官方客户端公开开播/下播状态单独确认；本地按钮和浏览器关闭不证明B站已经下播。不关闭用户正在使用的无关窗口，不终止所有Chrome/Java/Python进程。按进程归属登记关闭自己的资源。

## 6. 故障矩阵

| 故障 | 即时动作 | 恢复条件 |
|---|---|---|
| 文字模型超时/额度不可用 | 停新高层规划，已授权本地任务按健康租约继续或到时结束 | 渠道恢复后新快照重规划，不重播旧回复 |
| 视觉失败 | 失败该查询，继续已验证结构化能力 | 新帧与服务健康；不补播旧描述 |
| A/B控制连接断开 | B租约到期停控、升epoch、释放合成输入 | 新连接＋完整快照，保持PAUSED待明确恢复 |
| 状态通道过期但心跳仍在 | A拒绝新任务，本地状态异常按看门狗退出 | 新鲜状态连续恢复并重新检查前置 |
| Minecraft退出/换世界 | 本地取消任务、新world_session、清旧状态 | 新世界登记与能力/规则核对 |
| 任务卡住/无进展 | 到任务时限停止，核验部分效果 | 明确失败原因后新目标或人工处理 |
| B崩溃/断电 | 无法即时确认；恢复后先PAUSED，旧任务不重放 | 真实状态与本地账本核对，未证实效果标unknown |
| DSH宿主重启 | 旧controller_session失效，本地租约退出；A保留B最后版本并标记待核对 | 新宿主及唯一写入者、只读核对B任务终态、新播放租约；不自动AUTO |
| 人物/TTS失败 | 停该口播、隐藏字幕；按既有O07/F07回退 | 有效媒体与正式回执恢复，不造已播状态 |
| 正式播放器丢失 | 既有DSH停止发新口播；默认联动请求游戏PAUSED | 播放源实际恢复＋游戏重新授权，二者分别确认 |
| BGM/游戏音轨缺失或重复 | 停止错误路径，本地录像核对 | 单一路径可听且不重复 |
| SQLite不可写/磁盘满 | 拒绝新动作、停控并暴露storage_error | 修复空间/权限，一致性检查后重新准备 |
| 弹幕平台断连 | 显示连接状态，停止虚构新留言；游戏可按导播策略继续 | 实际事件恢复，旧事件不重复感谢 |

正式播放器丢失的游戏联动需要新增实现：既有播放回执保护只覆盖媒体，不能宣称它已经停止游戏。若A已不可达，B最终仍以本地租约退出。

`/game/panic`同时请求本地停控和已有Room panic，各分项独立确认。默认不能把“人物已静音、游戏未确认”合成绿色成功；本地热键是网络失败时的接管入口。

## 7. 监测与日志

| 维度 | 指标 |
|---|---|
| 游戏 | 平均FPS、1%低分位FPS、帧时间分布、可观测时TPS、输入释放耗时 |
| 状态/控制 | 状态年龄、序号缺口、重连、租约剩余、拒绝旧epoch数 |
| 任务 | 受理/启动/结束时间、成功/失败/取消、部分效果、重复请求 |
| 文字模型 | 排队/生成耗时、调用次数、取消/超时、token统计 |
| 媒体 | 实际呈现FPS、音频欠载、包缺失、解码错误、有效采样回执 |
| 资源 | GPU利用率/显存、RAM、CPU、磁盘、网络与编码负载 |
| 互动 | 留言速率、过滤/过期/溢出数、候选等待、事件到首播时间 |

统一日志关联run_id、game_instance、world_session、task_id、request_id、speech_request_id、utterance_id；不混用各层epoch。采样资源初始1Hz；关键事件即时记录，日志有界轮转。

跨机统计先记录各进程内耗时和RTT，校时并报告误差后再估计单向时间。观众CDN单独测量；本地文件或播放器回执不能证明观众已经收到。

## 8. 回滚与恢复演练

回滚先本地停控并确认，再停止MC服务、保存一致数据库与运行锁，切回已核验的旧媒体应用profile。保留原素材/声音/历史数据，MC布局不以覆盖旧文件实现。

旧数据库恢复到对应schema的二进制；不将新活动库直接交给旧程序。不从另一设备复制活动state、凭证或来源记录。需要状态迁移时另有一致备份方案。

当前A库schema3的已有库迁移会分别保存v1/v2一致快照；这是迁移保护，不能替代运行数据库、MC存档和媒体运行锁的完整备份。B端仍为独立的单所有者schema2 SQLite，具有JSON迁移备份、事务转移、本地旧boot/世界归档及原生backup/restore核心，见[B端恢复约束](B端账本与恢复.md)。B恢复要求游戏桥停止、同安装身份和哈希/版本/完整性核验，并先保存恢复前快照；活动数据库不能整文件覆盖。A/B状态、MC存档、媒体锁和后台维护尚未形成统一恢复入口。未知效果缺少账本证据时不能修改原任务或重放动作；当前可经[后台复核](世界会话与后台复核.md)单独记录人工确认，原结果继续未知，关联目标重新复核后再规划。

演练至少覆盖A退出、B断线、桥重启、换世界、正式播放源退出、磁盘写失败和下播重启。恢复成功必须同时核对“没有残留自动输入”“没有旧任务复活”“没有重复口播”，而非仅看进程重新运行。
