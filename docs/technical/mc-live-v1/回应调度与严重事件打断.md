日期：2026-10-30；分支：`mc`。对应023轮本地实现，属于同一完整交付候选。本文说明已存在的源码行为，不能替代真实模型、MC、正式人物声音、官方直播姬和观众端验收。

## 1. 调度权威与边界

`backend/game/narration-scheduler.mjs`由既有GameNarration调用，只负责候选合并、排序、主题间隔和严重事件取消决策。DSH、StreamState、人物/TTS、正式PCM完成证明和游戏控制权威均继续使用现有链路。没有第二个模型循环或声音消费者。

关闭自动回应会终止现有自动候选及其请求，重新开启不补播旧候选。手动播报属于既有Room操作，不被此开关或危险自动打断接管。游戏动作、模式和输入租约不由口播设置修改。

## 2. 后台配置

现有`POST /api/dsh/game/config`接收`patch.narration`，使用同一个expected_revision比较并保存。旧schema1配置可以缺少narration；读取时补默认值，下一次正常保存持久化，不修改设备部署配置或来源收据。未知字段和超出范围的值直接拒绝。

| 字段 | 默认值 | 范围与含义 |
|---|---|---|
| enabled | true | 自动公开回应开关，不替代MC总开关 |
| merge_window_ms | 3000 | 0–5000；0关闭合并，窗口从第一条到达算起 |
| aging_step_ms | 2000 | 500–5000；每等一个步长增加5点等待权重 |
| topic_cooldown_ms | 3000 | 3000–15000；普通相同主题提交间隔 |
| critical_interrupt | true | 是否允许严重危险中断普通自动回应 |
| interrupt_fresh_ms | 2000 | 500–3000；严重来源本身必须仍在此时距内 |
| interrupt_cooldown_ms | 10000 | 5000–60000；两次自动危险中断的最小间隔 |

后台以秒显示五个时长，提交时转换为整数毫秒。编辑中的草稿保留首次编辑时的版本，不被SSE刷新覆盖；冲突返回409，保留本地草稿并提示明确载入当前设置。所有设置仍通过原有无应用登录的接口完成。

## 3. 来源合并与事实

只合并同一广播、B站房间和世界会话内、尚未提交且attempt=0的候选，最多32个不同来源。生成开始后的上下文不会吸收新到达消息。合并不增加过期时间，重复来源在候选终结后也不会再生成一条回应。

| 来源 | 相同主题的确定规则 | 保留内容 |
|---|---|---|
| 留言 | NFKC、首尾/连续空白和大小写规范化后完全相同 | 首个仍可见原文、所有关联ID及首末时间；不同措辞不擅自判为同义 |
| 礼物 | 相同可靠user_key与gift_name | Room中的逐事件名称、数量、时间及可安全求和的数量；无可靠身份不按昵称合并 |
| 游戏事件 | kind、task_id、item_id与entity_id相同 | 原事件、序号、时间、严重程度和data；保留最高严重程度 |
| 任务/建议/投票结果 | 不合并成另一项结果 | 各自的任务或互动事实与完成关系 |

来源内容在使用时从Room或可靠游戏事件账本读取，不另存留言全文。隐藏首条留言后，使用剩余可见来源及其真实平台身份；全部不可见则停止。生成中来源集合改变会使旧上下文失效，再按既有次数和原期限核验。平台终态按每个成员的可见性分别记账，隐藏成员不能因另一成员正式完成而变成COMPLETED。

游戏变化只累加每个原事件明确提供的health_delta/count_delta，缺少任意一项就保留该总量为null并列入unknown_fields，不能用两次“剩余生命”猜第一下受伤量。礼物目前继承既有平台/Room归一化字段，原始缺失字段的可信标识、SC金额和完整平台字段生命周期仍待D06完成；本轮数量合并不证明这些上游事实已经完整。

同题多个观众共用一个公开回应，当前模型会话采用首个可见来源的现有平台身份，正式完成后标记所有仍可见关联留言。它不等于已为每位关联观众写入独立Humanity记忆；多观众记忆归属、去身份化和删除联动仍须单独实现与验收。

## 4. 等待权重与背压

| 组别 | 基础权重 |
|---|---:|
| urgent | 80 |
| question | 30 |
| task | 25 |
| gift | 15 |
| status | 10 |

权重=基础权重+min(50, floor(等待毫秒/aging_step_ms)×5)。同权重按创建时间，同一毫秒保留持久化入队顺序；不使用随机ID决定先后。较早的礼物或反馈可以超过刚到的问题。当前question仍是既有留言入口分类，完整问句/点名与普通聊天的语义区分尚待完成。

紧急候选单独优先选择，连续两条后给普通候选机会；紧急组内先选择仍新鲜的严重来源，再按等待权重排序。普通主题冷却期间跳过该候选，继续寻找其他可回应主题，事实重生成不被自己的间隔拦截。紧急来源和任务结果不受普通观众冷却错误压制。

总开放候选上限16。满载从等待项最多的普通组中选择较低权重、较新候选让位，保护已经提交、重生成等待和已等较久的候选。普通新消息不能挤掉满队列的紧急来源，一般危险也不能挤掉满队列的新鲜严重来源。历史仍只保留最近512条；主题提交时间仅保存哈希键，清理60秒之外记录并限制256项。

## 5. 原始有效期

游戏现场仍为8秒，留言与礼物仍为30秒。有效期取“候选创建＋TTL”和“原事件发生＋TTL”的较早值，合并、等待、重试均不续期。已超过8秒或超出2秒未来容差的游戏事件保留可靠账本和ACK，不能包装成新现场口播。任务和互动终态继续使用其候选原期限及明确的历史事实措辞。

过期现场不会自动改写成过去时补播；是否具有回顾价值，以及回顾来源如何投影为独立历史叙事，仍是完整节目调度待办。这样不会把现场TTL检查误报为已完成全部回顾节目能力。

## 6. 严重事件的受控打断

只有critical游戏事件，或者damage来源与当前新鲜玩家观测均显示生命不高于4，才成为严重候选。打断时重新检查严重来源本身的发生时间，不能让一个较新的普通合并事件替旧严重来源续期。

必须同时满足：自动回应及危险中断开关开启；节目LIVE、人物上下文就绪且未进入后台维护；正式播放权有效、世界会话和观测可用；既有取消处理器和媒体命令存在；目标为本调度器关联的普通自动回应；不在中断冷却内。普通important事件排队，不中断人工/私人公告或已在回应的紧急事件。

先持久保存被打断候选及原因，再调用现有StreamState.cancel。沿用代数屏障、模型AbortSignal与串行媒体cancel→speak；记录实际cancel_barrier_id，并拒绝旧模型迟到结果。后续选择重新读取候选版本，保留interrupted_request_id和递增revision。

“cancel_requested”只表示已走现有取消路径，不是已经静音或已经回答。取消异常记cancel_unconfirmed，被打断项为unknown；只要旧请求仍活跃，就不提交第二条声音。真实取消响应、残留声音、模型底层中断和官方源表现仍须正式链路核验。

## 7. API与界面

GET narration在原分页与active_items之外返回scheduler：当前设置、下一候选ID及最近一次中断记录。候选可包含source_ids、topic_key、severity、首末来源时间、等待毫秒、当前权重、主题冷却、被谁打断和所中断请求ID。新增字段不改变正式PCM完成判据。

“主播回应”后台展示合并条数、等待时间、中文终止/打断原因及来源记录。原始观众文本和ID均按纯文本渲染。调度设置不改变冻结直播布局、留言侧、人物遮罩或游戏控制。
