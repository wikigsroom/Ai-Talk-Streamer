## 1. 目标采用候选集合和绝对数量

MaterialTargets保存`候选物品集合 → 绝对库存目标`。相同集合跨祖先及子任务取最大目标；不同集合分别保留约束。每个任务最多64组、原根最多64个活跃任务，合并后最多4096组及4096种物品；每组最多256种候选。已有原根256次材料选择预算和停止清理规则继续生效。

| 目标和库存 | 结果 |
|---|---|
| 煤或木炭共5份，现有煤1、木炭5 | 可消费煤1；剩余木炭5仍满足目标 |
| 煤或木炭共5份，现有煤1、木炭4 | 都要保留，不能烧掉一份燃料 |
| A或B共3份，同时B或C共3份，现有B4 | 同一B3可以满足两个绝对库存条件，可消费B1 |
| A或B共4份，另外A至少2份，现有A2、B5 | A2必须留下，可消费部分B |
| 目标5份，现有候选合计2份 | 现有2份全部保留，不提前占用不存在的未来物品 |

这种共享适用于绝对库存条件。原料、燃料和每个配方格是实际消费需求，仍必须分别分配；同一份物品不能同时作为两份输入。

## 2. 用消费上限表达保留量

对每个目标组，读取当前36格主背包中所有候选的合计数量`have`，允许该组消费的上限为`max(0, have - target)`。每项实际消费必须同时遵守所有组的上限。组件限制仍通过实际允许的槽集合进入分配，不把不同组件的堆栈直接互换。

MaterialAllocation先把不相交或彼此包含的组放进同一个整数流网络。对于交叉组，验证候选分配；若某组超出上限，按必然需要减少的实际槽位数量继续搜索，保留所有可能的可行最优解。相同状态去重，整次计算共用最多2,000,000步及4096个搜索状态；超过预算沿用固定材料分配上限失败，不把未证明的部分结果当成成功，也不自动重放任务。

返回的分配只描述实际消费，不再制造一份独立的“保留分配”。采集缺口来自遵守全部约束后的最大可用输入，因此不会因给多个重叠目标重复占位而额外采集。旧单物品调用仍通过同一新规则计算；旧独立预留流接口保留给其既有纯计算调用和回归检查。

## 3. 原生入口共用目标

| 入口 | 对接内容 |
|---|---|
| ControlledSmeltingTask / SmeltingPlan | 保存完整候选集合，完成判断与保留量采用同样的合计数量含义 |
| MaterialReservations / ResourceMaterials | 原会话、世界、玩家、连接和原根任务持有分组目标；停止只释放本任务记录 |
| ControlledRecipeResourcesTask | 显式材料与目录配方采集共同计算祖先约束和自身目标，按实际缺口请求材料 |
| CraftSpec / ResourceRecipePlan / CraftPlan | 当前服务器配方及组件候选与同一组消费上限联合分配 |
| 单份进食、补给原料和燃料 | 原有singleUnits、consumable、conversionFuel入口继续调用，共用新的集合约束 |
| 建材数量、垫脚、垃圾选择及GUI丢弃 | usable、removable采用联合容量，保留部分堆栈时仍禁止整组丢弃 |
| 光标与副手 | 按当前外部候选加主背包候选总量，对包含该物品的每个目标组取最严格可消费量 |

不增加任务控制器、库存点击者、权限或自动重试。实际消费前的原生上下文、保护物品、组件、槽位与服务器确认检查继续有效。外部候选检查没有替代完整容器事务，也没有将所有容器中的库存纳入目标。
