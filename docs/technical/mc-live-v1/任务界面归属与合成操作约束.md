# 任务界面归属与合成操作约束

第018轮实现记录，属于同一[完整交付](08-完整交付规划.md)中的D03/D04工程进展。当前仅绑定原生背包和工作台界面，完整容器类型、真实Minecraft/Mixin/服务器验收仍未完成；生存候选的preLaunch继续无条件拒绝。

第019轮进一步接通[公开craft专用事务](合成事务与服务器同步核验.md)，材料分配进入实际点击、组件/剩余物和服务器同步；事务期间也禁止其他上游开关窗和换料。下文“公开craft尚未支持”为第018轮历史边界；真实GUI及完整配方范围仍须验收。

## 1. 同一个任务和同一份许可

界面类型和容器编号本身不能授权操作。`TaskGuiLease`记录当前根任务所有者、原控制Permit、客户端线程、世界/玩家对象、打开前handler和syncId，再将首次符合预期的界面对象、handler对象与syncId固定下来。新的同类界面、同编号的新handler、换世界/玩家或撤权都不能继承原授权。

游戏桥仍如实上报inventory/container，不将界面伪装成gameplay。`BridgeCore.observe`只有在当前受理任务及epoch匹配、实际端口核验当前对象归属成功时继续AUTO；menu/death/unknown保持停控。`ExecutorTaskSession`也复核同一实际GUI。开始新任务、恢复AUTO与公开前置检查仍要求gameplay，界面租约不会产生新控制权。

| 生命周期 | 原生候选约束 | 到期或不符 |
|---|---|---|
| 等待打开 | 1500ms，固定原世界/玩家、预期类型、前一handler与syncId | 迟到响应不能绑定 |
| 背包打开 | 本任务主动创建的精确InventoryScreen、玩家自身handler及原syncId | 不接受其他背包对象或任意菜单 |
| 工作台响应 | 本任务先与具体工作台交互，新CraftingScreen/handler及正的新syncId；方块仍为工作台且在限定距离内 | 不接受箱子、熔炉、交易等其他窗口 |
| 已打开 | 3000ms无进度期限，单次打开绝对上限15000ms | 观察不会续期，过期停控 |
| 实际槽位/配方操作 | 原授权下成功的操作才刷新无进度期限 | 不突破绝对期限或任务/控制租约 |

MC工作台打开响应没有可回传的客户端交互请求ID。首次绑定依据上述类型、时间、世界、方块、前一handler及新syncId约束，不能独立证明服务器响应来自某个请求。绑定后的所有操作再固定实际对象。真实服务器乱序/主动开窗、模组窗口与高时延仍须验收；不能据此关闭全部GUI或合成结果门槛。

## 2. 实际调用链

1. 直接调用`MinecraftClient.setScreen`、`ClientPlayerEntity.closeHandledScreen`以及交互管理器的interactBlock/clickSlot/clickRecipe，经过固定五条`gui_*`编译路由进入`SurvivalGui`。原policy的控制授权仍保留，路由签名不符在编译前拒绝。
2. 生存执行器也可能通过模拟使用键进入MC内部的doItemUse，绕过第三方JAR中的直接interactBlock调用。本轮在`InputOwner.click → ClientExecutor.beforeUse → SurvivalGui.beforeUse`补上同一原Permit内的预期工作台登记；已有待回应交互不重复发送。
3. `SurvivalGui`只在当前SurvivalAuthority根任务作用域内进行实际操作。背包必须由本任务主动打开；工作台先登记目标位置再发交互，异步到达后固定实际GUI对象。
4. 直接槽位操作复核当前player、交互管理器、handler、syncId、槽位范围和操作按钮。支持受限的PICKUP/QUICK_MOVE/SWAP/THROW/PICKUP_ALL；其他操作继续拒绝。无可见GUI时仅允许当前玩家自身背包handler，不把未知容器当背包。
5. 配方操作同时复核当前服务器recipe manager中的配方对象，旧配方/重载前对象不能直接继续点击。这仍不是材料分配到搬运、每批craft_result、动态产物/剩余物的完整实现。

普通gather的内部资源链可消费这些约束；公开craft尚未声明支持。本轮没有仅增加capabilities布尔值来宣布合成、普通PvE或完整生存完成。

实际通用转换为36处AltoClef与50处Baritone，另有23项Baritone回调转换。AltoClef由上一轮37处减少一处，是因为StorageHelper关窗补丁已直接调用专用`SurvivalGui.close`，无需再包一层通用写入口。13721条静态未分类指令仍包含读取和内部赋值，不能与选定转换数量相除得出副作用覆盖率。

## 3. 自然结束与人工接管

自然完成回调先进入`ControlledTaskRunner.beforeComplete`，仍处于原有效作用域时关闭本任务拥有且光标未持物的界面，再撤销根任务、停树、清输入，最后请求新的观测核验效果。界面关闭失败或光标仍持物时不报成功，执行完整清理并保留未知结果。

人工接管、租约撤销或取消时，根任务先失效，注销GUI所有权并停止后续槽位操作。撤权后的收尾不关闭当前界面，操作者可以继续处理光标与物品。上游StorageHelper的关窗补丁改为专用入口：撤权作用域内只做状态收尾，不发关窗包，也不在清理时获取新任务许可。重新AUTO仍需操作者回到gameplay并明确授权。

## 4. 检查与未完成范围

纯核心检查执行身份、handler/syncId、打开/无进度/绝对期限、原授权撤销、线程和清理；真实编译字节码检查五条路由与实际sink签名。Java↔Node使用编译游戏桥、持久任务和真实核心租约，但界面/玩家/物品效果由测试夹具提供，不是实际MC。

本轮保留首次往返检查的失败记录：启动后首份新鲜快照可能先于输入清理确认，测试入口现等待真实inputs_released；另一次冷启动账本打开耗时接近原启动等待期限，根因仍未关闭。没有放宽生产或夹具的既有期限，也不把后续通过当成所有间歇问题已修复。

最终数量和产物见[实现进度](实现进度.md)及[第018轮证据](../../evidence/mc-runtime-round-018.json)。完整写点/包/反射审查、其他容器、真实物理接管、界面和服务器异常、完整craft/PvE/补给/资源链与68项联合验收继续在同一完整交付中完成。
