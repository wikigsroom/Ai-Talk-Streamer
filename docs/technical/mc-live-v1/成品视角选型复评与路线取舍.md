# 成品视角选型复评与路线取舍

日期：2026-11-03；分支：mc。此页是此前三方案比较和固定gpt-6-luna视觉评估的产品取舍补充；遇到路线推荐口径差异，以本页的最终成品优先级为准。源码能力、实测事实与冻结原件保持原有边界。

## 一、结论

**当前没有证据证明原生方案最终会比Whale Craft或dsh-mc-agent做出更好的AI直播成品。新的选型建议是把dsh-mc-agent列为优先验证的游戏执行候选；现有原生方案作为已实测基线和特定模组环境的兼容备选，Whale作为较轻的基础路线。**

该建议不是候选已经胜出或已经替换运行方案。dsh尚未在当前服务器/世界、玩家和直播取景条件下完成验证，不能预先记为可用。原生已做出的短链成果同样不能证明长期自主生存或完整节目质量更优。

## 二、此前偏向原生的原因与修正

此前优先保护三个已有事实：当前350模组NeoForge离线档未开LAN、原NAIMEI图形客户端和玩家数据已有绑定、真实客户端取景已接入现有节目。原生方案可以在这些条件下继续执行；Mineflayer候选需要服务器入口、协议/内容兼容和独立玩家/取景安排。

这些是短期接入约束与迁移成本，不是原生方案在自主游玩、节目效果或维护方面天然更优的证明。此前建议把“现有环境继续推进方便”过多地延伸成“最终应继续选择原生”，对自主生存能力复用和长期维护成本的权重不足，应予修正。

已经编写的代码、文档和测试数量不能成为继续自研通用游戏技能的理由。应保留可复用的接口与证据，并按剩余投入和最终节目结果选择执行器。

原生的单输入所有者、租约、结果核验、原档兼容等价值应单独评价；它们不是必须与全部自研寻路、战斗、容器、配方和长期策略永久捆绑。

## 三、公平比较的范围

当前项目是一套主播系统，两个仓库是DSH游戏插件。保留相同的gpt-6-luna、林知夏人格、DSH/Humanity记忆、B站入口、声音、人物、字幕、后台和直播布局，仅比较游戏观察/执行及其适配成本，才是成品选型的有效对照。

不能用“当前已有B站、人物和后台，而候选仓库没有”给原生游戏执行器加分。更换执行器也不意味着这些上层业务都要重做。另一方面，候选并未自动接通当前定制宿主，工具、图片、任务语义、状态和停止规则仍需适配。

同样，真实客户端画面应作为独立取景要求。使用Mineflayer执行并不逻辑上排除真实客户端取景，但必须解决取景身份、权限、视角跟随、音效与GUI一致性；不能声称配置同名NAIMEI就能接管已有图形玩家，也不能把mc_observe重建图当成完整直播源。

## 五、修正后的推荐定位

| 编号 | 方案 | 推荐定位 | 选择依据 |
|---|---|---|---|
| 1 | dsh-mc-agent | 优先验证的MC执行候选 | 现成通用技能更广，与现有DSH方向一致；应优先检验是否减少自研和带来连续有效游玩 |
| 2 | 当前原生方案 | 已实测基线、特定模组兼容备选、可复用观察/控制契约来源 | 当前原档接入优势明确；保留原件和可复用能力，不据此默认继续扩展所有底层技能 |
| 3 | Whale Craft | 基础工具路线或轻量需求候选 | 宿主入口清晰；当前成品要求含长期生存和丰富互动，不因基础较轻就优先于其扩展版 |

如果dsh在必要协议、原模组内容、玩家身份或实际取景上无法满足成品需求，且修复成本明显高于原生，则原生才有继续承担主执行器的充分工程理由。不能仅以尚未验证为由长期拒绝验证候选，也不能在验证失败后假装已经迁移成功。

若最终换成dsh身体，现有Mindcraft物品求解器能否通过统一目标接口复用须单独评估；dsh本身不是Mindcraft运行时。用户此前Agent配合Mindcraft、完全自主的方向没有被本次研究静默删改。

## 六、用什么结果作最终决定

比较在同一外部gpt-6-luna、同类任务、相同预算及可比起始状态下进行。连接兼容性先于成果比较；不兼容的候选不能通过更简单世界的成绩冒充对原环境通过。

| 编号 | 必须回答的问题 | 有效证据 |
|---|---|---|
| A01 | 能否在目标环境真实游玩 | 连接、玩家数据、区块/实体、配方/容器和真实取景可用 |
| A02 | 是否持续产出可看的内容 | 有效成果/分钟、目标完成时间、无进展时长、重复动作和失败重试；单纯转圈或看状态不计成果 |
| A03 | 是否真正自主 | 食物、工具、战斗、路线阻塞、死亡/断线后的自动恢复；不由人工完成任务 |
| A04 | 主播是否理解并回应观众 | 真实弹幕到决策/声音时延、建议执行及效果反馈，游戏同时继续推进 |
| A05 | 画面和声音是否像成品 | 实际游戏视角、镜头连续性、人物动作、同步、长停顿与游戏音效 |
| A06 | 能否稳定维护和交付 | 联合负载、资源预算、状态恢复、更新回滚与同版验收 |

这些是同一次完整交付内的选型与工程验证，不拆成缩小功能的分批成品。最终仍按完整D01–D15、原68项及全部联合验收要求交付；[117项冻结待办](../../freezes/20261103MC/03-全范围剩余事项.md)不因路线研究消失。

本轮仅修正评估文档和推荐优先级，没有安装候选、修改游戏/模型运行代码、开LAN、迁移世界、连接远端或启动测试；没有使用Docker/WSL/虚拟机，也没有创建浏览器标签页。当前实际运行基线与冻结原件保持不变。
